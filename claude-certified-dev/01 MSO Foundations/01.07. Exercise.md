# 01.07 Exercise: Predict the Behavior (about 6 min)

Source: Developer Module 1, screen 7 of 9. Four scenarios, each tied to one foundation (sampling, prompting mode, request shape, context budget). You pick the option that predicts the behaviour and gives the right reason. Three of four correct earns partial credit. I did not submit it; the answers below are the ones the teaching screens support.

1. **Classification at temperature 0 vs high temperature, repeated runs.**
   Low temperature concentrates probability on the likeliest tokens, so the label is far more consistent, though never guaranteed identical even at 0. High temperature spreads the distribution, so wording and even the label can vary. A classifier wants the low-temperature behaviour. (See 01.02.)

2. **Wrong output structure under zero-shot; what changes with multi-shot?**
   Two or three correct input/output examples show the exact structure and usually fix it where more instruction text didn't. It does not retrain the model, and it costs extra tokens on every call, so use the fewest examples that make output reliable. (See 01.04.)

3. **50,000 documents overnight, nobody waiting.**
   Use the batch pattern: submit, then poll for completion, accepting latency for a lower per-token cost. A synchronous loop ties up the app and risks rate limits; streaming gains nothing with no user watching. (See 01.05.)

4. **Long multi-turn agent session; context keeps filling.**
   The context window is a fixed token budget that history and tool results gradually fill. Oversized input is rejected before generation; input that fits but hits the ceiling mid-generation returns truncated output with the stop reason `model_context_window_exceeded`. Typical symptom: it worked in testing, then fails as inputs grow. The app must trim or summarise history. The model does not silently drop turns and the window does not grow. (See 01.02.)
