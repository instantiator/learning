# 05.05 Contributing Back: Teaching (about 12 min)

Source: Developer Module 5, screen 5 of 25. Title: "Moving an asset from private reuse into shared infrastructure a maintainer accepts".

## Starting point
Packaging for reuse (05.02) already did most of the work: parameters show it can be configured, documented assumptions tell a maintainer the expected environment, and the bundled eval lets them confirm it still works. A contribution channel receives that packaged asset as one unit (version, install steps, components) so a team that never spoke to you gets the same working setup.

## Match the contribution to the channel
Contributing back = moving an asset from private reuse to shared infrastructure through a documented channel. Each channel suits a specific kind of contribution:
- **Claude Cookbook:** a GitHub repo of focused reference implementations: self-contained single- or multi-pattern examples that run end to end.
- **Open-source MCP servers and tools:** each lives in its own repo with its own contribution conventions.
- Sending a full multi-component application to the Cookbook is a mismatch: reviewers are set up to review one focused pattern, so it stalls. This is one of the most common reasons a contribution never gets reviewed.

## What lets a maintainer verify (the bar is verifiability, not cleverness)
1. The code does one thing (a sprawling contribution makes the reviewer reconstruct your intent).
2. An example shows it running (no harness for the reviewer to build).
3. A test proves it works (verify without reproducing your reasoning).
4. A short statement names the assumptions (else the first failure becomes the maintainer's problem).

## Rights and attribution come first
Licensing and attribution decide whether a contribution can be accepted at all, so they precede technical review. Code from a customer engagement may have constraints on where it can go. Confirm you have the right to contribute it and attribute anything you built on; skipping this creates a problem for legal to unwind later.

## Worked example
The customer service agent case: a reusable conversation-handling pattern built in an engagement is stripped of customer specifics and prepared as a general Cookbook example. The contribution motion is shared across all three roles in this curriculum; the Developer's part is technical readiness (focused code, example, test, assumptions, rights check). Engagement context comes from the broader team.

## Contribution-readiness reference
| Channel | What a maintainer checks | Licensing and attribution | Example and test bar |
|---|---|---|---|
| Cookbook for a focused example, or the tool/server's own repo for a tool or fix | The code does one thing and can be read in full | Confirm you have the right to contribute engagement code; attribute prior work | A runnable example plus a test that proves the behaviour, not just a description |

- **Handles well:** a packaged asset needs only the example, test and rights check to become shared infrastructure.
- **Adds cost:** clearing the maintainer bar and the licensing gate is real work beyond making the code run for you.
- **Use something else:** if code carries an engagement licensing constraint you can't clear, don't contribute it; escalate to the owner.
