# 05.06 Contributing Back: Watch Out (about 2 min)

Source: Developer Module 5, screen 6 of 25. Title: "The pull request a maintainer could not verify".

## The scenario
A developer opened a contribution with the exact code that solved their own problem. It worked for them, which is exactly why it lacked what a stranger needs to trust it.

## The exchange (condensed)
- Developer: PR open three weeks, no review; the code works, I use it daily.
- Maintainer: it probably works for you, but I can't tell: no test I can run, no example proving the behaviour, nothing saying what it assumes about the environment.
- Maintainer: a contribution a reviewer can't verify sits at the back of the queue until someone has time to reconstruct it. A focused PR with a test and an example gets reviewed fast because there's nothing left to reverse-engineer.

## Why it broke
The code was right, but the maintainer couldn't verify it without reconstructing the developer's work. The gap is easy to miss because the author already has the missing context; the example, test and assumptions statement seem obvious to them but not to the maintainer, and a reviewer who must reconstruct intent always does it last.

## What to watch for
A PR stalls on what the reviewer can't verify. Before opening a contribution add: the example that shows it running, the test that proves the behaviour, and a short statement of what it assumes. These move a contribution from the back of the queue to fast review.
