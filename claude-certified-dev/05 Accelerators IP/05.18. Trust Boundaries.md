# 05.18 Trust Boundaries: Teaching (about 14 min)

Source: Developer Module 5, screen 18 of 25. Title: "Coordinating several Claude deployments with the trust boundaries holding under review".

Accelerators, deployments and trade-offs now meet in one application. Connecting components multiplies the places where identity, secrets and untrusted input can cross, so identify every boundary before connecting anything.

## Map who does what first
A multi-component app coordinates more than one Claude capability in one workflow, e.g. an API request triggers a Claude Code task, which reaches a customer system through an MCP server. Each component contributes something the others lack; every connection is a crossing point. Map components before wiring them.

## The trust boundary is where data moves
A **trust boundary** is the point where data or instructions move from one deployment environment to another: exactly where the injection and access controls of Module 4 apply. Content fetched by a Claude Code task is untrusted when it reaches the next component; the receiver treats it as data, not instructions. Core discipline: treat every seam as a boundary; don't assume a component is trusted because it behaved correctly alone.

## Least privilege applies to the whole app
Give each component only the access its task needs. Each operates under an identity, and the application is only as contained as its **most privileged seam**: one over-scoped component is the weak point even if the rest are tight. Scoping each to its role keeps a steered component from reaching beyond its task.

## Regulated review pulls it together
A regulated review requires justifying audit logging, residency decisions and permission controls across the full application. For regulated deployments, Bedrock and Vertex AI are typically the platforms that satisfy regional residency constraints. Confirm ZDR and HIPAA BAA eligibility for each component against the Anthropic Trust Center and platform.claude.com before scoping.

## Multi-component integration map
| Component | Contributes | Trust boundary at its seam | Control that enforces it |
|---|---|---|---|
| First-party API | Orchestrates the workflow; holds the entry point | The request entering the app from outside | Input validation and the identity the call runs under |
| Claude Code task | Runs agentic work; may fetch external content | Content it fetched, untrusted downstream | Treat fetched content as data at the next seam |
| MCP server | Reaches a customer system to read or act | The system access it holds on the app's behalf | Scope the server to least privilege and log the access |

- **Handles well:** naming every seam as a boundary and scoping each component to least privilege makes a multi-component app deployable under review.
- **Adds cost:** mapping seams, enforcing controls at each and logging crossings adds design and audit work.
- **Use something else:** if a seam can't be secured, don't ship around it; escalate to a human owner.
