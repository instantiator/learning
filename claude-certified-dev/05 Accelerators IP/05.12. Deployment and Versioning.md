## The question
Packaged or contributed, an asset is just code until something runs it. Two decisions: **where it runs** and **how to lock its version**, so an upstream change isn't an untracked production change. The platform choice is rarely technical merit alone: it's usually shaped by where the customer already has cloud infrastructure, identity management and compliance agreements. First question: which platform does the customer already trust and operate on?

## Deployment platforms
The **deployment platform** is the environment where the workload runs. The same model can run in several; the customer's existing cloud usually decides.
- **First-party Claude API:** Anthropic's own environment; typically gets new features first.
- **Claude Platform on AWS:** accessed through the customer's AWS account, using Anthropic's model IDs and lifecycle; inference is Anthropic-operated, outside the AWS boundary.
- **Amazon Bedrock** has two integrations: *Claude in Amazon Bedrock* uses the Messages API at `/anthropic/v1/messages` with broad feature parity (a features-not-supported list exists, so confirm feature-specific needs in Bedrock docs); *Claude on Amazon Bedrock (legacy)* uses InvokeModel/Converse with ARN-versioned identifiers.
- **Google Vertex AI:** the same idea inside Google Cloud.
- **Third-party platforms** such as Microsoft Foundry embed Claude in a product the customer already uses. Foundry has two hosting forms: *Hosted on Azure* (currently Opus 4.8, Sonnet 5, Haiku 4.5; inference end-to-end on Azure; generally available) and *Hosted on Anthropic* (all other Foundry Claude models; Anthropic-operated infrastructure). Residency for regulated customers depends on the model's hosting form; confirm the split with Microsoft at build time.

## Identity and residency come from the platform, not your code
Bedrock uses AWS identity and keeps data inside the customer's AWS boundary; Vertex uses Google Cloud identity and boundary. Both offer regional routing when residency is a constraint. Matching the platform to the customer's existing compliance agreement avoids a data-residency review from scratch.

## Pin the version
Versioning stops a model or prompt change becoming a silent production change.
- Every model ID points to a specific snapshot. Aliases (Opus, Sonnet) are convenient but evolve and may resolve differently across platforms. A pinned full model ID resolves to a fixed snapshot, so an upstream update is a deliberate choice.
- Also version the prompt and the asset alongside the code, and keep the prior version available so a regression can be rolled back. An unpinned deployment makes every upstream update an untracked change to your output.
```python
# Pre-4.6: a convenience alias can resolve to a new version without you knowing
model = "claude-haiku-4-5"
# Pre-4.6 pinned snapshot: fixed until you change this line
model = "claude-haiku-4-5-20251001"
```
For Claude 4.6 and later the model ID alone pins a snapshot; for earlier models you need the ID plus a date suffix. Verify the current convention at platform.claude.com at build time.

## Promote through the eval
Gate promotion on the eval suite: send a new version to a portion of traffic, compare with the pinned baseline, promote or roll back on the result. The eval stops being a one-time test and becomes the deployment gate.

## Decision table
| Platform | Identity and data model | Choose when | How version is pinned |
|---|---|---|---|
| First-party Claude API | Anthropic identity and terms | No binding cloud or residency constraint; want newest capabilities | Pin full model ID, keep prior snapshot |
| Claude Platform on AWS | Anthropic identity and terms, via customer's AWS account; inference Anthropic-operated outside AWS boundary; lifecycle follows Anthropic's deprecation schedule | On AWS but want Anthropic model IDs, lifecycle and feature parity with first-party | Same model ID format as the Claude API (e.g. `claude-opus-4-8`); Anthropic's schedule (confirm at publish time) |
| Claude in Amazon Bedrock | Messages API at `/anthropic/v1/messages`; broad feature parity (confirm specifics); data stays in the customer's AWS boundary | On AWS, want broad parity, hold a compliance posture there | Full model ID with the `anthropic.` prefix; partner retirement dates differ from Anthropic's; confirm at publish time |
| Claude on Amazon Bedrock (legacy) | AWS identity and billing; InvokeModel/Converse; ARN-versioned identifiers | Existing InvokeModel/Converse integration not yet migrated to the Messages API | ARN-versioned identifiers per Bedrock's versioning controls |
| Google Vertex AI | Google Cloud identity, IAM and billing; regional or global endpoints for residency | On Google Cloud with a compliance posture there | Full model ID in Vertex's format, pinned before rollout; partner retirement dates differ from Anthropic's |
| Third-party platform | The wrapping product's identity and billing (Foundry hosting-form note above) | Customer already runs the platform that embeds Claude | Per the platform's versioning controls |

- **Handles well:** matching platform to customer cloud and pinning keeps a migration reviewable and a rollback possible.
- **Adds cost:** pinning, retaining prior versions and eval gating add release-process overhead to every deployment.
- **Use something else:** for a throwaway prototype that never ships, a moving alias is fine.
