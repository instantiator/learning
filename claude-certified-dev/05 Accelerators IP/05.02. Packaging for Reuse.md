# 05.02 Packaging for Reuse: Teaching (about 16 min)

Source: Developer Module 5, screen 2 of 25. Title: "Packaging a working build so the next engagement starts from an asset".

## Why
The costliest thing on a team is engineering time spent rebuilding the same thing for the next customer. An **accelerator** is a solution packaged so future engagements start from a working foundation, not a blank repo. Packaging for reuse = separate engagement-specific code from the reusable core, expose the specific parts as parameters with documented defaults, so the asset is configured, not rewritten. Do it while the build is fresh: reconstructing intent months later, after the person who knew why a value was hardcoded has left, costs more.

## Three asset types, each packaged differently
| Asset | Bundles | Correct packaging |
|---|---|---|
| Agent template | System prompt, tool schemas, loop structure | Pull domain-specific values into configuration with documented defaults, so a new team sets values rather than edits the loop |
| MCP server package | The tools it exposes, their inputs, the scope the installing team controls | Document each tool input and let the installing team set scope, so it installs into a new environment without code edits |
| Eval suite | Graded test set plus judge rubric | Ship dataset and rubric together so a new team can run them in their own context. The same suite doubles as a deployment gate: run a new model version against a pinned baseline score before promoting it to production |

Most common mistake: shipping an agent as loose scripts instead of a template. They run, so look reusable, but customer-specific values are buried across files and the next team copies and diverges them instead of configuring one asset.

## Document code and assumptions
Code shows behaviour; docs must cover what can't be inferred from source: assumptions about the environment, expected inputs, failure modes already handled, and the eval defining "still works". Otherwise the next team treats the asset as a black box and rebuilds it.

## Bundle the audit log
A regulated customer's reviewer asks what data the asset touches, what identity it acts under, and what log it leaves. An accelerator without these passes the demo and stalls at the first security review, so treat the audit log as part of the package.

## Packaging checklist
| Asset | Parameterize | Document | Bundle for audit |
|---|---|---|---|
| Agent template | Every per-customer value: prompts, paths, scopes, credentials by reference, thresholds | Environment assumptions, expected inputs, handled failure modes, the eval that defines working | Data touched, identity acted under, log of what the asset did |
| MCP server | Scopes, credentials by reference, per-customer paths | Expected inputs per tool, scope boundaries, handled failure modes | (same audit bundle) |
| Eval suite | Thresholds and dataset paths per customer or environment | Rubric logic, what scores mean, the baseline the asset is pinned to | (same audit bundle) |

- **Handles well:** parameterising while fresh turns one delivery into an asset the next engagement configures in hours.
- **Adds cost:** separating generalisable from customer-specific parts and documenting assumptions adds real time to the first build.
- **Use something else:** for a one-off the customer will never reuse, skip packaging; ship and move on.
