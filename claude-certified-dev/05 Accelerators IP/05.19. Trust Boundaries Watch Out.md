# 05.19 Trust Boundaries: Watch Out (about 2 min)

Source: Developer Module 5, screen 19 of 25. Title: "The seam nobody marked as a boundary". Shown as a pairing-session transcript.

## The scenario
A developer connected three components that each passed their own tests; verified parts feel safe to join. Each was trusted in isolation, but a seam between two trusted parts isn't automatically trustworthy.

## The session (condensed)
- Dev A: all three components pass their own tests; I just wired them up.
- Dev B: where does the Claude Code task send what it fetched?
- Dev A: straight into the next call as part of the prompt; it's just content pulled from the customer page.
- Dev B: that content is untrusted; if it carries instructions the next component runs them, because we never marked that seam as a boundary.
- Dev A: but each component was trusted on its own.
- Dev B: and the seam between them wasn't. Nobody treated it as a boundary, so fetched content crosses as instructions.

## Why it broke
Passing its own tests says nothing about the seam. The fetched content was untrusted the moment it left the Claude Code task, yet was passed into the next call as if trusted instructions. The boundary existed in the data flow but wasn't marked, so no control checked it. Every point where data crosses between deployment environments needs an explicit boundary control, regardless of how each component behaves alone.

## What to watch for
A component trusted in isolation doesn't make the seam leaving it trustworthy. Mark every place data or instructions cross between deployment environments as a boundary, and put a control there that treats fetched content as data, not instructions (as in Module 4's security section). The seam nobody identifies is the one a steered action crosses.
