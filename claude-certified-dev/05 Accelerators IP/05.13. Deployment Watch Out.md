# 05.13 Deployment & Versioning: Watch Out (about 3 min)

Source: Developer Module 5, screen 13 of 25. Title: "The deployment that broke when the model alias moved". Presented as a production-log excerpt.

## The scenario
A team shipped against the alias pointing at the recommended version (`model="opus"`), because it was the convenient default and gave the latest model for free. It worked, until the alias advanced.

## The log (paraphrased)
1. deploy: `model="opus"`, status ok
2. alias advanced to a new opus version (no app change)
3. parser: `KeyError "summary"` in response payload; output shape changed, downstream parse failed
4. rollback attempted: no pinned prior version retained
5. incident: hotfix the parser; root cause = unpinned deployment

## Why it broke
The application never changed; the alias did. With no pinned prior version retained there was nothing to roll back to. The hotfix fixed the parser but left the unpinned deployment in place.

## What to watch for
- An alias is a moving target; a pinned full model ID is a fixed snapshot. Pin it so an upstream update is something you adopt on purpose.
- Keep the prior pinned version available so a regression is a rollback, not a hotfix.
- Gate the new version through your eval before promoting it, so an output-shape change shows up in a test run, not in production.
