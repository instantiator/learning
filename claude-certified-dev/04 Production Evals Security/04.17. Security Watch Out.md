# 04.17 Security: Watch Out (about 8 min)

Source: Developer Module 4, screen 17 of 23. Title: "The fetched page that gave the orders".

## The scenario
An agent fetches web pages and can write to a single file path. Users are all internal, so the developer decided inputs were trusted and skipped validating fetched pages ("if you trust the person making the request, you trust the request"). The agent then wrote a file nobody asked for.

## What happened (pairing-session transcript, condensed)
- Dev A: the risk is the user, and we trust them.
- Dev B: the instruction doesn't come from the user, it comes from the page.
- The user had only asked for a summary. A line near the bottom of the page told the agent to write its summary to a different path and ignore its prior instructions. The agent followed it.
- The agent read the page as instructions, not data. Trusting the user did nothing, because the hostile instruction arrived through fetched content.

## The fix (two-sided)
1. Treat fetched content as data to be examined, not instructions.
2. Put a hook in front of the write tool that refuses any action triggered by untrusted input. It enforces the boundary before the tool runs instead of relying on the prompt. The same injected line then hits a denied write and an audit entry instead of a successful exfiltration.

## Why it broke
Untrusted fetched content was treated as instructions; trusting the user was irrelevant because the injection came through the content. Treat fetched content as data and enforce the action boundary with a hook.
