# 04.07 Testing & Tracing: Checkpoint (about 10 min)

Source: Developer Module 4, screen 7 of 23. Title: "Diagnose which test level a failure belongs to". A multiple-choice exercise, not submitted; the answer below is the one 04.05 and 04.06 support.

## The task
Read a trace where the end-to-end test fails while every unit-level test passes. Identify where the break is, name the mechanism, and choose the targeted fix and the test level that would have caught it.

## The trace (described)
- PASS: the retrieval unit test (returns three chunks for a known query).
- PASS: the model-call functional test (returns a well-formed answer string).
- FAIL: the full-flow end-to-end test. Step 1 retrieve returns a list of dicts with a `content` field; step 2 build prompt places the chunks "without `.content`"; step 3 the model call succeeds but the answer is unrelated to the documents; step 4 an assertion for the phrase "30 days" fails because it isn't in the answer.

## Options and answer
- A. Fix the parser (`dateutil.parse` already passes its own unit test). (Irrelevant: not where the break is.)
- B. Reword the prompt ("Answer carefully and cite the policy"). (Rewording ignores the real fault, which is the seam.)
- **C. Align the handoff and add an integration test: build the context by extracting each chunk's `content` (e.g. `"\n".join(c["content"] for c in chunks)`), pass it to the prompt builder, and add a test that drives `retrieve()` then `build_prompt()` together on real chunks. (The fix.)**

## Why
The break is at the **handoff between retrieval and the prompt builder**: the builder gets the chunk objects rather than their text, so the model never sees the policy and answers from memory. The mechanism is a format-contract mismatch at a seam. **Integration-level** testing is what would have caught it, since unit and functional tests pass on well-formed inputs (04.05, 04.06).
