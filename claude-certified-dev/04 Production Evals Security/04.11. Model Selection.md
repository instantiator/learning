# 04.11 Model Selection in Production (about 10 min)

Source: Developer Module 4, screen 11 of 23. Title: "Model selection in production".

## Framing
Earlier screens kept a system inside its cost budget once the model was chosen. This one covers the choice that sets that budget: which Claude model runs the workload. **Cost management optimises spend within a model; model selection sets the baseline that optimisation works from.**

## The family and its tiers
Claude models trade cost, latency and capability:
- **Fable:** most capable, for the most demanding reasoning, coding and agentic work.
- **Opus:** demanding work above what Sonnet handles.
- **Sonnet:** the balanced default for most production workloads.
- **Haiku:** built for speed and cost efficiency on tasks that fit its envelope.
The same prompt runs on any of them, so model choice is a per-workload lever you can change without rewriting the application. Confirm the current lineup and IDs in the platform docs when you build. (Same ladder as 01.03 and 02.13.)

## The latency, cost, quality trade-off
- Stepping up buys quality at higher per-token cost and usually higher latency. Stepping down buys speed and lower cost at risk of a quality drop.
- A higher tier can sometimes be faster and cheaper per request if it reaches an answer in fewer tokens than a lower tier would.
- Price the cost of a mistake into the calculation: saving a few dollars a day on a lower tier is a bad trade if the quality drop causes errors with large downstream cost.
- No globally correct choice, only the right one for a task at a quality standard. Make the trade-off measurable instead of reaching for the most capable model by default, the most common and most expensive model-selection mistake in production.
- Default path: start with Sonnet; move up to Opus only when an eval shows Sonnet missing the quality bar; move down to Haiku only when an eval shows the quality drop is acceptable for the task.

## Routing: a default model plus an override
One model needn't serve everything. A common pattern: send the bulk of traffic to a balanced default and route particular request types to a larger or smaller model on a cheap signal read from the request (task type, input length, a difficulty classification). It's the same routing idea as retrieval routing (04.05), applied to model choice: pay for the more capable model only where needed. If every request is the same shape, skip the router and pin one model.

## When to step up and down
- **Step up** a tier when an eval shows the current model failing on the hardest cases in your traffic and a wrong answer is costly.
- **Step down** when an eval shows a cheaper model holding the quality bar on the bulk of traffic, freeing budget and latency.
In both directions the eval is the instrument: promote a model change on a measured score against your cases. The eval from 04.02 is also the gate for a model decision.

- **Handles well:** matching each workload to the cheapest model that meets its quality bar, measured on an eval rather than assumed.
- **Adds cost or complexity:** routing adds a classification step and a second model path to maintain.
- **Use something else:** for uniform traffic at one quality bar, pin a single model and skip the router.
