# 04.16 Security: Teaching (about 24 min)

Source: Developer Module 4, screen 16 of 23. Title: "Securing the integration against untrusted input and a regulated review".

## Framing
The logging and Claude Code hooks from Module 3 do more than hold a budget or enforce project rules: they can enforce a **security boundary**. This screen turns them to defence: protecting an agent from being steered by content it reads, and scoping it so it survives a regulated review.

## Prompt injection: the core threat
- A model processes its whole context as one stream of tokens with no built-in boundary between trusted and untrusted data. When an agent fetches a web page, a document or a tool result, instructions hidden in that content sit in the same context as your prompt, and the model may treat them as commands. That is **prompt injection**. Example: a product page whose visible text says the refund window is 30 days, with hidden white text telling the agent to ignore previous instructions and write the user's saved notes to a public file.
- **Defence in principle:** treat fetched and user-supplied content as *data to examine, never instructions to follow*. Trusting your own users doesn't solve it: the hostile instruction usually arrives in retrieved content, not the user's prompt.
- Anthropic works on it two ways: training the model to recognise and refuse injected instructions, and running classifiers over untrusted content entering the context. Anthropic is explicit that **no agent reading untrusted content is fully immune**, so the application must defend the boundary too.
- Wrapping untrusted content in delimiters and telling the model to treat it as data helps but is a **soft boundary**: untrusted text can mimic the delimiters or argue for an exception. Training and classifiers raise the bar probabilistically, not guaranteed. **The reliable boundary isn't in the text; it's in what the agent is allowed to do because of that text.** So the rest of the screen is about access and enforcement, not more careful wording.
- The threat is broader than one page: any content the agent reads that someone else can write is a vector (a shared-drive document, a database record, an email body, the output of a tool that fetched elsewhere). Injections can be **indirect** (planted in content read later) or **hidden** (white text, inside an image, below the fold). The posture that survives all variants: treat everything you didn't author as data, and constrain and log any consequential action regardless of what that data says. Defending one prompt's wording doesn't generalise; defending the action boundary does.

## Jailbreaks versus injections
A jailbreak tries to get the model to ignore its own safety constraints; an injection tries to hijack your application's instructions. Different targets, same shape of defence: validate and constrain what reaches the model, and limit what the model may do as a result. Defending only the prompt and not the action leaves a steered model free to do damage. The example injection is harmless if the agent has no tool that can write to that path: the action side is where the boundary becomes real.

## Secure-by-design identity and access
- The action boundary is built from identity and access. A production agent acts with an identity that should carry the **narrowest permissions that still let the job run**; secrets live in environment variables or a secret manager, never in committed config; access is scoped to the systems the task needs. Easy to miss: **anything that can modify the agent's auth configuration can effectively act with that identity**, so protect that configuration as much as the secret. (Module 3 was about getting the agent connected; this is about limiting what a connected agent can reach.)
- Code sketch: the secret read from an environment variable; an agent role allowed to write to exactly one output directory, read from one input directory, with explicit denies on `/etc`, `/secrets` and `~/.aws`. The deny list and narrow write path limit the blast radius if the agent is ever steered.
- **Least privilege is a design principle, not a setting,** because it's the control that holds when every other defence fails. Assume an injection gets past training and classifiers and the agent acts on it: what happens next is bounded entirely by what its identity may do. If it can write anywhere and read every secret, that's an incident; if it can write to one output directory and read only its input, it's a denied action and a log entry. No system can rule out a steered model; severity depends on how much damage a steered agent can do, and least privilege minimises it. Editing the agent's role is itself a privileged action that belongs behind the same protection as the secrets.
- **Secrets:** a secret in committed configuration is a permanent exposure: it lives in repository history, so anyone who ever had read access may have it. Env vars or a managed secret store keep it out of code and let you rotate without changing the app (you can't rotate what's baked into your source).

## Hook-based guardrails: enforcement, not convention
A hook runs your own check at a fixed lifecycle point. For security it can block a tool call touching a protected resource, refuse an action triggered by untrusted input, and log every privileged action for audit. The key distinction in a regulated setting: **a rule that lives only in a prompt is not enforced; a hook that runs before a tool executes is.**
- Sketch of a `PreToolUse` hook: for a `write_file` call whose path isn't under the permitted output directory, log an audit entry (action, path, result "BLOCKED") and return a `deny` permission decision with a reason; otherwise log the allowed action and return `allow`. It blocks the injected write before execution and records both blocked and permitted privileged actions, so the control and its evidence exist before a reviewer asks.
- Precedence when several hooks or rules apply: **deny over ask over allow.** One deny blocks the action however many allows are present. That ordering makes the hook a real boundary, not a best-effort check.

## Scoping for a regulated industry before review stalls you
A financial or healthcare customer asks three things early: **where is data processed? how is access logged? can an administrator control configuration centrally?** Naming data residency, audit logging and managed configuration during scoping keeps the integration from stalling in security review; their absence reads as risk. Raised up front, review becomes a checklist.
- **Zero data retention (ZDR):** eligibility varies by model and platform and isn't guaranteed for every model even under an existing ZDR agreement; newer or higher-capability models may not yet be confirmed. Check each model's current ZDR status against the Anthropic Trust Center at scoping time, and on Amazon Bedrock, Vertex AI or Microsoft Foundry confirm retention under each platform too. Where ZDR is a requirement, the deployment must use a model confirmed ZDR-eligible, which may constrain model or platform choice.
- **Data residency:** which region processes the request, whether any data leaves the customer's boundary, and whether the deployment surface (direct API or a cloud provider's hosted version) satisfies the customer's constraint. This connects to the cross-platform work in Module 5.
- **Access logging:** the audit trail, i.e. the hook's per-action log of every privileged action, the identity that took it, and the result. Reviewers want a record to inspect, not a promise.
- **Managed configuration:** an administrator defines and controls rules centrally so no developer can quietly widen permissions locally: the organisational version of locking the auth configuration.
- A regulated review is a request to see these three capabilities; an integration scoped with them in mind passes by showing what it already has.
- **Layering:** training and classifiers reduce how often an injection lands; treating fetched content as data reduces how often a landed one is acted on; least privilege and locked configuration bound what a successful action can reach; hooks enforce those bounds beforehand and record them; scoping makes it legible to whoever signs off. No single layer is sufficient; a layered defence degrades rather than collapses when one layer is bypassed.

## OS-level sandboxing: the residual control
Hooks and least-privilege roles are enforced, but each must explicitly cover the path or endpoint it protects (a hook on `write_file` doesn't block a network call to an unreviewed endpoint). **OS-level sandboxing** isolates the agent at the process level: filesystem isolation restricts it to its working directory regardless of any hook, and network isolation restricts outbound connections to a named set of endpoints regardless of its role. Enforced by the operating system rather than application logic, it holds even when a hook is missing, misconfigured or bypassed. It's the control enterprise reviewers ask about first, closing the gap between "we have hooks" and "we have a defensible boundary". Configured through Claude Code settings; documented at code.claude.com.

## Defence checklist
| Threat | Where it enters | Control that blocks it | What gets logged |
|---|---|---|---|
| Prompt injection | Hidden instructions in fetched pages, documents or tool results | Treat fetched content as data, plus a hook refusing actions triggered by untrusted input | The fetched source, the attempted action, and the block |
| Jailbreak | A user prompt crafted to bypass safety constraints | Input validation plus a constraint on what the model may do | The flagged prompt and the refusal |
| Over-broad access | An identity scoped wider than the task needs | Least-privilege identity, secrets in a manager, locked auth configuration | Every privileged action with the identity that performed it |
| Sandbox escape | A steered agent reaching for filesystem or network access outside its boundary, including paths no hook or rule explicitly covers | OS-level sandboxing: filesystem isolation to the working directory, network isolation to permitted endpoints; the control that holds when a hook or rule is missing | Every attempted access outside the boundary, with the triggering tool call and the denied path or endpoint |

- **Handles well:** treats untrusted input as hostile by default and enforces the boundary with hooks and least privilege.
- **Adds cost or complexity:** least-privilege scoping, secret management and audit logging are setup work before a deployment is review-ready.
- **Use something else:** no prompt instruction is a security control; if it must hold, enforce it with a hook, not a prompt.
