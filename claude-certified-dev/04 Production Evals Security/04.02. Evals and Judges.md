# 04.02 Evals & Judges: Teaching (about 20 min)

Source: Developer Module 4, screen 2 of 23. Title: "Defining done before you ship: evals and a calibrated judge".

## Why evals
"I tried it a few times and it looked right" isn't a signal you can track. Production hardening starts by turning that intuition into a number you can follow as the prompt, tools or model change. That number comes from an **eval**.

## The design document: write it before the code
A short markdown page stating what's done, safe and affordable. It exists so you define correctness up front instead of rationalising whatever the model later produces, and every production layer in this module draws on it. Four decisions, each concrete enough that someone could check the built system against it:
1. **Success criteria:** what the feature must produce, in gradable terms. "Summarise the thread" can't be checked; "a two-sentence summary listing every action item and its owner" can. These become the eval's cases.
2. **Failure handling:** the failures the system must survive and what happens for each: list the errors production will throw, mark each retriable or terminal, and say what the user gets when recovery isn't possible. Decided on paper, it stops the first real rate-limit response from becoming an outage.
3. **Cost and latency budget:** the ceiling and the reliability floor: per-request budget, monthly cost ceiling, latency target, minimum reliability. Set before architecture. These become what you instrument and the floor you won't optimise below.
4. **Trust boundary:** which inputs are untrusted (content the agent reads that someone else can write) and the smallest set of actions and access the feature needs. Naming it turns least privilege into a decision you can enforce, with untrusted input treated as data and risky actions gated by a hook.
With an agentic coding tool, this document is also what you hand over before it writes anything: plan first, capture a written artifact, then implement against it. Clear criteria and constraints mean fewer assumptions and code you can check. The cumulative task at the end hardens a system against all four at once.

## What an eval is
Like a thermometer: it doesn't heal the patient, it gives a number you can trust. Collect input cases, write the expected behaviour for each, run the feature on every case, grade each output. That collection of cases, expectations and grades is the eval. "Done" stops being a feeling and becomes a score on a fixed set. Write the eval **before** the feature so you can't rationalise the output afterwards.
- The pipeline is small: load a dataset, run each case through the feature, grade each result, average. In code, three functions: run one case and grade it, grade it, loop over the dataset and average.
- A first score of two or three out of ten is normal. What matters is whether it rises as you change the prompt, tools or model. Change one thing at a time so you know what caused the gain.

## Matching the grader to the output
Choosing the wrong grader is where eval effort is wasted.
| Task type | Method | Catches | Unreliable where |
|---|---|---|---|
| One correct label or value | **Exact / string match** | A wrong answer when there is exactly one right answer; near-zero cost | Fails every valid paraphrase or reordering; wrong for open-ended output |
| Structured or code output | **Code-graded check** | Invalid JSON, unparseable code, out-of-range numbers, missing required fields | Says nothing about whether the content is *good*, only that it's well-formed |
| Open-ended quality | **LLM-as-judge** | Faithfulness, instruction-following, completeness, tone: things no code rule expresses | Noisy and costly, and gives a confident-looking number that means nothing until calibrated |
- A code grader is often just a parse attempt: score high if it parses (JSON, Python's `ast`), zero if it throws. Cheap, and catches a whole class of format failures.
- Worked comparison: a feature returns three capital cities as a JSON array. If the order differs from your reference string, exact match scores zero though the answer is right; a code check that parses and tests membership scores it well. For a one-paragraph rationale, the code check can only confirm it's non-empty (nearly worthless) and exact match is hopeless; only a judge can say if it's faithful and complete.
- Cost dimension: exact match and code checks are free per case and can run on every change. A judge is a second model call per case, so a thousand-case judged eval means a thousand extra API calls per run: fine as a periodic full pass, wasteful in a tight loop. Common split: code graders on every commit, the judge on a slower scheduled quality pass.

## Building and calibrating the judge
- A judge is a second model call guided by a clear rubric. Have it return **strengths, weaknesses and reasoning alongside the score**, not the score alone; otherwise models drift to a safe middle number (around six) whatever the quality. Asking for reasoning first anchors the score to specifics. The example prompt asks for JSON with `strengths` (1 to 3 points), `weaknesses` (1 to 3), `reasoning` (one or two sentences, 50 words max) and `score` (1 to 10).
- **Calibrate:** take cases a human has already labelled, run the judge on them, and measure how often it agrees with the human. A judge disagreeing half the time yields a number that looks rigorous and is worthless. Measuring agreement first turns the judge from a guess into defensible evidence. If agreement is low, fix the rubric: tighten what each score means, add a good and a bad example, re-measure.

## Coverage over perfection
A larger set with slightly noisier automated grading usually reveals more than a few hand-graded cases. The point is enough coverage to catch a regression, not a perfect rubric: twenty cases including irregular and edge inputs catch breaks three careful cases never touch. You can have Claude generate more cases from a small labelled seed, then spot-check them so the set stays honest.

## The improvement loop
Set a goal, write an initial prompt, run the eval, read where it failed, apply **one** change, re-run; repeat until the score holds where you need it.
- Change one component at a time. Rewrite the prompt, add examples and swap the model in one pass and you learn nothing about what moved the score.
- Read the **per-case** results, not just the average: a steady average can hide a change that fixed three cases and broke three others.
- A failing case points to a category, which makes the next change targeted: formatting failure means the output instructions; a factual failure on retrieved content means retrieval; a failure only on long input means context handling.

- **Handles well:** turns "looks right" into a tracked, defensible score and lets you move one deliberate change at a time.
- **Adds cost or complexity:** authoring cases and calibrating a judge is real up-front work before any feature ships.
- **Use something else:** for a single fixed-format output a code check alone is enough; skip the judge.
