Source: Developer Module 4, screen 15 of 23. Title: "Match each task to its agent type and cost lever". A matching exercise, not submitted; the answers below are the ones 04.11 to 04.14 support.

## The snippets (each labelled with agent type and primary lever)
- **A:** orchestrator-worker (large lead, small workers, five of them). Lever: parallel split.
- **B:** single agent on a small model with the Message Batches API and prompt caching on. Lever: Batches (roughly a 50% cost reduction, per the snippet's label) plus caching.
- **C:** single agent on a small model using fetch-once retrieval. Lever: model choice.
- **D:** single agent on a small model with streaming on. Lever: streaming.

## Matches
| Scenario | Snippet | Why |
|---|---|---|
| A single-fact lookup against a stable reference corpus | **C** | Fetch-once retrieval on a small model: one pass is enough, and iterative search or extra agents would only add cost (04.05, 04.13). |
| A broad research question that splits into independent parts explored at once | **A** | Genuinely parallel work is the case that justifies the orchestrator-worker token multiplier (04.13, 04.14). |
| A user-facing request where the reply should feel instant | **D** | Streaming makes a single response feel fast for a user in the loop; batching would be wrong because the user is waiting. |
| A cost-sensitive, non-urgent batch job | **B** | No one is waiting, so trade latency for cost with the Batches API; caching compounds the saving when the job repeats a long fixed prefix (04.13). |
