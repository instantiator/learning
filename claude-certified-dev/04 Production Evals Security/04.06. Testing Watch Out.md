# 04.06 Testing & Tracing: Watch Out (about 8 min)

Source: Developer Module 4, screen 6 of 23. Title: "The pieces passed and the seam broke".

## The trap
You tested the prompt and the parser in isolation, both passed, so you trusted the whole flow.

## The trace (described)
- A trace from an eval run shows the parser unit test passing (the parser returns date objects) and the model-call functional test passing (the call returns the expected fields). The end-to-end test **fails**.
- Reading the end-to-end trace: step 1 retrieve returns three chunks as a list of dictionaries; step 2 build prompt inserts that context "as a raw list"; step 3 the model call succeeds but its answer ignores the context; step 4 the assertion fails because the model answered from memory.
- Cause: retrieval returns a list of dicts (each with a `content` field) while the prompt builder was written to expect a **plain string**, so the model received malformed context and fell back on what it already knew instead of the retrieved policy.

## Diagnosis
Each side was correct in isolation. The handoff between them was never exercised because no test covered that seam. A unit test can't see it (the unit works). A functional test can't see it (the call works on well-formed input). Only a test driving retrieval into the model call with real retrieved data raises the mismatch before a user does. This is exactly the failure the integration level exists to catch (04.05).

## Why it broke
The **format contract** between the retrieval step and the prompt builder was never defined: one returned a list of dictionaries, the other expected a string, and nothing enforced the boundary.

## How to prevent it
Add an **integration test** that runs the two components together on real retrieved data. And define the contract at the seam (an explicit type or schema for what retrieval hands to the prompt builder) so a mismatch fails loudly rather than silently degrading the answer.
