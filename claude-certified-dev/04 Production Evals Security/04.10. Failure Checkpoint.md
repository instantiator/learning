# 04.10 Failure Handling: Checkpoint (about 8 min)

Source: Developer Module 4, screen 10 of 23. Title: "Repair the broken error and retry path". A write-your-answer exercise, not attempted, so the course's model answer was not revealed.

## The task
A short retry helper has one defect. Name it and write the corrected `call_with_retry()`.

## The broken code (described)
`call_with_retry(make_call, max_attempts=5)` loops up to `max_attempts` times. In each iteration it tries `make_call()` and returns the result; on **any** exception it sleeps for **0 seconds** and loops again. If every attempt fails it raises `RetryBudgetExhausted`.

## My read of the defect (not the course's model answer)
It retries every exception instantly. That is the tight-loop pattern from 04.09, and it breaks the rules from 04.08:
- no classification of retriable versus terminal, so a 400 or 401 is retried five times for nothing;
- `sleep(0)` means no backoff, so retries hammer the service and deepen a rate limit;
- no use of `retry-after`, and no jitter.

## A corrected version, in outline
- Catch API errors specifically and classify by status: retry only 429, 529 and 5xx (04.08's `RETRIABLE` set); re-raise terminal errors (400, 401, 403, 404) immediately.
- Compute the wait from the response's `retry-after` header when present; otherwise **exponential backoff with jitter** (e.g. base delay doubling each attempt, plus a random component, capped at a maximum).
- Keep the attempt cap, and after the last attempt raise a clean error (or route to a fallback) rather than looping forever.
- Remember that the SDK already retries transient failures: set this helper's attempts and the SDK's retries so they don't multiply (04.08).
