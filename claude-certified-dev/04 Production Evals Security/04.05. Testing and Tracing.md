# 04.05 Testing & Tracing: Teaching (about 14 min)

Source: Developer Module 4, screen 5 of 23. Title: "Testing and tracing".

## Why a second layer
An eval gives you a number for what good looks like. It doesn't say *where* a failure happened, and a passing eval can still hide a break somewhere in the workflow. Underneath the graded target you need tests that isolate each failure type and traces that show which step produced the bad result.

## Four test levels, each catching what the others miss
A test is only useful if you know which failure it identifies. Most silent production breaks live at one level.
| Level | What it isolates | What it can't catch |
|---|---|---|
| **Unit** | One function (a parser, a tool wrapper) on its own: it behaves, but says nothing about fit | How components fit together |
| **Functional** | One Claude call returning the expected shape for an input: right fields, right type, parseable | Failures in the system around that single call |
| **Integration** | The handoff between two components, e.g. a retrieval result passed into a model call. Where most silent failures hide: each side passes its own tests while the seam between them is broken | Whole-flow behaviour that only emerges end to end |
| **End-to-end** | The full flow as a user runs it, input to output. Catches breaks that only appear when everything runs together, but is the slowest and hardest to localise | Where exactly the break is, since it sees only the final result |

## Tracing: find where it failed
Tests tell you a failure exists; a **trace** tells you which step caused it. A trace records each step of a run (prompt, tool calls, intermediate outputs, timing) like a timeline. Without one, a failed eval says something is wrong but not where: the difference between a five-minute fix and a day tracing the workflow by hand.
- Example trace for the case "Where is my refund?": step 1 retrieve (ok, 42 ms, 3 chunks); step 2 build prompt (ok, 1 ms, 1,240 tokens); step 3 model call (ok, 980 ms, an answer); step 4 parse **FAIL** in 2 ms with `KeyError: amount`; final score 0, failure localised to step 4, the parser.
- It turns "the case failed" into "the parser raised a KeyError on a field the model didn't return". It also makes a change reviewable: you can show the step that moved, not just the score that dropped.

## Routing between retrieval approaches
Don't pick one strategy for everything. A cheap classification call can send single-fact lookups to **fetch-once** retrieval and multi-part questions to **search-across-rounds**, spending on iteration only when a query needs it. Defaulting everything to iterative search inflates cost and latency on questions one fetch would answer; defaulting everything to a static index gives shallow answers where several passes were needed. The router is one small model call: classify the query as "lookup" or "multi_step", then call `fetch_once` or `agentic_search`. It earns its cost when traffic is mixed; if every query has the same shape, skip the router and hard-code the fitting path. (Retrieval choice, from 02.13: fetch once for single-fact lookups in a stable corpus; multi-step questions and changing corpora need search across rounds.)

- **Handles well:** localises a failure to a step and matches each test to the break it can see.
- **Adds cost or complexity:** tracing and four test levels are infrastructure you build and maintain.
- **Use something else:** for a single-fact lookup in a stable corpus, fetch-once retrieval beats iterative search.
