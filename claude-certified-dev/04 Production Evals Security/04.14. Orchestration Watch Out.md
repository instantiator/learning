# 04.14 Cost & Orchestration: Watch Out (about 6 min)

Source: Developer Module 4, screen 14 of 23. Title: "The parallel fan-out that tripled the bill".

## The trap
A task ran slowly, so it was split across several parallel subagents on the reasoning that simultaneous work finishes sooner. Latency dropped a little. Then the bill came in several times higher than the single-agent version while answer quality barely moved.

## The exchange (illustrative)
- A developer: the orchestrator-worker setup works, but the bill tripled and the answers are barely better than the single-agent version. What are they paying for?
- A senior developer's answer: every subagent consumes its own tokens against its own context window. Anthropic has reported that its own multi-agent research system uses roughly **fifteen times the tokens** of a normal chat for exactly that reason. That multiplier is worthwhile when the task decomposes into independent parts that can be explored in parallel, like research across separate sources. This task doesn't split that way: each step depends on the last, so the subagents mostly wait on each other, and you pay the fan-out cost without the parallel benefit. Switch to a single agent with good context and the cost drops to what the work needs.
- Result: moved back to a single agent with the same context; the bill fell and quality held. The lesson isn't that orchestration is bad: the token multiplier only buys something when the work can genuinely run in parallel.

## Why it broke
Parallel fan-out on a task that didn't decompose into independent parts, so every subagent multiplied token cost without adding parallel value. Use orchestrator-worker only when the task needs parallel exploration (04.13).
