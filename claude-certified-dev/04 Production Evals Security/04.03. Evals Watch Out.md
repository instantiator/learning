# 04.03 Evals & Judges: Watch Out (about 7 min)

Source: Developer Module 4, screen 3 of 23. Title: "The demo that passed and the edge case that did not".

## The trap
You watched the agent answer correctly a dozen times and concluded it was done. But all twelve inputs looked like the ones you had in mind when you built it.

## Postmortem (composite)
- A team shipped a feature extracting structured fields from customer messages. Before launch they ran about a dozen example messages, read the outputs, agreed they looked right, and deployed. The feature had input validation: it confirmed each message was non-empty text, that a date field came back populated, and that the date wasn't malformed or impossible. It seemed fine for two weeks.
- Then a customer wrote a message with two dates in one sentence ("I placed my order on March 3 but did not receive it until April 12"). The feature returned the later date as the order date. Every validation check passed: both dates were well formed and the field was populated. Validation confirms a value is the right *shape*, not the right *value*. Downstream logic acted on the wrong date and a batch of records was updated incorrectly.
- The review found no bug in the model or prompt. The feature had never been measured against a two-date message, because nobody had defined expected behaviour for that case as a graded example. All dozen manual checks were single-date messages, the input the builder pictured. With no holdout set there was no signal that the two-date input existed in the population.
- Root cause: the missing graded set. A prompt change (most likely stating which date to extract) fixed the output; the eval didn't fix the extraction but **detected the failure, recorded the expected behaviour as a checkable case, and guards against that regression on every future change**. The two-date message became case one.

## Finding such inputs before a customer does
Ask the model to enumerate edge cases that could break the current implementation: two dates in one sentence, no date at all, a relative date like "next Tuesday". Turn the plausible ones into graded cases with a human-checked expected output: the same case-generation move from 04.02, applied before launch instead of after.

## Why it broke
Success was judged by impression, not by a graded set. The eval surfaces failures and guards against regression; the prompt is what changes the output. Write expected behaviour down as graded cases before shipping, and use the model to help find the edge inputs you didn't think to test.
