# 04.09 Failure Handling: Watch Out (about 6 min)

Source: Developer Module 4, screen 9 of 23. Title: "The call that never failed in development".

## The trap
In development you called the endpoint a few dozen times and it returned cleanly every time, so there was no reason to write an error path. Development traffic is low volume, on a stable connection, and rarely meets the conditions that make a call fail (rate limits, timeouts, transient network drops, a malformed response under load). None show up when testing by hand, so the code that handles them never gets written. The first failure happens in production, as an unhandled exception rather than a recoverable error.

## The incident (composite)
- A developer built a customer-facing feature that called the API in a loop over a batch: create a message, append the response content, assuming every call returns 200. Every development run succeeded because development traffic never approached a rate limit. There was no error handling because nothing had ever failed there.
- It shipped. At the first traffic peak the API returned a rate-limit response, the unhandled error was raised, and the **whole request failed** instead of waiting a moment and trying again. To users the feature looked broken.
- The developer's first instinct was immediate retries in a tight loop. That made it worse: each instant retry counted as another request against the same limit, deepening it.
- The real fix is the distinction from 04.08. The rate-limit response was **retriable**, so it needed **exponential backoff with a capped number of attempts**, honouring `retry-after` when the response included it. Development never produced the failure, so the path that would handle one was never written.

## Why it broke
A retriable failure met code with no error path, then met a hammering retry that deepened the limit. Classify the error as retriable, then back off with a cap, before traffic finds the gap for you.
