# 04.08 Failure Handling: Teaching (about 12 min)

Source: Developer Module 4, screen 8 of 23. Title: "Surviving production failure: tool errors".

## Framing
Tests now tell you a failure exists and traces tell you where. The next question: what does the system do at the moment a failure hits live traffic? Resilient versus fragile comes down to whether you decided in advance how each kind of failure is handled.

## Every failure starts with one question: retriable or terminal?
Would waiting and sending the exact same request again plausibly work? If yes: **retriable**. If no: **terminal**. A rate limit clears with time; a malformed request fails identically until the request itself is fixed.
- On the Anthropic API the status code tells you the bucket:
  - **Retriable:** 429 (rate limit), 529 (service overloaded), and 5xx server faults (500, 502, 503, 504), which are Anthropic-side and typically clear on retry.
  - **Terminal:** 400 (bad request), 401 (authentication), 403 (permissions), 404 (not found).
- Code sketch: a `RETRIABLE` set `{429, 529, 500, 502, 503, 504}` and a `TERMINAL` set `{400, 401, 403, 404}`; `is_retriable(status)` returns whether the status is in the retriable set, and everything else fails fast.
- Why it matters: retriable causes are transient (momentary overload, dropped connection, briefly exceeding a per-minute limit), so time resolves them. Terminal causes live in the request (malformed body, expired key, nonexistent model name), so time changes nothing. Retrying a terminal error burns retry budget, adds latency a genuinely retriable failure elsewhere might have needed, and hides the real problem behind a wall of identical failures. Correct classification saves the budget for failures that need it.
- Edge cases: a timeout is usually retriable (the work may simply have been slow), but repeated timeouts on expensive requests mean fix the request, not retry it. A 500 is retriable. A 403 is terminal. **When unsure, treat it as terminal and raise it:** a wrongly-terminal failure fails loudly and gets fixed; a wrongly-retriable one hammers a service and hides the problem.

## The SDK already retries; know what it covers
- The Anthropic client libraries automatically retry transient failures with progressive delays, up to a configurable number of attempts. Don't wrap your own retries around the same call: two loops multiply attempts against a rate limit instead of capping them. Decide where the retry lives: let the SDK handle transient cases and keep your code for application-specific fallbacks, or turn SDK retries down and own the whole path. Never run both without either knowing about the other.
- Responses carry rate-limit headers showing how much of your limit remains and when it resets. Most useful is **`retry-after`**, included on 429 and 529 responses: honouring it is more precise than guessing with backoff, because the service is telling you when capacity returns. Pattern: read `retry-after` first, fall back to exponential backoff only when the header is absent. Header names and limits are version-pinned, so confirm them in the reference at build time.

## Tool errors must go back to Claude explicitly
When a tool your code runs fails, return the `tool_result` with **`is_error: true`** and a message ("Tool failed: ..."), not a silent empty result. With the error visible, the model can react: try another approach, ask for clarification, or stop. A dropped error yields a confident wrong answer downstream, because the model treats the empty result as valid data and reasons on top of it. A visible failure is far easier to catch than a confident answer built on missing data.
- Refusals need their own check: a refusal comes back as HTTP 200 with `stop_reason: "refusal"`, so the retriable classifier won't catch it. Check `stop_reason` and raise (for example, "Model refused the request. Review input before retrying.").

## Decision table
| Error | Retriable or fail fast | Backoff | Fallback |
|---|---|---|---|
| Rate limit (429) | Retriable | Exponential backoff with jitter, honour `retry-after`, capped attempts | After the cap, raise a clean error or route to a cached or simpler result |
| Overloaded (529) | Retriable | Backoff; it reflects Anthropic-side load, so it isn't a rate-limit signal | Fail over to a fallback path, or a graceful error if it persists |
| Bad request (400) | Fail fast | None: the identical request fails again | Fix or reject the input and surface the error to the caller |
| Tool result error | Depends on the tool | Retry only if the underlying cause is transient | Return the error flag to Claude; never silence it |
| Refusal (200, `stop_reason: "refusal"`) | Fail fast | None: a content decision, not a transient error | Raise it to the caller and log it; don't silently retry or treat it as valid output |

- **Handles well:** stops one bad response cascading into an outage by handling each failure type by name.
- **Adds cost or complexity:** every failure path is code to write, test and maintain beyond the happy path.
- **Use something else:** don't retry a terminal error; retrying a 400 just wastes the retry budget.
