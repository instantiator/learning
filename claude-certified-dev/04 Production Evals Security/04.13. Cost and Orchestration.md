## Framing
A system that recovers from failure must also be affordable and fast. Earlier screens made it reliable; this one instruments and budgets it, then tackles the pattern that multiplies cost fastest: spreading work across several coordinating agents.

## Instrument every call
In development you never see the bill; in production cost and latency become the constraint. For each call record three metrics: **token usage (input and output), latency, and error rate**. Then you can see which step is expensive or slow instead of guessing from a monthly total. Do it from the start, or the bill arrives before the explanation. In code it's a thin wrapper: time the call, read the usage the API already returns (`input_tokens`, `output_tokens`), and log the step name, tokens and latency.
- Per-call data changes the questions you can ask: not "why is the bill high?" but "which step, on which request type?". A flow that looks uniformly expensive often has one step at about 90% of spend, and that's where optimisation effort belongs. The slow step is rarely the one you expected; the trace plus per-call timing tells you.

## The levers
A cost or latency problem almost always traces to one measurable component; identify the lever before tuning it.
- **Model selection:** use a smaller, faster model to cut the cost and latency of a bigger one; keep the most capable model for steps that need it and route simpler work elsewhere (04.11).
- **Streaming with tool use** (code pattern): accumulate deltas by block index until the stream closes, then rebuild tool calls from the completed blocks: on `content_block_start` register the block (type, id, name, empty `input_json`); on `input_json_delta` append partial JSON; on `text_delta` collect text; at `message_stop` break; afterwards parse each `tool_use` block's accumulated JSON. A `tool_use` block isn't safe to act on until the stream closes; acting on a partial one yields malformed inputs. A stream that breaks mid-response is a transient failure: retry the whole request, don't pass partial output downstream (02.10 to 02.12, 04.08).

## Prompt caching
- Normally the processing work for your input is discarded after the response, and repeated content is reprocessed from scratch next time. Caching stores that work so later requests read it back.
- **Economics:** cache writes cost more than base input (1.25x for the 5-minute lifetime, 2x for the 1-hour); reads cost a fraction (0.1x). It only pays when reads outnumber writes, so it suits stable, frequently reused prefixes.
- **Setup:** *automatic* mode (one cache flag at the top level; the system manages breakpoints as the conversation grows; the recommended starting point) or *explicit* breakpoints (a `cache_control` marker on a block caches everything up to and including it). Content after the last breakpoint is processed normally. Best candidates: a long system prompt and a large tool schema, which rarely change while the user message does.
- **Three properties decide whether it helps:**
  1. The cached content must be **identical**: matching is on an exact prefix, so any change before the breakpoint (even adding "please") invalidates the cache and forces a full reprocess.
  2. The same content must **recur soon**: the default lifetime is five minutes, refreshed on each hit; a one-hour lifetime costs extra. A prefix reused several times a minute pays off; one reused rarely doesn't.
  3. The prefix must clear a **minimum length**, which varies by model; shorter prompts see no benefit.
- **Trade-off:** the cache may hold stale content for as long as it lives. Fine for a fixed system prompt and stable tool schema (nothing goes stale); a consistency window to tolerate if the prefix reflects changing data.

## The Batches API
For work that can wait (an overnight classification run, a backfill, a scheduled report), the Message Batches API runs requests asynchronously at a lower per-request price: the deciding lever for non-urgent high-volume work (the discount is version-pinned; check the docs). The trade is latency for cost, with results within an asynchronous completion window. It's wrong for anything a user is waiting on and right for scheduled work. It mirrors streaming in reverse: streaming makes one response *feel* fast for a user in the loop; batching cuts the bill where no one is waiting. They never compete for the same request. **Batching and caching compound** when a non-urgent job reuses the same context across many requests: the batch discount lowers each request and caching lowers the repeated prefix inside each one.

## Multi-agent orchestration as a deliberate trade-off
- **Orchestrator-worker pattern:** a lead agent decomposes a task and delegates subtasks to subagents working in parallel, each in its own context window; the lead then synthesises. In code: plan, parallel fan-out, synthesise.
- It genuinely helps with large tasks that split into independent parts, e.g. research across many separate sources, since subagents explore simultaneously. Think of it as a hiring decision: five researchers finish a broad survey faster, but you pay five salaries; hire a team only when the work splits into parts that don't wait on each other.
- Anthropic's own research system uses it. On an internal research eval, a setup with a top-tier lead and smaller subagents substantially beat a single top-tier agent, at roughly **15 times the tokens of a normal chat interaction**, because every subagent spends its own tokens in its own context. Analysis found token usage explained most of the performance variance: the architecture works chiefly because it buys more parallel computation.
- It's less effective for tightly coupled work such as coding, where each step depends on the last. Use it only when the task truly needs parallel exploration; a single agent with good context handles most work at a fraction of the cost. The multiplier compounds if something misbehaves: a runaway subagent or oversized tool result can exceed the 15x baseline.
- **Rough cost estimate:** a single agent answers a research question in about 10,000 tokens; a lead plus four subagents (five contexts plus a synthesis pass) is about 15x, so on the order of 150,000 tokens. If the question was really a single lookup, you paid the multiplier for nothing. Whether the number is large depends on whether the task needed the extra agents.
- **Control dimension:** more agents mean more failure points. Each subagent needs the same retriable-versus-terminal handling, backoff and fallback discipline (04.08). A subagent that hits a rate limit with no backoff can stall the whole compilation while the lead waits for a return that never comes. Orchestration multiplies the failure-handling work, not replaces it.
- **Model mix:** use a more capable model as the lead and cheaper models for the subagents, so you aren't paying top-tier rates in every parallel context.

## Reliability has a floor you tune cost within
Cost is half the budget; reliability sets a baseline below which cost must not go. The cheapest configuration is rarely the most reliable. **Define the floor first** (a retry budget, a latency ceiling), then optimise cost above it, not below. Cutting beneath it swaps a visible expense for silent failures, and a slightly higher bill is easier to defend than a system that doesn't work.
- Example floor: a user-facing request must finish within four seconds and may retry a failed dependency up to three times. Every cost optimisation must satisfy that. A cheaper model is fine if it fits the latency ceiling and doesn't raise the error rate enough to burn the retry budget; cutting retries to two to save money on a slow dependency is not acceptable if it pushes failures past what the floor allows.
- Order matters because cost pressure is louder: a high bill shows on a dashboard daily, while reliability problems look like occasional noise until they become an incident. Optimise cost first and the louder pressure wins; set the floor first and reliability stays the fixed constraint. The **eval set from 04.02 makes the floor enforceable**: a pinned baseline score defines minimum acceptable reliability, so a cost-saving change that drops the score below baseline fails the gate before it ships.

## Reference table
| Metric | Where to instrument | Single agent vs orchestrator-worker |
|---|---|---|
| Token cost | Per call, aggregated per request and per flow | A single agent pays once per step; orchestrator-worker multiplies by the number of subagents (about 15x in Anthropic's reported case), on input and output tokens alike, since each subagent has its own context |
| Latency | Per call, with traces identifying the slowest step | Parallel subagents can cut wall-clock time on independent work but add coordination latency to plan and compile |
| Error rate | Per call and per dependency | More agents mean more failure points; each subagent needs the same retry and fallback handling |

- **Handles well:** makes spend and latency visible per call so a cost problem traces to a named lever.
- **Adds cost or complexity:** parallel subagents multiply token cost (about 15x in the reported case) before improving any answer.
- **Use something else:** for tightly coupled work such as coding, a single agent with good context beats fan-out.
