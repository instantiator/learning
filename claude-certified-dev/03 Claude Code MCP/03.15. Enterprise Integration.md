## Why enterprise integration differs from a prototype
A prototype answers "does the connection work?" A production enterprise integration must also answer: who is the model acting as, and is that identity auditable? What data can it reach, and where does that data leave the organisation? Can an administrator lock the configuration so no developer can change the auth setup? Can access be logged to a compliance standard? These are the ordinary identity, access and compliance requirements for any external system touching regulated data; treating them as part of the design is what separates a demo from something deployment-ready.

## Authentication by service type
- **Remote service with user identity (SaaS, cloud):** use **OAuth**. The MCP server returns `401 Unauthorized` to signal authentication is needed; the client starts a browser sign-in; after the user approves, a token is issued and stored. No one copies a secret by hand. Linear (03.12) works this way; GitHub, by contrast, uses a personal access token in a header.
- **Remote service with service identity (internal API):** an API key held in an **environment variable**, never in committed config (from the checklist table).
- **Local (file system, local database):** no credential; file-system permissions, with deny rules enforcing path access (from the checklist table).

## Managing the secret after authentication
Choosing the auth pattern establishes the connection; keeping the secret safe is separate. The leaked key in 03.13 wasn't a bad auth choice: the credential lived in the wrong place and couldn't be cleaned up once it spread. Three practices:
1. **Separation:** a credential never travels with the configuration that references it. The config holds a variable reference; the value lives elsewhere. Config files get committed, shared and cloned, and an inline value rides along with every copy and enters history in a way overwriting doesn't remove.
2. **Where the value goes:** for a secret local to one machine or pipeline run, an environment variable injected at execution is enough (the CI runner sets it as a secret, the config reads it by name, nothing is written to disk). For a value several services or people need, use a **secret store**: a managed service that holds credentials, returns them to authorised callers at runtime, and records who read what. It centralises the value so one rotation updates every consumer and removes the scattered copies. Environment variable when local and short-lived; secret store when shared or auditable.
3. **Rotation:** replace a credential on a schedule and immediately after suspected exposure. It's the only proper response to a leak, since an exposed key can't be made secret again. A value baked into committed code can't be rotated cleanly (the old one stays in history and every consumer hard-coded to it breaks). A credential read by name from a secret store or env var rotates without touching the code.
Two habits make rotation cheaper: scope each credential to the narrowest access its task needs (so a leak reaches only that integration's reach), and keep a record of which services use each credential so a rotation doesn't surprise its consumers. Separation keeps the value out of the file, a secret store or env var gives it a home, and rotation helps recovery only when the first two hold.

## What regulated industries add
A financial-services or healthcare customer asks where data is processed, how access is logged, and whether an administrator can lock the configuration (for example during an audit window).
- **Locking:** the enterprise managed configuration (03.02, 03.12), deployed by an administrator and not overridable by users, keeps the auth setup consistent across the organisation instead of depending on each developer's settings file.
- **Logging:** a `PostToolUse` hook that records every tool call and its parameters to an audit store. It fires deterministically for every call whatever the model decides, so the log can't be skipped (03.05).
- **Data residency:** an HTTP endpoint in a specific region plus a platform deployment that pins processing to that region gives a compliance reviewer a checkable answer to "where does the data go?" The infrastructure and platform choices matter at audit time, not just build time.

## Code modernisation as a test case for the whole module
Modernising legacy code concentrates the risks the module's tools address: high blast radius, unpredictable dependencies, limited reversibility.
- The explore, plan, code loop is the core workflow. **Plan mode** holds the agent in the read-only explore phase while you build confidence: review proposed edits, spot anything touching unexpected paths, push back before any file changes.
- **Hooks** enforce guardrails that block edits to specific paths during the most sensitive phases.
- **`CLAUDE.md`** carries the conventions for the new target patterns so the agent applies them consistently instead of drifting back to legacy patterns it reads nearby.
Three scoping questions before the session starts (true of any high-risk agentic task):
1. **Blast radius:** which systems depend on the code being changed, and what breaks downstream if an edit is wrong?
2. **Auditing:** is a `PostToolUse` hook logging every tool call, and does that log satisfy whoever must review what the agent touched?
3. **Approval:** who approves each phase before the next begins? Plan mode enforces the explore/execute boundary, but the approval decision is yours to define and document up front.

## Authentication and integration checklist
| Service type | Auth method | Where secrets live | What gets logged | Who can lock the config |
|---|---|---|---|---|
| Remote, user identity (SaaS, cloud) | OAuth | Token issued by the provider and stored by the client | `PostToolUse` hook to an audit log | Administrator via enterprise managed settings |
| Remote, service identity (internal API) | API key in an environment variable | Environment only; never in committed config | `PostToolUse` hook to an audit log | Administrator via enterprise managed settings |
| Local (file system, local DB) | File-system permissions | No credential; deny rules enforce path access | `PostToolUse` hook to an audit log | Deny rules in enterprise managed settings |

## Cost, complexity, risk
- **Cost:** OAuth adds a one-time setup step per user per service; API-key management needs a rotation process; audit hooks add small overhead per tool call.
- **Complexity:** regulated environments add requirements absent from a prototype; surfacing them during scoping keeps the integration on schedule.
- **Risk:** concentrates as a prototype nears production. Hard-coded credentials, no audit log and no central lock will fail a regulated customer's security review. The fixes aren't hard but need attention before the review.
- **Handles well:** any integration touching data a regulated customer cares about, using tooling that already supports managed settings and audit hooks; scoping security up front adds little and stops it stalling at final review.
- **Adds cost or complexity:** teams unfamiliar with OAuth or enterprise secrets management; these usually need coordination with security or IT, so allow for it in the timeline.
- **Use something else:** a proof of concept that will never see production data doesn't need the full checklist, though using an environment variable for secrets costs nothing and is good practice.
