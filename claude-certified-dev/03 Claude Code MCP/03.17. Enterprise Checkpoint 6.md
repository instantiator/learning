# 03.17 Enterprise Integration: Checkpoint 6 (about 3 min)

Source: Developer Module 3, screen 17 of 22. Title: "Checkpoint 6: diagnose the authentication failure from a trace". A multiple-choice exercise, not submitted; the answer below is the one 03.15 supports.

## The task
Read a connection trace, name the authentication failure mechanism, and pick the targeted fix.

## The trace (described)
- The MCP client connects to an internal data-API MCP endpoint and requests a token: `401 Unauthorized`.
- It reads a credential from a file in a CI runner's home directory (`/home/jenkins/.config/mcp-credentials.json`); the value is a warehouse token, shown redacted.
- It retries with that credential and gets `401 Unauthorized` again, and the connection fails after three attempts.

## Diagnosis (my reading)
The service is rejecting the stored API key: a credential kept in a file on the runner that is no longer valid (stale, expired or rotated at the other end), with nothing in the pipeline able to refresh it. The mechanism is a **file-stored service credential that has gone stale**, the pattern 03.15 warns against: the value lives in a file rather than being injected, so replacing it means editing files on the machine.

## Options and answer
- A. Rotate the key and update the credentials file with the new value. (Fixes today's failure but keeps the credential in a file, so it will recur and spreads copies.)
- **B. Rotate the rejected key, then move the credential out of the file, inject it as an environment variable in the CI pipeline runner configuration, and update the MCP configuration to reference the variable. (The fix.)** It addresses both the immediate rejection and the cause: separation, with the value injected at execution so future rotations need no file edits (03.15, 03.13).
- C. Switch to OAuth. (Not targeted: this is a service-identity internal API, where an API key in an environment variable is the expected pattern; OAuth suits user-identity services.)
