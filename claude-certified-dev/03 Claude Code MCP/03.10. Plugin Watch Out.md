# 03.10 Packaging Workflows: Watch Out (about 3 min)

Source: Developer Module 3, screen 10 of 22. Title: "The plugin that installed on your machine and failed on everyone else's".

## The trap
A clean install says the package was assembled correctly; it says nothing about whether the plugin will run. Install copies files into place. Execution resolves the paths and variables those files point at, against whichever machine runs them. If the author bakes their own machine's layout into a skill, the install succeeds everywhere and execution fails everywhere except the author's setup, and the author can't see the gap.

## What happened (composite)
- A developer built a deployment-workflow skill, packaged it as a plugin, tested locally (passed) and shipped it through the internal marketplace. Every teammate's install succeeded, and the moment anyone ran the skill it failed.
- **Failure 1, an absolute path:** `SKILL.md` ran a script at the author's own home directory (`/Users/<author>/projects/deploy-utils/validate.sh`). That directory existed only on the author's machine, so every teammate's run looked for a file that wasn't on their system or in the plugin. Plain text in the file; a reviewer could have caught it.
- **Failure 2, an undocumented environment variable:** a second skill relied on `DEPLOY_TOKEN`, set in the author's shell profile and never mentioned in the README. Nothing in the package announced the dependency, so the skill ran fine right up to the step that needed it. Three teammates spent two hours tracing it.
- Same root cause: the plugin treated the author's machine as the team's machine. The environment variable is the more dangerous kind because it is invisible.

## What to do
- Every path in a skill, hook command or plugin component must be relative to the project root or built from an environment variable for the base path. Use `$CLAUDE_PROJECT_DIR` for scripts stored in the project and `${CLAUDE_PLUGIN_ROOT}` for scripts bundled inside the plugin, so paths resolve whoever runs them and wherever the session started.
- Bundle every script, config file or asset the plugin depends on inside the plugin, or put it in a shared project location, so all teammates get the same files after install.
- Document every required environment variable and validate it at install time, so a missing one surfaces immediately rather than mid-run.
- Test the install on a clean machine before distributing; that catches what the build machine hides.
