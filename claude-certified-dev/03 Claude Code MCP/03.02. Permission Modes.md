# 03.02 Permission Modes & Human Gates: Teaching (about 17 min)

Source: Developer Module 3, screen 2 of 22. Title: "Claude Code agent loop, permission modes, settings, and where a human gate goes".

## The loop in Claude Code
Claude Code runs the same agent loop as Module 2, plus a permission system that gates every action the agent wants to take. It doesn't start writing straight away:
1. **Explore:** reads files, traces logic, builds a picture of the codebase.
2. **Plan:** produces a structured description of the edits it intends to make.
3. **Code:** only after you approve the plan does it write and execute changes.
This gives better output (fewer assumptions, more downstream effects caught) and is where the permission modes plug in. **Plan mode** holds Claude in explore, blocking all edits and shell commands until you release it: a good default for unfamiliar or high-stakes work.

## The six permission modes
Modes set how often Claude stops to ask; each trades speed for oversight. Choose by how well you know the codebase and how reversible the changes are.
| Mode | Auto-approves | Still gated | Notes / limits |
|---|---|---|---|
| `default` | Reads only | All file edits and shell commands | Safe but slow on trusted work; the baseline for any new or unfamiliar project |
| `acceptEdits` | Reads, file edits, and common filesystem commands (`mkdir`, `touch`, `rm`, `rmdir`, `mv`, `cp`, `sed`) **inside the working directory** | All other shell commands; writes outside the working directory; writes to protected paths | Trusted local work where shell execution still needs a human eye; unsuitable if the agent must run scripts |
| `plan` | Reads only; researches and proposes, no edits | All edits and shell commands until you approve a plan | Exploration and planning on sensitive or unfamiliar code; not for tasks that must write output |
| `auto` | Everything, but a separate classifier reviews each action first and blocks anything escalating beyond your request, targeting unrecognised infrastructure, or seemingly driven by hostile or inappropriate content | Blocked by default: production deploys and migrations, mass deletes, credential exfiltration, force-push to main | Reduces prompts but doesn't guarantee safety; a research preview, not a substitute for reviewing sensitive operations; availability depends on plan, model version and admin settings, so verify before building |
| `dontAsk` | Only tools you pre-approved in an allow rule, plus read-only commands | Everything else is **denied** outright; there's no confirmation queue | Built for locked-down CI and scripts; restrictive, not a way to cut friction on local interactive work |
| `bypassPermissions` | All tool calls, with no prompts and no safety checks | Nothing in normal operation; only catastrophic deletes like `rm -rf /` and `rm -rf ~` still raise a last-resort prompt | Only inside an isolated container or VM that is disposable; never on a developer workstation against a live codebase |

## Where configuration lives
| Level | File | Scope |
|---|---|---|
| User | `~/.claude/settings.json` | Every project on the machine; preferences that should follow you (e.g. a default mode for exploration) |
| Project | `.claude/settings.json`, committed | Everyone who clones the repo; team conventions, allow rules for tools the project uses, deny rules for paths to leave alone |
| Local project | `.claude/settings.local.json`, auto git-ignored | Your personal overrides for one project |
| Enterprise | `managed-settings.json`, set by administrators | Cannot be overridden by users or project files; organisation-wide controls such as denying edits to env files or blocking certain shell commands |
Allow and deny rules sit on top of the chosen mode. **A deny rule always beats an allow rule, whatever the mode.** The most durable control is an enterprise-level deny: no developer can remove it, and it applies even in a bypass mode.

## Placing the human gate by worst-case cost
Modes and deny rules decide what the agent may do without asking; they don't decide where a human must still look. The question is: what is the worst outcome if this runs unchecked? The cheaper and more reversible the mistake, the more you let through; the costlier and harder to undo, the more it needs a human gate before it executes. The same logic applies when an agent runs unattended (for example a bot commenting on or blocking a pull request). Three placements:
1. **Let low-stakes, reversible actions through** (a formatting fix, an edit inside the working directory): approving each one buys oversight you don't need. This is what `acceptEdits` is for.
2. **Gate anything hard to undo or touching a sensitive path:** a write outside the working directory, a destructive shell command, an edit to a security-relevant or protected file. The agent pauses and surfaces it for a person.
3. **Never let the agent be the only gate on code your team has marked sensitive.** Its work is an input to a human decision; a person reviews before merge however confident the agent or its own review sounds.
The mode is the session-wide default; the gate is where you override it for the one action too costly to leave to the default. Both come from asking what breaks if this runs unchecked.

## Cost, complexity, risk
- **Cost:** default mode on trusted work adds prompt latency to every tool call, accumulating on a long refactor.
- **Complexity:** several settings levels with an override hierarchy need consistent care; an enterprise deny that contradicts a project allow must be understood by everyone maintaining the config.
- **Risk:** using the wrong mode for the context. A bypass mode set out of impatience on a non-isolated machine removes every safety prompt between the agent and your live files and, unlike the other modes, also removes the protected-path guard.
