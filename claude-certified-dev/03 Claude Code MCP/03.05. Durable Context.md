# 03.05 Durable Project Context: Teaching (about 20 min)

Source: Developer Module 3, screen 5 of 22. Title: "Durable project context with CLAUDE.md, rules files, hooks, and subagents".

## Framing
03.02 covered what the agent is *allowed* to do (permissions). This section covers what it *knows* and how it behaves, so the rules you set in one session are still in force at the start of the next.

## CLAUDE.md: always-on project memory
- On start, Claude Code reads `CLAUDE.md` at the project root and prepends it to your prompt, so every convention, constraint and command in it is present from the first message of every session.
- `/init` scans the codebase and generates a starter `CLAUDE.md`. Treat it as a baseline to validate, then refine to the rules that actually steer outcomes: test commands, framework conventions, paths the agent must not touch, style choices that differ from defaults.
- **Size is the main failure mode.** A file that grows with every new instruction takes more of the window, makes each rule a smaller share of what loads, and lowers the odds the agent follows the one rule that catches a real mistake. Keep it to behaviour-changing constraints and move the rest into Skills that load on demand.

## Rules instruction files: scope guidance to where it applies
- They live in `.claude/rules/` and add a narrower layer on top of `CLAUDE.md`.
- Scoping comes from a `paths` glob in the YAML frontmatter, **not** from file placement. A path-scoped rule loads into context only when Claude works with files matching the glob.
- Subdirectories of `.claude/rules/` (e.g. `.claude/rules/database/`) are organisational only. A rules file with **no** `paths` field loads unconditionally at launch, with the same priority as `CLAUDE.md`, wherever it sits.
- Division of labour: universal constraints go in `CLAUDE.md` ("never modify the database schema"); narrow path-specific guidance goes in a scoped rules file (for example `.claude/rules/database.md` with `paths: ["src/db/**/*.sql"]` and the rule "all SQL here must include an explicit transaction boundary").

## Hooks: your scripts at fixed lifecycle points
A hook intercepts or reacts to tool calls. A line in `CLAUDE.md` saying "run Prettier after every edit" is followed most of the time; a hook does it **every time**, because it fires independently of what the model decides. Hooks are defined in settings files and configured with `/hooks`; each binds to a lifecycle event, an optional matcher scoping it to tool types, and a command.
| Event | When | Use |
|---|---|---|
| `PreToolUse` | Before a tool call executes. Can **block** it: exit code 2, with the reason on stderr as feedback the agent sees | Enforce access controls in the configuration layer instead of hoping the agent complies |
| `PostToolUse` | After a call completes; can't block it | Automatic side effects: run a formatter after an edit, run tests after a change, write an audit log |
| `UserPromptSubmit` | When you submit a prompt, before the model sees it | Inject context or validate the request before work starts |
| `Stop` | When the model finishes responding | End-of-turn follow-ups: notifications, cleanup, committing the audit log |
| `Notification` | When Claude Code sends a notification (it needs permission, or has been idle 60 seconds) | Route those signals to an external channel or log |
| `SessionStart` | When a session starts or resumes | Initialise state, validate env vars, check required services |
| `SessionEnd` | When a session ends | Teardown, final audit writes, close-out notices |
A `PreToolUse` hook blocking edits to a production config path enforces the constraint at every tool call in every session, regardless of permission mode. That is the difference between a guardrail and a convention.

## Subagents: delegating to an isolated context
A subagent is a specialised assistant Claude Code delegates a task to. It runs in its own context, doesn't inherit your conversation history, accumulated files or session state, starts clean, and returns only its output.
- Built-ins differ in what they load. **Explore** and **Plan** skip `CLAUDE.md` and git status to stay fast and cheap, so project rules from `CLAUDE.md` are *not* in their context. The **general-purpose** subagent loads both. (The built-in set grows; check the docs, but this split holds across versions.) If your constraints must be respected, use the general-purpose subagent or a custom one that explicitly loads the rules it needs.
- Custom subagents don't automatically see skills either. For a custom subagent in `.claude/agents`, list any skill it needs in its frontmatter. Built-ins have no preloaded skills; for skill-backed behaviour make a custom subagent with the skills listed.

## The four mechanisms side by side
| Mechanism | Loads | Runs | Context cost | Belongs here |
|---|---|---|---|---|
| **CLAUDE.md** | Full file prepended at session start | Every session, unconditionally | Persistent per session; dilutes with size | Universal constraints, commands, framework decisions |
| **Rules file** | File contents, scoped by `paths` glob (unscoped loads like CLAUDE.md) | When Claude reads a file matching the glob; unscoped at session start | Path-scoped: only when triggered; unscoped: same as CLAUDE.md | Path-specific guidance that would be noise elsewhere |
| **Hook** | Runs your script; adds nothing to context | At the configured event | Minimal: only script output routed back to Claude | Enforced guardrails, automated side effects, audit logging |
| **Subagent** | Task context only; isolated from the main session | When the main session dispatches it | Returns a summary, not the whole task history | Exploration, investigation, output that would bloat the main context; parallelisable work |

- **Handles well:** projects you return to over many sessions, where stable rules, per-directory variation or unconditional guardrails repay the setup.
- **Use something else:** one-off tasks you won't revisit; for a quick look at an unfamiliar codebase the setup isn't worth it.
