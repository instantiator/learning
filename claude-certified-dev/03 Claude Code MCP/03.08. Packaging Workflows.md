## Framing
03.05 covered durable context and enforcement (`CLAUDE.md`, rules, hooks, subagents), which live in `.claude/` and are version-controlled. The question now: how do you package that setup so a teammate can install it in one step instead of repeating your manual configuration?

## Skills: reusable workflows loaded on demand
A skill is a portable Markdown file (`SKILL.md`) in `.claude/skills`: frontmatter that identifies it and says when it applies, then the steps. The same skill can run in Claude Code, be invoked through the Messages API, or be loaded by the Agent SDK. The file doesn't change; **where it runs, how it loads and what it may touch** do.
- **Claude Code** (the one tab captured): discovered from `.claude/skills` on the filesystem; loads on a description match or when you invoke it by name. Steps run in your terminal session against your local files, under the active permission mode and deny rules. It's filesystem-based and governed by the settings layer.
- The Messages API runs skills in a code-execution container, not your environment (see 02.19); the Agent SDK loads them depending on `settingSources`; Managed Agents is Anthropic-hosted. (Not captured from this screen.)

### Three portability rules
1. **Write the description as the matching criterion.** The model loads a skill by comparing your request to its description. A description that says when the skill applies works in every runtime; a vague one fails to load in all of them.
2. **Don't assume a local filesystem or local tools inside the skill body.** A skill that shells out to a local command works in Claude Code but breaks on the Messages API, where it runs in a container without that command. Keep steps within what the runtime is guaranteed to provide.
3. **Subagents don't inherit skills** (as in Module 2): list the skill explicitly for the subagent, in every runtime that supports subagents.
Author once, reuse everywhere, but design for it: a skill with a clear description and no local-environment assumptions ports cleanly; one that assumes a specific local setup does not.
- **Handles well:** a task-specific procedure written once and reused across the interactive terminal, an API integration and a headless SDK job.
- **Adds complexity:** each runtime loads and sandboxes it differently: account for beta headers on the API and `settingSources` on the SDK.
- **Use something else:** instructions that must apply to every session in a project belong in `CLAUDE.md`; skills are for on-demand, portable procedures.

## Giving a workflow an explicit entry point
- A custom command is a shortcut for a defined procedure. In current Claude Code, **skills are the recommended format** for both explicit and automatic invocation: invoke one directly with `/skill-name`, or let Claude load it when relevant. The older `.claude/commands/` directory still works but is legacy.
- For a workflow that should run **only** when you call it, use a skill with `disable-model-invocation: true` in the frontmatter.
- Plugin commands are **namespaced automatically**: the plugin name is the prefix, so `run-tests` in a plugin called `payments` is `/payments:run-tests`. Two plugins can both ship `run-tests` without colliding. Treat the plugin name as part of the interface: renaming the plugin renames every command.

## Plugins: the packaging layer
A plugin bundles skills, hooks, subagents and MCP servers into one installable unit, distributed through a marketplace (a catalogue of plugins). The official Anthropic marketplace is available automatically in Claude Code; add third-party marketplaces hosted in a GitHub repository with `/plugin marketplace add <owner/repo>`. Teammates then run one install command to get the same setup: a versioned, auditable install replacing a page of manual steps. Skills go in a skills directory; hooks, subagents and settings go in their own locations; a manifest describes the bundle and the install command wires it in. Plugins can be installed by individuals or enterprise-wide.
- **Enterprise deployment:** administrators deploy plugins through managed settings. A **managed marketplace allowlist** controls which marketplace sources users may add. The allowlist only restricts what users can add; it doesn't register marketplaces. To push a marketplace to everyone without them running the add command, pair the allowlist with `extraKnownMarketplaces` in managed settings. Because managed settings sit above user and project settings, a plugin deployed at managed scope takes priority and can't be overridden. Check the reference layer for exact setting names.

## The packaging decision table
| Layer | What it is | For | Reach for it when |
|---|---|---|---|
| **Skill** | Markdown file in `.claude/skills`, loaded when its description matches or when invoked by name | An individual or team using Claude Code interactively | A task-specific procedure should stay out of context until needed (a PR review, a deployment checklist) |
| **Custom command** | A named shortcut that runs a defined procedure when invoked explicitly | Developers wanting a predictable entry point for high-frequency procedures | The procedure has a clear name and you want to trigger it directly rather than rely on description matching |
| **Plugin** | Versioned bundle of skills, hooks, subagents and MCP servers distributed through a marketplace | A team wanting one-step install of a shared setup | A working setup lives on one machine and must be shared, versioned and kept consistent |

## Cost, complexity, risk
- **Cost:** skills add context cost on activation, while a plugin adds install and maintenance overhead. Do you pay the setup cost once (a plugin install) or repeatedly (every developer doing the manual steps)?
- **Complexity:** a plugin that hard-codes absolute paths in its skills works for the author and fails for everyone else. Any path or environment assumption baked into a skill or hook command is what most often breaks across machines.
- **Risk:** a plugin carries only the components it bundles. A deny rule or hook the author relied on locally is not included unless explicitly listed; if skills or hooks depend on a guardrail left out of the bundle, that protection doesn't reach a teammate's machine.
