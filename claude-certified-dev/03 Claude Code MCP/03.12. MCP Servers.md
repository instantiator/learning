## Why a server rather than wiring a tool directly
Wiring a tool into an application means defining its schema and behaviour in that application's code; three applications needing the same external service means three integrations. MCP (Model Context Protocol) separates tool definitions from applications and turns them into a **server**: a process exposing **tools, resources and prompts** to MCP clients. Claude Code has a built-in MCP client: connect to a server and it discovers the tools and can invoke them in a session. Build the capability once; every connecting client gets it.

## Resources and prompts
- **Resource:** read-only data the server exposes for the client to fetch and put into context directly, instead of the model calling a tool to get it. Requested by address. A *direct* resource has a fixed address (e.g. a list of documents); a *templated* resource takes a parameter in the address (e.g. a document ID). Use one when known data should be in context from the start of a turn and loading it directly is cheaper and more predictable than a tool call. Client support varies: check yours can inject resources into context first.
- **Prompt:** a pre-written instruction template the server exposes so a client can invoke a vetted prompt by name. Useful where carefully built wording gives materially better results than whatever a user would type and you want consistent quality everywhere; it's maintained once on the server.

## Transport: how the client talks to the server
Transport depends on where the server runs.
- **stdio:** the client launches the server as a local subprocess and talks over standard input/output. Right for a local tool, a personal script or a dev server on your own machine. Doesn't work for a server shared with a team or hosted remotely.
- **HTTP:** for remote, network-hosted servers (the GitHub server below is one). (Panel not captured.)
- **SSE:** older streaming transport; deprecated in favour of HTTP (per 02.07). (Panel not captured.)

## Context cost
Each connected server contributes tool definitions that would fill the window if loaded upfront. By default Claude Code **defers** them and uses a search step to load only the tools a task needs. An opt-in mode loads definitions upfront when they fit within about 10% of the context window, deferring only beyond that. Either way, connect only the servers you need.

## Prompt caching (same idea as 02.13)
- Caching stores processing for a stable prefix so follow-up requests reuse it at a fraction of the cost. The prefix must match exactly: one changed character before the cache point invalidates it and forces a fresh write. Best candidates: a long system prompt, a large tool-definition set, a reference document queried repeatedly.
- Enabled per breakpoint: add `cache_control` of type `ephemeral` to the last block to cache (everything up to and including it). Up to four breakpoints. Requests are processed in the fixed order tools, system prompt, messages, so a breakpoint after the tools caches them while messages stay dynamic.
- Lifetime: default five minutes from the last read (each read resets the clock), suiting back-and-forth. An opt-in one-hour lifetime (`ttl: 1h`) suits agents that pause between steps; if the window lapses before the next request you pay the write cost again for no read benefit. A minimum token threshold applies (1,024 for most current models), so short prompts aren't cached even with a breakpoint.

## Retrieval-augmented generation (RAG)
A model reads everything in its window every request, so loading all reference material up front eats context. RAG keeps material outside the window, finds the parts relevant to the request, and supplies only that slice.
- **Classical RAG:** does the work upfront. Source material is split into chunks, each converted to an embedding (numbers capturing meaning) and stored in a database; a question is converted the same way and matched to the most similar chunks. Analogy: a librarian who pre-read every book and wrote a summary card per chapter.
- **Agentic search:** no upfront index. The model works out what it needs when asked and fetches it: searching live sources, reading documents on demand. Analogy: a researcher who goes and finds the answer. You may already use it: Claude Code loads only the MCP tools a task needs, and Claude.ai Projects surfaces only the relevant document sections once a knowledge base outgrows the window.
- Same fundamental move (find a relevant slice, generate from it); the difference is timing: matching against a pre-built index vs. searching at the moment of need.
- Two properties: it **scales** (per-request cost stays roughly flat as the library grows, since only the relevant slice is sent), and it is **only as good as what it finds** (if retrieval misses the document, the model never sees it, so organisation matters: descriptively named files surface more easily than "notes_final_v3.pdf").

## Configuration scope: who loads the server
| Scope | Stored in | Applies to |
|---|---|---|
| **Local** | `~/.claude.json` under the current project's path | Only that project; not shared; for a project-specific server you're not ready to commit |
| **User** | Your personal Claude settings | All your projects; still personal and not in the repo; for a personal utility used everywhere |
| **Project** | `.mcp.json` at the repo root, committed | Everyone who clones the repo, automatically; for a server the whole team uses |
| **Enterprise** | Centrally managed configuration set by an administrator | Pushed to all users in the organisation without individual setup; for shared internal services and security tooling |

## Permission rules for a single MCP tool
Connecting a server exposes its whole tool list, but you rarely want the agent to use all of it unchecked. The permission layer from 03.02 extends to MCP tools by name: `mcp__server__tool`.
- An allow rule on `mcp__github__create_issue` lets that one tool run without a prompt while every other GitHub tool still prompts. A deny on a write-capable tool blocks it while read-only tools stay available. A deny on one tool overrides an allow on the server.
- Via the API MCP connector, an `mcp_toolset` object has an `enabled` flag per tool. Permission rules decide whether an *exposed* tool may run (governance); `enabled` decides whether the model sees it at all (context cost and scope). Use them together, and check the exact rule syntax and connector beta header in the docs.

## The GitHub MCP server as a worked example
A remote server maintained by GitHub (review PRs, open issues, search code and more), using **HTTP** transport: register it by URL. Scope: **project** if the whole team needs the same repository tooling, **local** if only you do.
- **Authentication:** a Personal Access Token you generate in GitHub, passed as a Bearer token in the request header, supplied through an **environment variable** and referenced from the config. Never inline in `.mcp.json`: a token written into a committed file enters repository history and can't be removed by overwriting the file in a later commit.
- **OAuth** is the other mechanism: for services that authenticate individual users through a browser sign-in. Linear is the example: first connection redirects to Linear's sign-in, you approve, and a token is issued and stored automatically, with no credential copied by hand. Right where authorisation is tied to user identity.
- Both are remote HTTP servers with the same transport and scope logic; only the authentication step differs.

## Setup reference
| Context | Transport | Scope | Config location | Secrets |
|---|---|---|---|---|
| Personal local tool, your machine only | stdio | Local | `~/.claude.json` (per-project entry) | Environment variables only; never in the config file |
| Shared team server | HTTP | Project | `.mcp.json` committed at repo root | OAuth or env vars; API keys never committed to `.mcp.json` |
| Personal experiment, not ready to share | stdio or HTTP | Local | Personal Claude settings | Environment variables only |
| Organisation-wide, admin-managed | HTTP | Enterprise | Managed settings | Secrets managed by the administrator; config locked against override |

## Cost, complexity, risk
- **Cost:** each connected server adds tool definitions to the window; the more servers, the bigger every request. Load only what a task needs.
- **Complexity:** transport and scope are independent choices that interact: a stdio server can't be project-scoped for sharing because it runs on one machine. Match transport to where the server runs, then choose scope.
- **Risk:** committing an API key inside `.mcp.json` is the most common mistake here. It travels into repository history and rotating later doesn't remove the exposure. Secrets go in environment variables; the config file holds only the server address.
- **Handles well:** a reusable integration used across sessions and shared with a team, stable enough to maintain as its own process (the GitHub server).
- **Watch closely:** teams not managing environment secrets carefully; more servers mean more places a secret could be mishandled, concentrated in the committed `.mcp.json`.
- **Use something else:** a one-off where the tool logic can live in the codebase and needn't be reused; for a single-project, single-person integration, wiring the tool directly into the API call may be simpler than running a server.
