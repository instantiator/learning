# 03.20 Recap: Seven Key Takeaways (about 6 min)

Source: Developer Module 3, screen 20 of 22. One takeaway per section.

1. **Permission mode is a risk decision, not a speed decision.** Modes run from prompt-before-everything to prompt-for-nothing; match the mode to the risk of the work and environment, not to a wish for fewer prompts. Bypass on a developer workstation against a live codebase removes every checkpoint between the agent and your files. A deny rule on the path that must not be touched, set at project or enterprise level, covers the gap a mode alone leaves. (03.02 to 03.04)
2. **An AI code review gives findings to triage, not a verdict to apply.** Trust what the reviewer can prove from the diff in front of it (a missing null check, an unclosed resource) and confirm it on the cited lines. Treat claims about runtime behaviour or other systems as hypotheses to test, since the reviewer lacks the evidence. Put the human gate where a finding turns into a hard-to-reverse action, and raise accuracy by giving the reviewer the conventions it would otherwise guess. *(Note: the module introduction lists reviewing AI-generated code as a goal, and this recap covers it, but I did not see a dedicated screen on it in the 22-screen sequence.)*
3. **A skill is portable, but "runs everywhere" is something you design for.** The same `SKILL.md` runs in Claude Code, on the Messages API and through the Agent SDK, but each loads and sandboxes it differently: filesystem discovery in Claude Code, beta headers and a code-execution container on the API, `settingSources` on the SDK. A skill with a clear description and no local-environment assumptions ports cleanly. Subagents start clean in every runtime and don't automatically preload skills. (03.08, 03.09)
4. **Durable context needs the right mechanism for each concern.** `CLAUDE.md` is session-persistent project memory but dilutes with size; rules files scope guidance to where it applies; hooks enforce guardrails deterministically rather than probabilistically; subagents keep exploration out of the main context. Forcing everything into `CLAUDE.md` gives one file that is harder to maintain and easier to ignore. (03.05 to 03.07)
5. **A shareable setup needs portable components.** A plugin referencing an absolute path in the author's home directory installs on one machine and fails on the rest. Shared skills, hooks and plugin components must use paths relative to the project root, with any environment-variable requirement documented or validated at install time; test the install from a clean machine before distributing. (03.10, 03.11)
6. **Transport and scope are independent decisions with dependent consequences.** stdio is for servers on your machine; HTTP for anything hosted remotely or used by several developers. Local scope keeps a server personal; project scope shares it via `.mcp.json`. They must match the intent: a shared team server needs HTTP plus project or enterprise scope. A stdio server in `.mcp.json` looks shareable but isn't. (03.12 to 03.14)
7. **Enterprise integration means finding the security requirements before deployment.** A regulated customer asks about identity, data residency, access logging and configuration control. The answers: OAuth for user-identity services, environment variables for service credentials, `PostToolUse` hooks for audit logging, enterprise managed settings for configuration lock. None is hard to build; all are hard to retrofit after a deployment fails a security review. (03.15 to 03.17)
