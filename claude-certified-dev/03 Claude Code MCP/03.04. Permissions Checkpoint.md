# 03.04 Permission Modes: Checkpoint 1 (about 4 min)

Source: Developer Module 3, screen 4 of 22. Title: "Checkpoint 1: assemble the settings file and place the human gate". Not submitted; the answers below are the ones 03.02 and 03.03 support.

## The scenario
You're configuring Claude Code for a trusted local refactor of the payments module. The refactor should auto-approve file edits, must never run destructive shell commands, and `.env.production` must never be readable by the agent.

## Part 1: pick the two `settings.json` pieces that assemble the right configuration
- A: `defaultMode: "default"`
- B: `defaultMode: "bypassPermissions"`
- C: `allow: ["Bash(npm run:*)"]` and `deny: ["Bash(rm:*)", "Bash(git push:*)"]`
- D: `deny: ["Read(.env.production)"]`
- E: `allow: ["Bash(*)", "Edit(*)"]`

**Answer I'd give: C and D.**
- C allows the project's own npm scripts while denying `rm` and `git push`, which covers "never run destructive shell commands".
- D denies reading `.env.production`, which covers the secret-file requirement.
- B is out (bypass removes the safety net, 03.03). E allows every shell command and every edit, so it can't satisfy "never destructive". A on its own sets the safest mode but doesn't express either hard requirement; deny rules are what beat any mode (03.02).
- Caveat: none of the offered pieces sets `acceptEdits`, the mode built for auto-approving in-directory edits, so "auto-approve file edits" isn't directly expressed by the pair. C and D are the pair that meets the two hard "never" requirements.

## Part 2: where does the human gate go?
The agent proposes a change to a deployment configuration file that several production services read. Your settings auto-approve edits.
**Answer: (b)** a human reviews and approves the change before the write executes, because a wrong value there is hard to undo and reaches systems beyond the file.
- (a) "nowhere, edits are already auto-approved" ignores worst-case cost.
- (c) adding `bypassPermissions` removes gates entirely (03.03).
- (d) reviewing only after the write, at the next pull request, puts the check after the damage.
This is the worst-case-cost rule from 03.02: gate anything hard to undo or that reaches beyond the working file.
