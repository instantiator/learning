## The task
An agent implementation has **four planted bugs, one per layer**: schema, streaming (where the response is assembled and committed), context (where the message structure is built), and memory. For each, name the layer and write one sentence on what it causes at runtime.

## The implementation (described, not copied)
- **Tools:** one tool, `get_customer_data`, described only as "Gets data.", with a single string parameter `id` (required).
- **`run_agent(user_request, session_history)`:** starts `messages` from the session history plus the new user request, then loops:
  - sets up an empty `blocks` dict and `stop_seen = False`; streams a request with `max_tokens=4096`, the tools, the messages and `thinking={"type": "adaptive"}`;
  - on `content_block_start` creates a block, on `content_block_delta` applies the delta, on `message_stop` sets `stop_seen = True`;
  - after the stream, builds `assistant_content` from the assembled blocks **filtering out any block of type `thinking`**, and appends it to `messages` as the assistant turn;
  - finalises the response; returns on `end_turn`; otherwise, **for each `tool_use` block**, executes the tool and appends a separate user message holding a single `tool_result`.
- **`build_session_history(prior_sessions)`:** concatenates the message lists of *all* prior session transcripts into one in-context history.

## My read of the four bugs (not the course's answer)
1. **Schema layer:** the description "Gets data." and the bare `id` give Claude nothing to choose on: no when-to-use or when-not-to-use, no sense of what kind of ID. Result: wrong-tool or malformed calls once there is a second tool (02.07/02.08).
2. **Streaming layer:** `stop_seen` is set but never checked, so the assistant turn is committed to history whenever the loop exits. An interrupted stream commits a half-built turn (possibly a truncated `tool_use`), and the next request is rejected (02.11/02.12).
3. **Context layer:** this is the layer I'm least sure which line the course means, because two things are wrong in the message construction:
   - thinking blocks are stripped from the assistant turn, violating the carry-back rule: with adaptive thinking on and tools in use, the API rejects the next request (02.05);
   - each `tool_result` is appended as its own user message; all results for one assistant turn must come back together in the immediately following user turn (02.07, 02.16 checklist).
   The first looks like the intended planted bug, given the explicit `thinking` filter and the `thinking` parameter. The second is a real defect either way.
4. **Memory layer:** `build_session_history` concatenates every prior session transcript into the live context, so history grows without bound and fills the window by a later session (02.19/02.20). Use external storage, or inject a summary or relevant subset.
