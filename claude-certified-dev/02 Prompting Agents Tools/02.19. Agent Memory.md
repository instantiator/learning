# 02.19 Agent Memory: Teaching (about 8 min)

Source: Developer Module 2, screen 19 of 29. Title: "Choosing the right scope for state that survives sessions".

## The problem
The agent from 02.16 works inside one session but remembers nothing once it ends. Memory scope decides what the agent knows at the start of the next session and what it costs to carry that forward. The screen also recaps related agent patterns built earlier in the module: the tool-use loop, multi-step task decomposition (ordered subtasks), and planning-and-execution (deciding the plan separately from carrying it out, which is the split the post-planning HITL check guards).

Two opposite failure modes:
- too much state in context: every call re-reads the whole conversation, so cost scales with session length;
- too little persisted: anything not written down vanishes when the conversation ends.

## Four memory scopes
| Scope | What persists | Cost | Use when | What you lose |
|---|---|---|---|---|
| **In-context** | State lives in the active conversation, across turns within one session | No retrieval overhead; token cost grows as the conversation grows | Short sessions where everything fits in the window and nothing must survive a restart | Everything when the session ends (a clear or new session wipes it) |
| **External storage** | State written to a database, read back at session start or on demand | Retrieval latency per call, plus the read/write engineering | State that must survive sessions, move between users, or be shared across agent instances | Nothing on persistence; the cost is latency and ongoing complexity |
| **Summarised memory** | A condensed version of prior conversation injected at the next session's start | Lower tokens per session than replaying history, but summarising drops detail | Long-running conversational agents whose full history would outgrow the budget | Any detail the summariser didn't keep |
| **Stateless** | Nothing; each session is independent | None | Task agents that finish and close out, or fully independent pipelines | All prior context; follow-ups can't reach earlier sessions |

## Decide at design time
- An agent helping the same user over several days needs state carried between sessions (summaries or full history outside the window). A single-job agent can run stateless.
- The default path, storing full history in the `messages` array and sending it every call, works at first. Then cost rises with every turn, latency climbs as the window fills, and a long session eventually hits the hard limit.
- The eventual refactor is mechanical (a few hundred lines and a database the team already has), but it happens under production pressure. Choosing during design is cheap; doing it as a deadline refactor is expensive.
- **Handles well:** scope matched to the task: external storage for cross-session threads, stateless for self-contained jobs, in-context for short sessions that needn't survive a restart.
- **Adds cost or complexity:** external storage needs retrieval latency and read/write logic; summarised memory depends on a well-specified summariser prompt or task-critical state is dropped each compression.
- **Avoid:** keeping everything in context on the assumption the window will be big enough. Without caching or compaction, long sessions cost more than teams expect from early-turn measurements. Measure real session token use against the window first.

## Skills: reusable instructions that load on demand
A different problem from state: how to carry repeatable instructions across tasks without paying to inject them every session. A **Skill** is a reusable markdown file teaching Claude one kind of task, loaded automatically when a request matches its description.
- It lives in a `SKILL.md` inside an identified directory: frontmatter (name, description) plus the instructions. The description is the matching criterion. Claude reads every available Skill's name and description, compares them to the request, and loads the full instructions only on a match; otherwise they never enter the window.
- Contrast: in-context memory is always present and grows each turn. `CLAUDE.md` in the Claude Code CLI loads into every session regardless of task. In the Agent SDK, whether `CLAUDE.md` and other filesystem settings load is controlled by `settingSources`: set it explicitly rather than relying on a default, and confirm current defaults in the Agent SDK reference. Skills load only when the task calls for them in both environments.
| Pattern | Loads | Context cost | Best for |
|---|---|---|---|
| **Skill** (`SKILL.md`) | On demand when the request matches its description | Low: only name and description at startup | Task-specific expertise: domain output formats, specialised review checklists, workflows for a subset of tasks |
| **CLAUDE.md** | Every session, unconditionally | Fixed per-session overhead | Always-on project standards: team coding conventions, required output rules, constraints for all tasks |
| **In-context instructions** | Every turn of that session | Grows with the session; gone at session end | Short, one-off, single-conversation work |

### Skills on the Messages API (beta)
Available today but in beta, with a different configuration from Claude Code or the Agent SDK. Two beta headers are required on the request: `code-execution-2025-08-25` and `skills-2025-10-02`. Skills run inside the code-execution container, not your application's environment, which limits the tools and filesystem access they can assume. Headers change as features move toward general availability, so verify header values, GA status, and the runtime path in the current API docs before building on it.

### Subagents and Skills
Subagents do **not** inherit Skills (or conversation history) from the parent: they start with a clean context. They *do* inherit the parent's permission context, so permission scope isn't reset on delegation. If a subagent needs a Skill, list it explicitly in that subagent's configuration; register the instructions against the subagent at design time rather than assuming they carry over.
