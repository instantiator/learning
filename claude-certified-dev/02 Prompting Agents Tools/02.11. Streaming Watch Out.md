# 02.11 Streaming: Watch Out (about 5 min)

Source: Developer Module 2, screen 11 of 29. Title: "The stream that left a half-written tool call in the history".

## The trap
A streamed response can look fine on screen and still corrupt the next request. The text rendered, the user saw an answer, and the turn was appended to history, but the stream had dropped mid-block, so the stored `tool_use` was missing part of its input. The failure surfaces on the *next* request, so the error points away from the real cause.

## Postmortem (composite)
- An agent streamed so operators could watch output live. The handler accumulated `content_block_delta` events and appended the assistant turn to history when its read loop ended.
- In testing on a fast local connection, streams always finished, so the loop always ended at `message_stop` and stored turns were complete.
- In production, a network blip ended a stream after a `tool_use` block opened and got part of its JSON input, but before `content_block_stop`. The loop ended exactly as it always did, so the handler appended an assistant turn whose `tool_use` input was truncated JSON.
- The operator saw a partial answer and retried. The retry carried the corrupted turn in history, and the API rejected it with a validation error about the malformed `tool_use`.
- The team spent an afternoon inspecting the schema and the retry logic, because that's where the error appeared. The real bug was upstream: the handler treated "the read loop ended" as "the message is complete".

## Takeaways
- A stream ending is not the same as a message completing. Only `message_stop` means the message is whole.
- Gate the history append on `message_stop`; on interruption, discard the partial turn and retry from the last complete turn.
- When a tool-use error appears on a retry, check whether the previous turn was assembled from a stream before touching the schema.
