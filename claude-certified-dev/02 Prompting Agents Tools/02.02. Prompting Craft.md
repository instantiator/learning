## Core idea
A prompt that works once interactively often breaks in production on untested inputs. The cure is rarely "more words". Diagnose which structural piece is missing, add that one piece, re-run. Rewording changes phrasing, not structure: if Claude blurs the boundary between your instructions and your data, or the format keeps drifting, "please format this correctly" won't fix it.

## Failure mode -> missing technique
| What you see | What's missing | Why it fixes it |
|---|---|---|
| Wrong shape (a sentence instead of a label, prose instead of JSON) | **Output constraint** | Controls the form of the answer independently of content; without it the parser gets plausible text it can't accept. |
| Content or scope drifts, tone shifts, worse deeper into the conversation | **System prompt** (or a more specific one) | Holds role, scope and format steady across turns. |
| Right task, invented structure | **Few-shot examples** | Showing the pattern beats describing it; one correct input/output pair pins the shape. |
| Fine on tested inputs, breaks on a variant/edge case | **A constraint or example covering the variant** | Test inputs were too narrow; name the variant. |

Rule: name the failure, add the one matching technique, re-run; if still failing, diagnose again. A prompt that gets longer every pass is a sign you're skipping diagnosis.

## Worked example: support-ticket classifier
- Bare prompt ("You are a support classifier. Classify the ticket.") returns "Billing", "billing", or a full sentence on different runs, which breaks the router.
- Fix stacks three techniques: a system prompt that says classify into exactly one of BILLING, TECHNICAL, ESCALATION and return only the label; XML tags (`<sample_input>`, `<ideal_output>`) separating the examples from the instruction; two few-shot pairs showing exact label and casing.
- Result: consistent enough to route programmatically.

## When to stack vs simplify
- **Stack all four** when there is a well-defined output contract and edge cases that examples can cover.
- **Simplify** when a simple task needs only one (summarising a paragraph doesn't need examples plus a schema).
- **Diagnose before adding** when the prompt keeps growing: after about five re-prompts, identify the failure type first.

## The four techniques (what I captured)
- **System prompts:** the persistent behavioural contract for the session; write once. Defines role, output format, rules that must not change between conversations.
- **XML tags:** use when a prompt mixes inputs with instructions (e.g. code plus docs). Wrap each in descriptive tags like `<my_code>` and `<docs>` so the boundary is unambiguous. Names needn't be official; descriptive ones work best.
- **Few-shot examples:** (panel not captured) per the table above, they show Claude the exact shape; cost is extra tokens per call (see 01.04).
- **Output constraints:** (panel not captured) per the table above, they fix the form, field names and stopping point of the response.

## Structured outputs: moving control into the API
Prompts are requests, so Claude can still emit a stray sentence, wrong field name or malformed JSON. Structured outputs hand the API a JSON schema and use constrained decoding: at each token only tokens that keep the output valid against the schema are allowed, so a violating response can't be produced.
- **JSON outputs** constrain the final response: set `output_config.format` with type `json_schema` and your schema.
- **Strict tool use** constrains tool inputs: set `strict: true` on a tool definition so arguments are validated against its input schema before your code runs. Useful in agent loops where a bad argument would crash the step.
- Why it belongs in code, not only the prompt: a prompt instruction holds on the cases you tried and slips on one you didn't; the schema is enforced on every token. Correctness moves from "verify afterwards" to "ruled out beforehand".

Costs to weigh (don't enable everywhere by default):
- First request on a new schema is slower (schema compiled to a grammar); grammars are cached for 24 hours from last use.
- Input tokens rise slightly because the API injects a format-describing system prompt that is billed.
- A guaranteed schema is not guaranteed success: a refusal (`stop_reason: refusal`) or hitting `max_tokens` (stop mid-structure) can still yield non-matching output.
- Not compatible with message prefilling; pick one.
