# 02.07 Tool Schemas: Teaching (about 20 min)

Source: Developer Module 2, screen 7 of 29. Title: "Tool schemas Claude selects correctly: definition, loop, and calling patterns".

Note: the screen has a clickable six-step loop diagram; only the first step's panel was captured. The other steps are summarised from the surrounding text.

## Mindset shift
Up to now you steered language toward a good answer. With tools you hand Claude a set of actions and trust it to pick one, and that choice is driven almost entirely by what you wrote in the schema.

## How the loop works
Claude does not run tools. It reads your definitions, decides which fits, and tells your application what to call and with what inputs. Your code executes it and sends the result back; Claude continues from there. Most tool-use bugs live at this boundary.
Steps: (1) define schema (name, description, input schema); (2) send message with the tools; (3) Claude returns a `tool_use` block; (4) **your code** executes the tool (the loop is not automatic); (5) return the result; (6) Claude continues. A systematic miss in tool choice is fixed back at step 1, the schema.

## Message blocks
Turns are lists of blocks:
| Block | Who | Holds | Rule |
|---|---|---|---|
| `text` | Claude | prose | If it arrives alongside a `tool_use`, keep the whole content array when appending to history; dropping it corrupts later context. |
| `tool_use` | Claude | tool name, unique ID, input args | Must be answered by a `tool_result` in the very next user turn. |
| `tool_result` | you | matching `tool_use_id`, result content, optional `is_error: true` | ID must match exactly; matters when one turn makes several calls and results come back out of order. |
| `thinking` | Claude (extended thinking only) | reasoning | Return unchanged (signature check); redacted blocks too (see 02.05). |

Invariant: every `tool_use` needs a matching `tool_result` in the immediately following user turn. Missing, mismatched, or late results fail validation. This is structural, not fixable by prompting.

## Schema anatomy
Three parts: **name**, **description**, **input_schema**. The description decides selection.
- Name: short and specific (`get_account_balance` beats `get_data`).
- Description: say both when to use it and when not to. "Use this to find information" is indistinguishable from any other retrieval tool; "retrieve the current balance for an account ID; don't use for transaction history" gives an exclusion condition.
- `input_schema`: JSON Schema for parameters. Require only what the call can't work without; make the rest optional. Overlapping parameter shapes across tools are the commonest cause of wrong-tool calls.

## Design decisions
| Decision | Guidance | Why |
|---|---|---|
| Subtask dependency | Dependent calls run in sequence (separate turns). Independent ones can be issued as several `tool_use` blocks in one turn. | Current models default to parallel calls when independent; use `disable_parallel_tool_use` to force serial where needed. |
| Required fields | Required only if the call makes no sense without it. | Over-requiring forces Claude to invent values. |
| Optional fields | For sensible defaults or meaningful absence; give defaults in your function. | Lets Claude omit what it doesn't know instead of guessing. |
| Description length | Three to four sentences: what it does, when to use it, what it returns; examples where format matters. | Too short means guessing; too long buries the trigger conditions. |
| Overlapping parameter types | Add disambiguating domain/trigger language to each description. | Routing is name plus description; identical signatures leave description as the only signal. |

## Worked example (illustrative)
Two tools, `search_knowledge_base` and `get_cached_result`, both described as "use this to find information", get confused. Fix: add exclusion conditions. Search: use for current-information lookups, but not if a prior search this session already covers it. Cached: only if `search_knowledge_base` already ran for the same query. This only works if full conversation history is sent each time; truncate it and the exclusions fail silently.
- Handles well: reliable routing when descriptions are specific and exclusions stated.
- Poor fit: two similar tools needing ever-longer descriptions; merge them into one tool with a type parameter.

## MCP as an alternative to writing schemas
The Model Context Protocol moves tool definitions and execution into dedicated servers. If a maintained server exists (e.g. GitHub), connect instead of hand-building every schema.
- The loop is unchanged. Only setup differs: your MCP client sends a `ListToolsRequest`, receives the tool list, and passes it to Claude, which can't tell them from hand-written ones.
- Context cost: server tool definitions occupy the context window even when unused. Register only servers you need, and check the budget when connecting several.
- With the API MCP Connector, control cost via an `mcp_toolset` object in the tools array: a `default_config` plus per-tool overrides in `configs`. `defer_loading` delays loading a definition until needed; `enabled` switches tools on/off (allowlist/denylist). It requires the `mcp-client-2025-11-20` beta header.
- Transports: local servers use **stdio** (your app spawns a subprocess); remote servers use **Streamable HTTP** (POST for client-to-server, optional GET-based SSE stream for server pushes). The older SSE-only transport is deprecated. The API connector supports only HTTP-exposed (remote) servers; stdio needs you to manage the client yourself via the SDK or use Claude Desktop/Claude Code.
- **Use MCP** when a well-maintained server covers the operations you need. **Write schemas manually** when none does, or you need precise description quality (scope alone can often be handled with allowlisting). **Use both** for breadth plus precision: narrow the tool set first, then tune descriptions.
