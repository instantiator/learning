# 02.17 Agent Construction: Watch Out (about 5 min)

Source: Developer Module 2, screen 17 of 29. Title: "The agent that edited a production file".

## The trap
An agent that works end to end in testing because the test environment is forgiving. Same tools, same loop, same system prompt, but the human-in-the-loop (HITL) checkpoint is missing because testing never produced a case that needed one.

## The incident (composite)
- A developer built an agent with three tools: `read_file`, `write_file`, `validate_config`. After each write it re-ran `validate_config`; if validation still failed it adjusted and rewrote, capped at ten iterations.
- Tested against a scratch copy of the config, it converged in two or three iterations every time.
- Deployed to a customer environment, it found a parameter out of range, proposed a fix, called `write_file`, re-ran `validate_config`, got a pass, and stopped after one iteration. Exactly as designed.
- The parameter was a rate limit the customer's application relied on. `validate_config` only checked the value was within the schema's allowed range, not whether downstream systems depended on the old value. Within minutes the customer's application failed because requests were throttled at a rate it couldn't handle.

## Diagnosis
The loop did what it was told. The exit condition ("`validate_config` passes") was scoped to the file being edited. Nothing sat between "validation passed on this file" and "write committed to the customer environment". The missing piece was an explicit state between "proposed change ready" and "write committed", where the change is surfaced for human review before the first `write_file` touches live config. Tests never produced a case needing it, so it was never added.

## Takeaways
- This is a permissions question that was never asked at design time. The agent had write access because the task was editing files, and the task was legitimate. The gap is between an agent that **proposes** a change and one that **commits** it. In a disposable test environment that gap never shows.
- The question to ask: what is the worst outcome if `write_file` runs without a human check? The answer decides whether a HITL checkpoint is required.
- If a tool can take an irreversible action in production, it needs a checkpoint before it runs. Decide this while scoping the tool surface, not after the first incident. (Placement guidance is in 02.16.)
