# 02.25 Multimodal and Batch Ingestion: Watch Out (about 4 min)

Source: Developer Module 2, screen 25 of 29. Title: "The batch job that was not actually a batch".

## The trap
Splitting a job into chunks and processing them one after another is not batching. It is serialisation with extra steps. Looping over inputs against the synchronous API hits rate limits as soon as the volume is real, however you slice the list.

## The scenario (illustrative conversation)
- A developer has re-run a nightly classification job for three nights and hits rate-limit errors at about the same point each time. They've already split the input into smaller chunks.
- The senior developer asks how the chunks are submitted. Answer: looping over the list and calling the API once per item.
- Diagnosis: that's serial calls against the synchronous endpoint. Chunking doesn't change what the API sees, which is one request per item, back to back. The rate limit fires because of thousands of individual synchronous calls.
- The fix: the Message Batches API. One call can carry up to 100,000 requests or 256 MB, returns a `batch_id`, and runs asynchronously. Your code polls the batch status on a schedule until it completes. Per-token cost is lower, and the rate limit doesn't fire because you aren't making thousands of separate requests.
- The trade-off: latency is non-deterministic and a batch can take hours. For a real-time user interaction that would be the wrong tool; for a nightly classification run it's ideal.

## Takeaways
- Chunking plus a synchronous loop produces the same number of calls as the un-chunked job and meets the same limits. The Batches API is a different submission model, not a smaller batch size.
- Use it for high-volume, offline work; use synchronous calls only when a user is waiting.
- Results come back in arbitrary order, not submission order. Put a `custom_id` on each request and use it to match results back to inputs.
