# 02.20 Agent Memory: Watch Out (about 2 min)

Source: Developer Module 2, screen 20 of 29. Title: "The agent that filled the window on session four".

## The trap
In development you ran one long continuous session, so the window never filled and in-context memory held everything. Production runs many shorter sessions across more days, with state accumulating between them, and the window fills at session four.

## Postmortem (composite)
- An agent assisted a support engineer with ongoing escalation cases. Development used continuous sessions of 10 to 15 turns; in-context state held the full history correctly. Token usage per session was never measured before shipping.
- In production each session was shorter, but state accumulated across sessions. By session four the injected in-context history exceeded 40,000 tokens before a single tool call, and with the system prompt and tool schemas over 45,000 tokens of the budget were gone before the first productive turn.
- As tool calls accumulated, the remaining budget ran out before the analysis finished and the agent returned incomplete results. This first looked like a tool-selection failure, not a memory-architecture one.
- Fix: a refactor to external storage: pull accumulated history out of the live context, persist it in a database, and inject only the relevant subset at session start. Done under production pressure it took far longer than it would have at design time; the storage layer, retrieval logic and session management all needed decisions that belonged before the first deployment.

## Takeaway
A single long session and many short sessions with accumulated state are different shapes, and in-context memory handles them differently. Before choosing in-context as the default, measure expected state per session (history plus system prompt plus tool schemas) against the context limit. (Compare 02.14: another "looks like tool selection, is really context" failure.)
