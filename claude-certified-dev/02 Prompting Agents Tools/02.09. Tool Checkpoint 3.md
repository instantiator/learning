# 02.09 Tool Schemas: Checkpoint 3 (about 4 min)

Source: Developer Module 2, screen 9 of 29. Title: "Checkpoint 3: Spot and fix the schema bug". A multiple-choice exercise, not submitted; the answer below is the one 02.07 supports.

## The scenario
A session trace for `get_account_balance` ends in an API validation error. The schema is valid, the description is specific, and the tool result content is correct.
- Turn 1 (user): asks for the balance of account A-4471.
- Turn 2 (assistant): a short text block, then a `tool_use` with id `toolu_01`, calling `get_account_balance` with `account_id: "A-4471"`.
- Turn 3 (user, tool result): a `tool_result` whose `tool_use_id` is `toolu_02`, content "Balance: $1,240.18".
- Turn 4: the API returns `invalid_request_error`: the `tool_result` references an unknown `tool_use_id`.

Convention to remember: `tool_result` blocks are sent in the **user** role even though your application generates them; the role says who is sending the message to Claude, not who wrote the content.

## Task
Identify the missing or mis-ordered block, name the broken rule, and pick the targeted fix.

## Options and answer
- A. Add an exclusion condition to the tool description. (Not it: description isn't the problem.)
- **B. Correct the `tool_use_id` on the `tool_result` so it matches the id issued in the assistant turn. (This is the fix.)**
- C. Add a `required` array so `account_id` can't be omitted. (Not it: the input was supplied.)

## Why
The ID pairing rule from 02.07: every `tool_use` must be answered by a `tool_result` in the next user turn carrying the same ID. Here the result says `toolu_02` but the call was `toolu_01`, so the pairing fails. It is a structural bug in your code, not a prompt or schema-design problem.
