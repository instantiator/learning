# 02.13 Context Engineering: Teaching (about 16 min)

Source: Developer Module 2, screen 13 of 29. Title: "Model selection and keeping multi-turn sessions in budget".

## Framing
Two early constraints: which model runs the workload (it sets the price/speed floor for everything after), and the context window. Every tool result is appended and stays for the rest of the session. In a ten- or twenty-call agent session the window fills fast, and then the agent either compacts (losing detail) or stalls. **Context engineering** is deciding in advance what goes into the window, what comes back out as a summary, and what never enters at all.

## Model selection
- Four tiers: Fable (most capable), Opus, Sonnet (balanced default), Haiku (fast and cheap). Confirm the current lineup and IDs in the platform docs.
- Start with Sonnet. Move up to Opus only when an eval says Sonnet misses your quality bar; move down to Haiku only when an eval says the quality drop is acceptable for the task, not merely to save money. Moves should be measured. (Same rule as 01.03.)

## The window is not free
- It holds every message, tool result, injected document and response.
- Input already over the window: rejected with a validation error before generation. Fits on input but hits the ceiling mid-generation: output so far is returned with stop reason `model_context_window_exceeded`. Neither path silently drops your oldest content, so your app must trim or summarise history before the next request.
- Development hides this (small inputs, short sessions). In production tool outputs are often 3 to 5 times longer than test fixtures and the window can fill by turn eight instead of fifty. Not planning for it means an outage.

## Four strategies
| Strategy | What it does | Apply when | What you lose |
|---|---|---|---|
| **Pruning** | Jump back to an earlier message and continue from there, removing what came after | Claude went down an unproductive path or accumulated debugging chatter | Everything after the rewind point; anything learned there must be relearned |
| **Compaction** (`/compact` in Claude Code; server-side compaction in the API, a beta where the platform summarises for you; manual summarisation is the client-side alternative) | Replaces history with a condensed summary | Nearing the ceiling but continuing the same work | Detail the summary didn't capture |
| **Clearing** (`/clear`; new session in the API) | Fresh conversation, empty context | Next task is unrelated and old context would bias it | All session context; anything needed later must live somewhere persistent such as a `CLAUDE.md` |
| **Subagent handoffs** | Subagent in its own isolated window gets only the task and system prompt it needs, returns a summary | Self-contained subtasks, especially exploration where the journey is noisy but the answer short | Visibility into how it reached the answer |

## Two cost levers
- **Prompt caching:** reuses processing for a stable prefix. First request writes the cache; later requests sending identical content up to that point pay a fraction. Best for things that rarely change: a long system prompt, big tool definitions, a reference document queried repeatedly. Enable with a `cache_control` field of type `ephemeral` on the last block to cache; up to four breakpoints. For multi-turn sessions with stable system prompt and tools, this is the biggest cost reduction available.
- **Token counting:** the `count_tokens` endpoint takes the same body as a messages call and returns the count without running inference. Use it in development to check budget assumptions against real tool output, and in production to gate requests that would exceed the window.

## Where a RAG path breaks (three places)
- **Chunking:** too small and a chunk lacks context; too large and it dilutes the match. Sentence or section chunking with slight overlap is a sound default.
- **Embedding match:** similarity search finds semantically close content, not necessarily the exact term. A query for a specific identifier can miss the right chunk if something more semantically similar ranks higher.
- **Assembly:** retrieved chunks must reach the model in the structure the prompt expects, or it answers from memory instead of the retrieved text.
- Trade-off: a fetch-once index is inspectable and testable but needs building, syncing as the corpus changes, and securing. Searching across rounds (the model reads current files at query time) needs no index and has no staleness but costs more tokens and time and is less inspectable. Stable corpus with simple lookups: own the index. Changing corpus or multi-step questions: iterative search is usually simpler despite higher per-query cost. The reported gain for single-agent agentic search over an index is version-specific; verify before relying on it.

## Compaction: the summariser prompt decides what survives
- In Claude Code `/compact` chooses the summary content. In the API, the main documented route is server-side compaction (beta); otherwise you write the summariser prompt.
- "Summarise the conversation so far" yields a generic summary that may drop task-critical state (which files changed, what was decided at a branch, which errors were met and fixed).
- Better: ask it to preserve all modified file paths, all decisions made, and all errors with their resolutions. Losing task-critical state to a vague summariser is a very common cause of multi-session agent failure.

## Subagent handoffs for long tasks
A bigger window isn't the answer to a task that's too large; decompose it. Each subagent gets a scoped task, the minimum relevant context (including directly relevant prior results), the tools it needs, and clear exit conditions; the parent collects results. Keeps per-turn cost low and makes long-horizon work tractable. Like pruning and compaction it adds implementation overhead, so use it only where context cost is a real constraint.
- **Handles well:** multi-step agent sessions exceeding budget; design it at architecture time, not as a late patch.
- **Use something else:** pipelines that never approach the limit; measure token usage first.
