# 02.08 Tool Schemas: Watch Out (about 5 min)

Source: Developer Module 2, screen 8 of 29. Title: "The description that sent Claude to the wrong tool".

## The trap
A schema can look correct and still fail. Typed parameters and passing happy-path tests show the structure is valid, but not that Claude can reliably choose between tools when an input sits near the boundary of two overlapping descriptions. Initial testing misses this and production finds it.

## The scenario (composite, illustrative)
A developer has re-run a case four times and Claude keeps calling `search_docs` even when the answer is already in context. A senior developer asks to see the descriptions:
- `search_docs`: "Use this to find information about the product."
- `get_context_summary`: "Use this to retrieve relevant information from the current session."

To Claude these are the same thing: both say "find information". One of them has to say when *not* to call it.

## The fix
Both tools need the boundary, not just one.
- `search_docs`: use it when the user asks something requiring content not already in the conversation; do not call it if the answer is available in the current session context.
- `get_context_summary`: use it only if the answer is already present in the session; do not use it to look up new information.
Two sentences per tool: one saying when to use it, one saying when not to.

## Why it happens
Claude picks a tool by reasoning over all registered descriptions in light of the whole conversation. If two descriptions look alike, there's no reliable signal, so it falls back on small surface differences that may not match the distinction you meant.

## Rule
For overlapping descriptions, add one sentence naming when not to call the tool, to give Claude a decision boundary. If the descriptions can't be cleanly separated even with exclusions, merge the tools into one with a type parameter (see 02.07).
