# 02.10 Streaming: Teaching (about 16 min)

Source: Developer Module 2, screen 10 of 29. Title: "Streaming responses and handling partial output without corrupting state".

## What changes
A non-streamed call returns one complete message. A streamed call returns a series of events describing the message as it is built. The final message is identical, but **you** assemble the pieces and **you** decide what happens if the events stop early. Each event is a small independent message about one change; nothing live is held open for you.

## Event sequence and what your handler does
| Event | Signals | Handler |
|---|---|---|
| `message_start` | A new message begins (empty content shell, initial usage) | Create an empty content array. |
| `content_block_start` | A block opens, with type (`text`, `tool_use`, `thinking`) and index | Make a slot at that index. A `tool_use` opens with name and id but no input yet. |
| `content_block_delta` | An incremental piece of one block (text, partial JSON for tool input, or thinking) | Append to the block at that index. Tool input arrives as a partial JSON string across several deltas and can't be parsed yet. |
| `content_block_stop` | That block is complete | Finalize it. For `tool_use`, this is the first moment the accumulated JSON is complete enough to parse. |
| `message_delta` | Top-level changes: `stop_reason`, final usage | Record the `stop_reason`. |
| `message_stop` | Stream complete | The assembled array is now the finished message; treat it like a non-streamed response. |

## Core rule: don't act on a partial block
- A `tool_use` input is not valid JSON until `content_block_stop`. Parse or run the tool earlier and you either choke on malformed JSON or run with half the arguments.
- Collect deltas; act only after `content_block_stop` for that block.
- Same discipline for history: append a streamed assistant turn only after `message_stop`, with every block assembled. A half-built `tool_use` in history makes the tool-use pairing rules reject your next request.

## When the stream stops early
Dropped connections, timeouts and client disconnects can end the stream before `message_stop`. The danger is treating what you have as complete. A partial text block shown to a user is cosmetic; a partial `tool_use` written into history corrupts the next turn.
- **Track completion deliberately:** a turn is usable only after `message_stop`; until then it's provisional.
- **On interruption, discard the partial assistant turn** rather than saving it, then retry the request.
- **Check `stop_reason`** (from `message_delta`) before continuing a loop: `tool_use` means your assembled tool calls are ready to run; any other value means a different path.

## Summary box
- **Handles well:** long responses and user-facing UIs where showing output as it generates removes the blank-screen wait.
- **Adds cost or complexity:** you assemble blocks, must not act on partial ones, and must handle interruption explicitly.
- **Use something else:** for short responses or backend jobs with nobody waiting, a non-streamed call is simpler and removes the partial-state risk.
