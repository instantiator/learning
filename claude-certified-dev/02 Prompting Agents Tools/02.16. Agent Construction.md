## What an agent is
A multi-step tool-use loop with managed context and a defined goal. Combined components bring failure modes that isolated tests miss: routing decisions compound, context fills faster than expected, and a step gets the wrong input because an earlier tool call was malformed. The question to ask first: does this problem need an agent at all? Agents bring coordination overhead, larger context cost and more failure surface.

## Workflow or agent?
Picking wrong is the most costly early mistake: an agent where a workflow would do adds behavioural complexity for no capability; a workflow where an agent is needed breaks when input leaves the scripted path.
| Choose a workflow when | Choose an agent when |
|---|---|
| You can enumerate the exact steps in code | You can specify the goal and tools but not the path |
| Error cost is real and step-level guardrails matter | The path can't be enumerated in advance |
| You need observability with standard tooling | Non-determinism is acceptable and actions are bounded by the registered toolset |
| Inputs are well-constrained to a known set | Inputs vary unpredictably in content and structure |
| Every run follows the same sequence | The task needs creative sequencing of tools |
Progression: single API call, then workflow, then agent; move up only when the simpler pattern can't handle the variability.

## The pattern is constant; the wiring path is a choice
For a single agent, the loop (call tools, manage context, run until the goal is met) is the same on all three paths. Multi-agent designs (planner, executor, evaluator handing off through structured artifacts) add decisions covered later in the track. The paths differ in how much of the runtime you own:
1. **Raw Messages API loop:** your code runs every iteration: send, read tool-use blocks, execute tools, append results. You own the full loop, tool execution, context management, retries and exit conditions. Choose it for full per-step control, constraints a library can't meet, or to learn the loop before abstracting. Every behaviour the SDK would give free (context management, parallel tool handling) becomes code you write and test.
2. **Agent SDK:** runs the same loop in your own process and supplies tool registration, system prompt setup, context management and iteration structure; your code still executes tools.
3. **Claude Managed Agents** (public beta): Anthropic runs the loop and sandbox.
Choose on deployment and compliance constraints, not on what's fastest to prototype.

## Managed Agents in detail
You define the agent once (model, system prompt, tools, MCP servers, skills) as a versioned API resource, refer to it by ID, send user events, and stream results back over server-sent events.
| | You stop owning | You take on instead |
|---|---|---|
| Execution and infrastructure | The loop, execution sandbox, in-loop retries, tool runtime | An agent definition as an API resource, plus an app layer that sends events and consumes the stream |
| Session duration and state | Holding long-running execution open (minutes to hours) | Server-side, Anthropic-stored session state, subject to its data policies |
| Sandbox lifecycle | Provisioning and teardown | Dependence on the managed sandbox's tools and execution model |
Choose it when: the task runs long; you want a managed sandbox; or you'd rather not build the loop, sandbox and tool runtime at all and accept defining the agent as a resource.
**Deciding constraint for regulated work:** sessions are stateful and stored server-side, so they are not currently eligible for Zero Data Retention or a HIPAA BAA. For PHI or ZDR workloads this path is out regardless of fit; use the Agent SDK or a raw loop on a covered configuration.
Common progression: prototype on the Agent SDK locally, move to Managed Agents for production. The definition carries over conceptually but must be re-expressed (code/filesystem config versus a versioned API resource), not exported.
- **Handles well:** long-running agents; avoiding building and securing your own sandbox and loop.
- **Adds cost or complexity:** server-side stateful sessions, an agent-as-resource format, and a beta surface that may change.
- **Use something else:** PHI/ZDR workloads, or when you need full in-process control.

## Four steps that hold on every path
1. **Register tools** (same schema structure; the SDK registers them against the agent).
2. **Set a scoped system prompt:** name the task and the tools available. A broad prompt gives broader, less reliable routing.
3. **Handle the tool-use loop:** whoever iterates, your code executes every tool call and returns a tool result.
4. **Define exit conditions:** without them the agent keeps requesting tool calls past the task; define when "done" is done.

## Loop wiring checklist
1. Tools registered: every tool needed is registered; the system prompt references none that aren't.
2. System prompt scoped: names the task and available tools; doesn't describe tools it lacks; doesn't omit scoping guidance for tools it has.
3. Tool-use loop implemented: every tool-use block gets a tool result before the next assistant turn; all blocks from one assistant turn are resolved together.
4. HITL insertion point defined: at least one human check in the loop.
5. Exit conditions defined: a stopping criterion that doesn't rely on Claude volunteering to stop.

## Human-in-the-loop placement
Ask: what is the worst outcome if this step runs unchecked?
| Insertion point | Trigger | Risk addressed |
|---|---|---|
| Before a destructive tool call | About to write, delete or send | High: irreversible actions |
| After a planning step | A plan exists and execution is about to begin | Medium: a wrong plan gives wrong outcomes even if every step runs right |
| On unexpected output | Error flag, empty result, or out-of-bounds value | Variable: failures retry logic alone won't resolve |

## Tool orchestration: over- and under-tooling
Routing depends on how tools are described and how many are registered. Too many tools with overlapping descriptions gives erratic routing; too few forces hallucinated paths or incomplete results. Over-tooling is the commoner production problem ("just in case" tools degrade selection). Start with the minimum set and add a tool only for a confirmed capability gap.
- Agents fit goal-directed tasks with unenumerable paths or variable inputs needing dozens of branches in a workflow.
- Cost: the path emerges from model reasoning over accumulated context rather than explicit code, and observability needs transcript-level tooling rather than ordinary operational logging.
- If you can enumerate the steps in code, use a workflow.

## Regulated data sets the route before the wiring
Constraints such as privilege, HIPAA, GDPR, FedRAMP or internal residency policy decide which endpoint your code calls, which credentials it carries and where logs land, before any prompt, tool or memory design. Fixing the wrong client configuration after wiring is far costlier than setting it right first.
| Constraint | Tends to rule out | Usually survives review |
|---|---|---|
| Attorney-client privilege | Consumer Claude.ai surfaces the firm can't audit end to end; sending privileged content to any endpoint not approved for it | Direct API/SDK calls inside the firm's app, SSO-authenticated, via a firm-approved gateway with full request/response logging (the course notes native compliance conversation content isn't captured by Anthropic's own tooling, so you log it yourself) |
| HIPAA (PHI) | Sending PHI to any route or log path not covered by a BAA for that exact configuration | Direct API/SDK on a BAA-covered configuration arranged with Anthropic (a dedicated HIPAA-enabled organisation); the BAA excludes Console, Workbench, beta features and consumer plans, and not every API feature is covered, so check the current eligibility list |
| GDPR / data residency | Routes where the execution region can't be pinned in code; defaulting to a global endpoint without a region | A cloud-mediated route (e.g. Bedrock or Vertex) with region pinned to a covered jurisdiction; the direct Anthropic API doesn't currently offer EU data residency |
| FedRAMP / government | Any code path hitting an endpoint not on an authorised environment at the required impact level, including dev/test paths hitting commercial endpoints (credentials and patterns leak) | Three authorised routes as of publication: Claude for Government (FedRAMP High via Palantir's service), Claude on Amazon Bedrock GovCloud (FedRAMP High and DoD IL4/5), and a third cloud route (detail truncated in my capture) |
| Internal data-residency policy | SDK clients against a cloud vendor outside the approved list | The route on the partner's already-approved cloud vendor; don't switch mid-project |
SOC 2 is out of scope here (it governs how systems are built and operated, not endpoint choice); Module 4 covers it, along with IAM and privacy patterns, prompt-injection defences, runtime guardrails and agent hardening.
