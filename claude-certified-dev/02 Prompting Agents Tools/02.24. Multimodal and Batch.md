# 02.24 Multimodal and Batch Ingestion: Teaching (about 13 min)

Source: Developer Module 2, screen 24 of 29. Title: "Images, PDFs, and high-volume processing".

## Framing
Earlier topics managed what Claude remembers between turns. Multimodal ingestion is about what you send in: every image and PDF uses context budget before Claude reads a character of your prompt. The second half covers the opposite problem: thousands of inputs, where one-at-a-time synchronous calls stop making sense and the Batches API takes over.

## Image token cost: calculate before you commit
- Images are processed in 28 x 28 pixel patches, one visual token each, so cost is ceil(width/28) x ceil(height/28). A 1,000 x 1,000 image is 36 x 36 = 1,296 tokens, roughly the same budget as a detailed system prompt per ten high-resolution screenshots.
- Each model has a maximum native resolution (a long-edge limit and a visual-token limit), which differs by tier; newer models accept larger images. Anything over either limit is downscaled first, so the formula applies to the scaled size. Limits have changed between generations: check the Vision docs ("Resolution and token cost") when you build.
- At design time, measure the token cost of a typical production image against the model's context limit before writing ingestion code. An over-budget pipeline is often fixed with a ten-minute resize step; discovering it after deployment takes longer.

## Three ways to send an image
| Method | How | Overhead | Best when |
|---|---|---|---|
| **Inline base64** | Encode the bytes as base64 and put them in the message block | The whole payload travels with every request (bigger requests, more latency on large images) | One-off images where an upload step isn't worth it; avoid if the same image is sent repeatedly |
| **URL reference** | Pass a public URL in the source block; Claude fetches it at request time | No payload, but the URL must be stable, public and reachable at that moment | Images already hosted at a stable public URL you control; skip anything behind auth, with a short-lived signature, or not guaranteed reachable |
| **Files API** | Upload once through a separate call, get a `file_id`, reference it in any later message | One-time upload; later requests carry only the ID, so payload overhead is near zero. Currently beta and not available on Bedrock or Vertex AI, so check your platform | The same image or PDF appears across requests or turns, or the asset is large; also cleanest when asset management should live apart from inference |

## PDFs: the document block
- The block type is `document` (not `image`). The `source` follows the same pattern: base64, URL, or a Files API `file_id`. For base64 you give `media_type: application/pdf` and the data.
- No `name` field is required. Optional `title` (a readable name) and optional `context` (extra metadata) exist. Token-cost and Files API reuse points apply as for images.

## Prompting multimodal inputs
The prompting techniques from 02.02 still apply: a bare "describe this image" gives shallow output for the same reason a bare text prompt does, because there's no target structure. Images add ambiguity that text doesn't (overlapping objects, depth and spatial relationships, partial occlusion), so the prompt should say how to handle each, e.g. "if objects overlap, describe each separately and note the overlap".

## Message Batches API
- For the same prompt pattern across hundreds or thousands of inputs, synchronous calls are the wrong model: each blocks, so you burn threads or hold thousands of concurrent connections against rate limits.
- A single batch accepts up to 100,000 requests or 256 MB, whichever is reached first. You submit it, receive a `batch_id`, poll for completion, then download results. Per-token cost is lower than synchronous.
- Trade-off: latency. Processing is non-deterministic and can take up to 24 hours, often much less. Suits offline pipelines, eval runs and data processing, not real-time interaction.
| Use case | Pattern | Why |
|---|---|---|
| A user uploads a photo and expects an immediate classification | Synchronous | Real-time response needed |
| Nightly pipeline classifying 5,000 customer records | Batches | No latency constraint; cheaper and async |
| Eval run testing a new prompt on 2,000 examples | Batches | Offline, no real-time need |
| Chatbot replying to a user's message | Synchronous | The user is waiting |

## When multimodal and batch fit together
Good fit: offline workloads that reuse the same assets and need structured output across thousands of inputs. The textbook case is a nightly pipeline classifying images against a fixed taxonomy: the Files API removes redundant uploads, Batches absorbs the latency, and structured-output techniques (02.02) keep results machine-readable. Two ways it breaks:
1. **Misreading latency:** using batch in any user-facing flow with an image passes tests and fails in production, because the user is waiting and the batch isn't.
2. **Underestimating context cost:** images and PDFs consume budget before any text is processed, so pipelines loading several large images per request blow past limits at scale. Measure on production-scale inputs first.
