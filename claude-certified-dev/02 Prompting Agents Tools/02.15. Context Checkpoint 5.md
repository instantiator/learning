# 02.15 Context Engineering: Checkpoint 5 (about 3 min)

Source: Developer Module 2, screen 15 of 29. Title: "Checkpoint 5: Diagnose the context failure". A multiple-choice exercise, not submitted; the answer below is the one 02.13 and 02.14 support.

## The scenario
A multi-turn agent run with degrading tool selection. You identify the turn that triggered the failure, name the mechanism, and choose a one-line fix. The trace:
- Turns 1 to 4: `fetch_policy_document`, correct each time, 2,400 tokens per result.
- Turn 5: `search_knowledge_base` chosen instead of `apply_coverage_rule` (wrong), 1,800 tokens.
- Turn 6: `search_knowledge_base` again (same wrong pick), 1,800 tokens.
- Turn 7: session ends without a result.

The course's hint on turn 4: it is the last correct turn, and four large results (9,600 tokens) now sit in the window, crowding out the instructions that tell Claude which tool to use next.

## Options and answer
- A. Add a clearer description to the `apply_coverage_rule` schema. (Not it: the schema wasn't the problem; selection was fine until the window filled.)
- **B. Prune `fetch_policy_document` results after each turn so accumulated outputs don't crowd out current instructions, and apply compaction before turn 5. (The fix.)**
- C. Raise `max_tokens` to give Claude more room to respond. (Not it: that limits output length and doesn't free input context.)

## Why
Mechanism: accumulated tool output crowding out the instructions (02.14). The trigger is turn 4 (or just after it), when the context became too full for the guidance to hold. The remedy is the context-budget toolkit from 02.13: prune used tool results, compact before the ceiling.
