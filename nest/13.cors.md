# 13. How CORS Is Managed (and When It Is Needed)

## What CORS is

CORS (**Cross-Origin Resource Sharing**) is a browser security mechanism. "Origin" means
the *scheme + host + port* of a page, e.g. `https://app.example.com` or
`http://localhost:3001`.

By default, a web page may only talk to servers on its **own origin**. A page served from
`http://localhost:3001` is not allowed to fetch from `http://localhost:3000` unless the
second server explicitly says it is OK. That permission is given via **response headers**
sent by the API server.

So: CORS is enforced by **browsers**, not by the server and not by the network. `curl`,
`Postman`, mobile apps and server-to-server calls are not affected at all — they have no
browser to enforce it.

## When you need to care

You need to configure CORS when a **browser-based client lives on a different origin than
your API**. The classic case: a React/Vue/Angular app served at `localhost:3001` calls your
NestJS API at `localhost:3000` during development. Without CORS, the browser blocks the
response and you see an error like:

```text
Access to fetch at 'http://localhost:3000/api/cats' from origin
'http://localhost:3001' has been blocked by CORS policy
```

You do **not** need CORS for:

- Same-origin requests (page and API share host/port).
- Server-to-server communication.
- Native mobile apps.
- `curl`/API clients.

## How it works (briefly)

For simple requests the browser adds an `Origin` header, and the API answers with
`Access-Control-Allow-Origin`. If the origin is allowed, the browser delivers the response
to the page.

For requests that can change state (custom headers like `Authorization`, methods other
than GET/POST with certain content types), the browser first sends a **preflight** `OPTIONS`
request asking "may I send this?" The server must answer with the allowed methods, headers
and origins. NestJS's `enableCors()` handles all of this for you.

## Enabling CORS in NestJS

Enable it in `main.ts`:

```typescript
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  app.enableCors({
    origin: 'http://localhost:3001',     // exactly one frontend origin
  });

  await app.listen(3000);
}
bootstrap();
```

## The common options

```typescript
app.enableCors({
  origin: ['http://localhost:3001', 'https://app.example.com'], // allow a list of origins
  methods: ['GET', 'POST', 'PUT', 'DELETE', 'PATCH'],           // HTTP verbs allowed
  allowedHeaders: ['Content-Type', 'Authorization'],            // headers the page may send
  credentials: true,                                            // allow cookies / auth headers
  exposedHeaders: ['X-Total-Count'],                            // response headers the page may read
  maxAge: 86400,                                                // how long the browser may cache preflight answers
});
```

| Option              | Purpose                                                |
| ------------------- | ------------------------------------------------------ |
| `origin`            | Which origins may call. String, array, or `true` (allow any). |
| `methods`           | Allowed HTTP methods.                                  |
| `allowedHeaders`    | Request headers the page may send (e.g. `Authorization`). |
| `credentials`       | Allow cookies / credentials. Must be `true` if your auth uses cookies. |
| `exposedHeaders`    | Response headers the page may *read* (they are otherwise hidden). |
| `maxAge`            | Seconds to cache preflight responses (fewer round trips). |

### The two common mistakes

1. **`origin: true`** allows *any* origin. Fine for a public API with no credentials; a
   bad default if your app has authentication — any website could then call your API from
   a browser. Be explicit about your frontend origins.
2. **`credentials: true` + `origin: '*'`.** Browsers refuse `*` when credentials are
   involved — you must name the origins explicitly. If you use cookie-based auth, list the
   actual frontend origin(s).

### Many origins at runtime

If the allowed list varies per environment, compute it from configuration (chapter 03), or
use a function form if you need dynamic decisions:

```typescript
app.enableCors({
  origin(origin, callback) {
    const allowed = ['https://app.example.com', 'https://admin.example.com'];
    if (!origin || allowed.includes(origin)) {
      callback(null, true);          // allow (null origin = non-browser client)
    } else {
      callback(new Error('Not allowed by CORS'), false);
    }
  },
});
```

## Where CORS is NOT applied

- NestJS CORS applies to **HTTP routes**. WebSockets have their own origin handling (see
  chapter 17).
- Server-Sent Events are subject to normal CORS rules (chapter 09).
- If you set a **global prefix** (`app.setGlobalPrefix('api')`), CORS still applies to the
  whole app — it does not care about paths.

## CORS + the other security middleware

Helmet (chapter 14) sets headers too, and middleware order matters. Register CORS and
helmet **before** any route definitions, so their headers are present on every response:

```typescript
app.use(helmet());                 // first
app.enableCors({ ... });           // then CORS
```

## Decision summary

| Situation                                 | CORS needed? |
| ----------------------------------------- | ------------ |
| Frontend on a different origin calls your API | Yes, allow that origin. |
| Same origin (page and API same host)      | No.          |
| Mobile app / curl / server-to-server      | No.          |
| Public API with no auth                   | Can allow all origins. |
| API with cookie-based auth                | Yes — named origins + `credentials: true`. |
