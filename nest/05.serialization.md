# 05. How Serialization Works

## What serialization is

Serialization is the process that runs **between your controller method returning a value
and that value being written to the HTTP response**. It decides what the client actually
sees.

The most common use is to hide data: a user entity loaded from the database contains a
`password` hash, but you must never send that to a client. Without a systematic approach,
you end up manually deleting fields all over your code — easy to forget, easy to get wrong.

NestJS solves this with a built-in piece called the `ClassSerializerInterceptor`, backed by
a package called `class-transformer`. It lets you express "what should the response look
like" as decorators on a class, in one place, and applies those rules everywhere.

## Install

```bash
npm install class-transformer class-validator
```

(`class-transformer` does the actual object transformation. `class-validator` is its
validation sibling and is often installed at the same time.)

## The basic idea

You decorate a class that represents "the data as it should be sent", then attach the
interceptor. When the interceptor sees your method return an *instance* of that class, it
applies the decorators.

### Exclude a property

```typescript
// users/user.entity.ts
import { Exclude } from 'class-transformer';

export class UserEntity {
  id: number;
  firstName: string;
  lastName: string;

  @Exclude()
  password: string;

  constructor(partial: Partial<UserEntity>) {
    Object.assign(this, partial);
  }
}
```

### Use it in a controller

```typescript
// users/users.controller.ts
import { Controller, Get, UseInterceptors, ClassSerializerInterceptor } from '@nestjs/common';
import { UserEntity } from './user.entity';

@Controller('users')
@UseInterceptors(ClassSerializerInterceptor)
export class UsersController {
  @Get(':id')
  findOne() {
    return new UserEntity({
      id: 1,
      firstName: 'John',
      lastName: 'Doe',
      password: 'supersecret',
    });
  }
}
```

A request to `GET /users/1` returns:

```json
{
  "id": 1,
  "firstName": "John",
  "lastName": "Doe"
}
```

No `password`. And because the rule lives on the entity class, **any** endpoint that
returns a `UserEntity` is protected automatically.

### Important detail: you must return class instances

The interceptor only works on instances of the class (or arrays of them). If you return a
plain object literal, the decorators are not applied:

```typescript
// This does NOT hide the password:
return { id: 1, firstName: 'John', lastName: 'Doe', password: 'supersecret' };
```

Two ways to fix this:

1. Construct the instance (as in the example above): `return new UserEntity({...})`.
2. Tell the interceptor which class to convert plain objects into, using
   `@SerializeOptions({ type: UserEntity })`:

```typescript
@UseInterceptors(ClassSerializerInterceptor)
@SerializeOptions({ type: UserEntity })
@Get(':id')
findOne() {
  return { id: 1, firstName: 'John', lastName: 'Doe', password: 'supersecret' }; // converted for you
}
```

The second option is convenient when you are returning plain data from a repository or
mapping service. Whichever you use, returning the class instance keeps things explicit and
is easy to follow.

## More decorators

### `@Expose()` — add or rename fields

A getter decorated with `@Expose()` becomes part of the response:

```typescript
export class UserEntity {
  firstName: string;
  lastName: string;

  @Expose()
  get fullName(): string {
    return `${this.firstName} ${this.lastName}`;
  }
}
```

`@Expose({ name: 'firstName' })` renames a property for the response.

### `@Transform()` — change a value

```typescript
import { Transform } from 'class-transformer';

@Transform(({ value }) => value.toUpperCase())
name: string;
```

The callback receives an object with the current `value`. A common pattern is to replace a
nested entity with just its id: `@Transform(({ value }) => value.id)`.

### `@SerializeOptions()` — change the rules

Per-controller or per-method overrides:

```typescript
@SerializeOptions({
  excludePrefixes: ['_'],   // hide every property starting with "_"
})
@Get()
findAll() {
  return this.users.findAll();
}
```

Other options include `strategy: 'exposeAll'` (send every property unless explicitly
hidden), `groups`, and `version`.

## Make it global

Instead of putting `@UseInterceptors(ClassSerializerInterceptor)` on every controller,
register it once:

```typescript
// app.module.ts
import { Module } from '@nestjs/common';
import { APP_INTERCEPTOR } from '@nestjs/core';
import { ClassSerializerInterceptor } from '@nestjs/common';

@Module({
  providers: [
    {
      provide: APP_INTERCEPTOR,
      useClass: ClassSerializerInterceptor,
    },
  ],
})
export class AppModule {}
```

Now the rules apply everywhere. Most production apps do this.

## Alternatives and where serialization does NOT apply

- The interceptor does **not** transform `StreamableFile` responses (streamed files), and
  it does not affect WebSocket or microservice responses in the same automatic way.
- For bigger jobs you can also just call `plainToInstance(...)` yourself wherever you need
  to transform data, without the interceptor.
- Note that this is *output* shaping. *Input* validation (checking what comes in) is the
  job of pipes and `class-validator` — a different feature, covered in the feature list in
  chapter 01.

## When to use it

Use serialization whenever a returned object is "too much for the client to see". The two
canonical cases:

- **Security**: stripping passwords, tokens, internal ids.
- **API shape**: flattening, renaming, or combining fields so clients get a clean contract
  that stays stable while your internals change.
