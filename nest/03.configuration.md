# 03. How Configuration Works

## The problem configuration solves

An application needs different settings in different environments:

- **Local development** uses your own database, your own API keys, port 3000.
- **Production** uses the real database, real keys, and a different port.
- **Tests** use a throwaway database.

If these values are hard-coded in your source code, you must edit and redeploy for every
environment. The standard solution (from the "12-factor app" methodology) is to put
settings in the **environment** — variables that live outside the code, supplied by the
operating system or by `.env` files.

When your code needs a value, it reads it from the environment instead of hard-coding it.

## How Node.js exposes environment variables

In Node.js, environment variables are available on a global object called `process.env`:

```typescript
process.env.DATABASE_HOST   // e.g. "localhost"
process.env.PORT            // e.g. "3000"
```

This works out of the box, but reading `process.env` directly is awkward:

- Everything is a string; you must convert types yourself (`parseInt`, `=== 'true'`).
- Nothing is validated; a missing variable silently becomes `undefined`.
- Testing and switching values is fiddly.

NestJS gives you a proper solution with the `@nestjs/config` package, which wraps a popular
tool called `dotenv`.

## Installing and enabling configuration

```bash
npm install @nestjs/config
```

Import `ConfigModule` in your root module. The `forRoot()` method loads a `.env` file from
the project root and makes its contents available through a `ConfigService`:

```typescript
// app.module.ts
import { Module } from '@nestjs/common';
import { ConfigModule } from '@nestjs/config';

@Module({
  imports: [ConfigModule.forRoot()],
})
export class AppModule {}
```

A typical `.env` file looks like this (plain text, one `KEY=VALUE` per line):

```text
DATABASE_HOST=localhost
DATABASE_PORT=5432
DATABASE_USER=app
DATABASE_PASSWORD=secret
JWT_SECRET=some-long-random-string
```

Two important behaviors:

- **Real environment variables win.** If a variable is already set in your shell
  (`export DATABASE_USER=...`), that value takes precedence over the `.env` file.
- **Values are strings.** `"5432"` is a string until you convert it.

### Making it global

By default each module must import `ConfigModule` to inject `ConfigService`. Most projects
just make it global so any module can use it:

```typescript
ConfigModule.forRoot({
  isGlobal: true,
});
```

## Reading values: the ConfigService

Inject `ConfigService` into any provider and read values with `get()`:

```typescript
import { Injectable } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';

@Injectable()
export class DatabaseService {
  constructor(private readonly configService: ConfigService) {
    const host = this.configService.get<string>('DATABASE_HOST');
    const port = this.configService.get<number>('DATABASE_PORT', 5432); // default if missing
  }
}
```

Key points:

- The type argument (`<string>`) is only a *hint* for TypeScript; the actual value is still
  a string from the environment. Convert real types in a helper function (see below).
- The second argument is a **default value**, used when the key is missing.
- Dot notation works for nested config objects: `get('database.host')`.

In `main.ts`, which is not part of any module, you can grab the service directly after the
app is created:

```typescript
const app = await NestFactory.create(AppModule);
const configService = app.get(ConfigService);
const port = configService.get('PORT');
await app.listen(port);
```

## Organising settings: namespaces and config files

Instead of sprinkling `get('SOME_VAR')` calls everywhere, group related settings into a
single typed configuration object. `registerAs` gives the group a name:

```typescript
// src/config/database.config.ts
import { registerAs } from '@nestjs/config';

export default registerAs('database', () => ({
  host: process.env.DATABASE_HOST || 'localhost',
  port: parseInt(process.env.DATABASE_PORT ?? '5432', 10),
}));
```

Load it in the root module:

```typescript
import databaseConfig from './config/database.config';

@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,
      load: [databaseConfig],
    }),
  ],
})
export class AppModule {}
```

Now read it in two ways. Either by key:

```typescript
const host = this.configService.get<string>('database.host');
```

Or — better, because it is strongly typed — by injecting the whole namespace:

```typescript
import { ConfigType } from '@nestjs/config';
import databaseConfig from '../config/database.config';

@Injectable()
export class DatabaseService {
  constructor(
    @Inject(databaseConfig.KEY)
    private readonly dbConfig: ConfigType<typeof databaseConfig>,
  ) {}

  someMethod() {
    const port = this.dbConfig.port; // already a number
  }
}
```

The `load` option accepts an array, so you can have one config file per concern: database,
auth, redis, and so on.

## Validating configuration at startup

It is much better to fail fast at startup than to crash randomly later with a missing
variable. `@nestjs/config` supports two styles.

### Style 1: a Joi schema

Install Joi (`npm install joi`), then describe what the environment must contain:

```typescript
import * as Joi from 'joi';

ConfigModule.forRoot({
  validationSchema: Joi.object({
    NODE_ENV: Joi.string().valid('development', 'production', 'test').default('development'),
    PORT: Joi.number().default(3000),
    DATABASE_PASSWORD: Joi.string().required(),
  }),
});
```

If `DATABASE_PASSWORD` is missing, the application refuses to start and prints why.

### Style 2: a custom validate function

If you prefer the `class-validator` style used elsewhere in NestJS:

```typescript
import { plainToInstance } from 'class-transformer';
import { IsNumber, IsString, validateSync } from 'class-validator';

class EnvironmentVariables {
  @IsNumber()
  PORT: number;

  @IsString()
  DATABASE_PASSWORD: string;
}

export function validate(config: Record<string, unknown>) {
  const validated = plainToInstance(EnvironmentVariables, config, {
    enableImplicitConversion: true,
  });
  const errors = validateSync(validated, { skipMissingProperties: false });
  if (errors.length > 0) {
    throw new Error(errors.toString());
  }
  return validated;
}
```

Then wire it up:

```typescript
ConfigModule.forRoot({
  validate,
});
```

A useful side effect of the `validate` approach: with `enableImplicitConversion` your
values come back with real types (numbers, booleans) instead of strings.

## Handy extras

| Option               | What it does                                                                  |
| -------------------- | ----------------------------------------------------------------------------- |
| `envFilePath`        | Path to the `.env` file (or an array of paths). Default: `.env` in the root.  |
| `ignoreEnvFile`      | `true` = only use real environment variables, skip `.env` files.              |
| `expandVariables`    | `true` = one env var can reference another: `APP_URL=example.com`, `SUPPORT_EMAIL=support@${APP_URL}`. |
| `cache`              | `true` = remember resolved values for faster repeated `get()` calls.          |
| `skipProcessEnv`     | `true` = only read from your custom config files, ignore `process.env`.       |

### Conditional modules

Load a module only when an environment variable says so:

```typescript
import { ConditionalModule } from '@nestjs/config';

@Module({
  imports: [
    ConfigModule.forRoot(),
    ConditionalModule.registerWhen(SentimentModule, 'SENTIMENT_ENABLED'),
  ],
})
export class AppModule {}
```

### A note on secrets

`.env` files belong in `.gitignore`. Do not commit real keys. In production, prefer
providing real environment variables directly to the process (from your hosting platform's
secret store) rather than committing a `.env` file.

## Recommended layout for a real project

```text
src/
├── main.ts
├── app.module.ts
└── config/
    ├── configuration.ts        # base configuration (optional)
    ├── database.config.ts      # registerAs('database', ...)
    ├── auth.config.ts          # registerAs('auth', ...)
    └── redis.config.ts         # registerAs('redis', ...)
.env                            # not committed
.env.example                    # committed; documents which keys are needed
```

The `.env.example` file is a convention: it lists every variable the app needs with dummy
values, so a new developer can copy it to `.env` and fill in real values.
