# 12. How to Set Up Authorization

## Authorization vs authentication

Authentication (previous chapter) answers *who are you?* Authorization answers *may you
do this?* The auth guard runs first and puts the identity on the request; an
**authorization** guard runs next and checks permissions.

Two standard models:

- **RBAC (role-based access control)** — users have roles (`admin`, `user`, `guest`).
  Roles are checked against route requirements. Simple and widely used.
- **ABAC (attribute-based access control)** — decisions come from *attributes* of the
  user, the resource, and the context ("only the owner of a post may edit it", "only
  during business hours"). More flexible, more code.

## The core mechanism: a guard that reads metadata

NestJS lets you attach metadata to routes with `SetMetadata`, and a guard can read it with
the `Reflector`. That is the whole trick behind `@Roles('admin')` style decorators.

### Step 1: a `@Roles()` decorator

```typescript
// common/roles.decorator.ts
import { SetMetadata } from '@nestjs/common';

export const ROLES_KEY = 'roles';
export const Roles = (...roles: string[]) => SetMetadata(ROLES_KEY, roles);
```

### Step 2: a `RolesGuard`

```typescript
// common/roles.guard.ts
import { CanActivate, ExecutionContext, Injectable, ForbiddenException } from '@nestjs/common';
import { Reflector } from '@nestjs/core';

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const requiredRoles = this.reflector.getAllAndOverride<string[]>(ROLES_KEY, [
      context.getHandler(),
      context.getClass(),
    ]);

    // No @Roles() on the route -> no restriction.
    if (!requiredRoles || requiredRoles.length === 0) return true;

    const { user } = context.switchToHttp().getRequest();
    if (!user) throw new ForbiddenException();

    // user.roles must exist from authentication (e.g. inside the JWT payload)
    const ok = requiredRoles.some((role) => user.roles?.includes(role));
    if (!ok) throw new ForbiddenException();
    return true;
  }
}
```

### Step 3: use it

```typescript
import { Controller, Post, UseGuards } from '@nestjs/common';
import { Roles } from '../common/roles.decorator';
import { RolesGuard } from '../common/roles.guard';

@Controller('admin')
@UseGuards(RolesGuard)          // attach the guard
export class AdminController {
  @Post('users')
  @Roles('admin')               // require the admin role
  createUser() {
    // only admins reach this
  }
}
```

Roles usually live in the JWT payload (`{ sub, username, roles: ['admin'] }`), or are
loaded from the database in a passport strategy's `validate()`.

## Ownership checks (attribute-based)

Role checks are not enough for "a user may only edit their own profile". That decision
needs the resource, so do it in the service with the identity from `req.user`:

```typescript
@UseGuards(AuthGuard)   // any authenticated user
@Delete('posts/:id')
async deletePost(@Param('id') id: string, @Request() req) {
  const post = await this.postsService.findOne(id);
  if (post.authorId !== req.user.sub) {
    throw new ForbiddenException('Not your post');
  }
  await this.postsService.remove(id);
}
```

For larger applications, encode these rules so they are testable rather than scattered in
handlers. A lightweight approach is a small policy helper:

```typescript
// common/policies.ts
export function canDeletePost(user: { sub: number; roles: string[] }, post: { authorId: number }) {
  return user.roles.includes('admin') || post.authorId === user.sub;
}
```

For complex rule sets, teams adopt the **CASL** library (`@casl/ability`), which
formalizes "this actor can perform this action on this subject" and nests cleanly with
NestJS. It is worth looking at once you have more than a handful of rules.

## Chaining guards and ordering

Guards run in the order they are attached — and order matters:

```typescript
@UseGuards(AuthGuard, RolesGuard)   // Auth first, Roles second
```

The auth guard must run first, because the roles guard reads `req.user`. The same ordering
applies when guards are registered globally (`APP_GUARD`) — NestJS runs them in provider
registration order, so register `AuthGuard` before `RolesGuard`.

## Where to apply authorization

| Level           | How                                                          |
| --------------- | ------------------------------------------------------------ |
| Whole app       | Register guards via `APP_GUARD` (but then you need `@Public()` handling, see chapter 11). |
| A controller    | `@UseGuards(Guard)` on the class.                            |
| A route         | `@UseGuards(Guard)` on the method — combines with the class-level guard. |
| Inside logic    | Ownership checks in services (the example above).            |

## A practical authorization checklist

1. **Never trust the client.** Every check reads `req.user`, which only your auth layer
   populated — not anything the browser sent.
2. **Fail closed.** Deny by default; only the explicitly allowed path passes. (NestJS
   guards throw by default, which gives you this.)
3. **403 vs 401.** 401 = "I don't know who you are" (auth). 403 = "I know who you are but
   this is not allowed" (authorization). Use `ForbiddenException` for the latter.
4. **Check both roles and ownership** where both apply (admin *or* owner).
5. **Keep authorization rules near the code they protect**, and write tests for them — this
   is security logic, not incidental detail.
