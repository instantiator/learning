# 16. How to Implement Rate Limiting

## What rate limiting is for

Rate limiting caps how many requests a single client may make in a time window. It
protects your API against:

- **Brute-force attacks** — an attacker hammering a login endpoint with password guesses.
- **Denial of service** — one client (or a botnet) flooding your server.
- **Abuse** — scrapers or misbehaving clients burning your resources.

The server counts requests per client (usually per IP address) and rejects requests beyond
the limit with **HTTP 429 Too Many Requests**.

NestJS's official package is `@nestjs/throttler`.

## Install and configure

```bash
npm install @nestjs/throttler
```

Register the module in your root module. Note that `ttl` is in **milliseconds** in the
current version:

```typescript
// app.module.ts
import { Module } from '@nestjs/common';
import { ThrottlerModule } from '@nestjs/throttler';

@Module({
  imports: [
    ThrottlerModule.forRoot({
      throttlers: [
        {
          ttl: 60_000,    // window = 60 seconds
          limit: 100,     // a client may send at most 100 requests per window
        },
      ],
    }),
  ],
})
export class AppModule {}
```

There is a `seconds()` helper if you prefer reading times in seconds:
`ttl: seconds(60)`.

## Enabling the guard

The module only *defines* the rules; the `ThrottlerGuard` enforces them. Register it
globally:

```typescript
// app.module.ts
import { APP_GUARD } from '@nestjs/core';
import { ThrottlerGuard, ThrottlerModule } from '@nestjs/throttler';

@Module({
  imports: [
    ThrottlerModule.forRoot({
      throttlers: [{ ttl: 60_000, limit: 100 }],
    }),
  ],
  providers: [
    {
      provide: APP_GUARD,       // apply to every route
      useClass: ThrottlerGuard,
    },
  ],
})
export class AppModule {}
```

Alternatively attach it per controller or per route with `@UseGuards(ThrottlerGuard)`.
Global is the usual choice, so no route is accidentally left unprotected.

## Adjusting limits per route

`@Throttle()` overrides the default limits for one route or whole controller:

```typescript
import { Controller, Get } from '@nestjs/common';
import { Throttle } from '@nestjs/throttler';

@Controller('auth')
export class AuthController {
  // Strict limit for the login endpoint (brute-force target):
  @Throttle({ default: { limit: 5, ttl: 60_000 } })
  @Post('login')
  login() {
    // ...
  }
}
```

### Skipping rate limiting

`@SkipThrottle()` turns it off for a class or method. Useful for health checks or
webhooks that legitimately receive bursts:

```typescript
@SkipThrottle()               // skip everything in this controller
@Controller('health')
export class HealthController {
  @Get()
  check() {
    return { status: 'ok' };
  }
}
```

To skip most of a controller but re-enable one route:

```typescript
@SkipThrottle()
@Controller('users')
export class UsersController {
  @SkipThrottle({ default: false })   // re-enable for this route
  @Get()
  findAll() {
    // ...
  }
}
```

### Several windows at once (named throttlers)

Different rules for different windows: at most 3 requests per second **and** 100 per
minute. Give each rule a name and refer to it in the decorators:

```typescript
ThrottlerModule.forRoot({
  throttlers: [
    { name: 'short',  ttl: 1000,   limit: 3 },
    { name: 'medium', ttl: 10_000, limit: 20 },
    { name: 'long',   ttl: 60_000, limit: 100 },
  ],
});
```

```typescript
@Throttle({ short: { limit: 1, ttl: 1000 } })
@Get('expensive')
expensive() {
  // at most 1 per second for this route
}
```

## Running behind a proxy / load balancer

This matters and is easy to get wrong. In production your API usually sits behind a proxy
(Nginx, a load balancer, a cloud gateway). The proxy makes the request, so `req.ip` is the
proxy's address — every user would share one IP and share one limit.

Two fixes, both needed:

1. **Trust the proxy** so Express reads the real client IP from the `X-Forwarded-For`
   header:

   ```typescript
   // main.ts
   const app = await NestFactory.create<NestExpressApplication>(AppModule);
   app.set('trust proxy', 'loopback');   // trust requests arriving from the proxy
   ```

2. **Tell ThrottlerGuard which value to count** by subclassing it:

   ```typescript
   // throttler-behind-proxy.guard.ts
   import { Injectable } from '@nestjs/common';
   import { ThrottlerGuard } from '@nestjs/throttler';

   @Injectable()
   export class ThrottlerBehindProxyGuard extends ThrottlerGuard {
     protected async getTracker(req: Record<string, any>): Promise<string> {
       return req.ips?.length ? req.ips[0] : req.ip;  // first forwarded IP
     }
   }
   ```

   Then register `ThrottlerBehindProxyGuard` instead of `ThrottlerGuard` via `APP_GUARD`.

## Storage: making it work across instances

The default storage is **in-memory**: each app instance counts its own requests. If you
run several copies behind a load balancer, each instance lets its own 100 requests
through — an attacker gets 100 × number-of-instances. For distributed deployments, plug in
a shared store such as Redis so all instances share one counter. The community provides a
Redis storage for throttler (e.g. `throttler-storage-redis`), implementing the
`ThrottlerStorage` interface:

```typescript
ThrottlerModule.forRootAsync({
  inject: [ConfigService],
  useFactory: (config: ConfigService) => ({
    throttlers: [{ ttl: 60_000, limit: 100 }],
    storage: new ThrottlerStorageRedis({
      host: config.get('REDIS_HOST'),
      port: config.get('REDIS_PORT'),
    }),
  }),
});
```

(Check the package's docs for the exact class and options — the interface is stable, so any
storage implementing `ThrottlerStorage` works.)

## Options quick reference

| Option                | Meaning                                              |
| --------------------- | ---------------------------------------------------- |
| `name`                | Identifier for the rule set (default `default`).     |
| `ttl`                 | Window length in **milliseconds**.                   |
| `limit`               | Max requests per window.                             |
| `blockDuration`       | Extra time to block a client that exceeded the limit.|
| `ignoreUserAgents`    | Regexes of user-agents to never count (e.g. monitoring bots). |
| `skipIf`              | A function; return true to skip counting for a request. |
| `storage`             | Where counters live (default: in-memory).            |
| `errorMessage`        | Custom 429 response message.                         |

## Config from environment

Use `forRootAsync` so limits come from config (handy: stricter in production than dev):

```typescript
ThrottlerModule.forRootAsync({
  imports: [ConfigModule],
  inject: [ConfigService],
  useFactory: (config: ConfigService) => ({
    throttlers: [
      {
        ttl: config.get('THROTTLE_TTL_MS', 60_000),
        limit: config.get('THROTTLE_LIMIT', 100),
      },
    ],
  }),
});
```

## Practical tuning advice

- Set generous global defaults (protects the whole API) and **tighten specific
  sensitive routes** with `@Throttle` — login, password reset, registration.
- Watch real traffic before finalising numbers; limits that are too tight break real users
  (and your own frontend's many parallel requests).
- Remember the proxy issue, or your limits will either do nothing or hit everyone at once.
- The guard works with WebSockets and GraphQL too, but needs small extensions — see the
  official docs for the gateway/GraphQL guard snippets if you use those transports.
