# 04. How Databases Are Commonly Used

NestJS does not have one "official" database. Instead it gives you first-class integration
for the ORM/ODM libraries the Node ecosystem already uses, plus providers for almost any
other driver. This chapter shows the three most common approaches:

1. **TypeORM** — the most popular ORM for relational (SQL) databases.
2. **Prisma** — a modern ORM with a schema file and type-safe queries.
3. **Mongoose** — the standard ODM for MongoDB (document database).

Two concepts first:

- **ORM** (object-relational mapper) lets you treat database tables as TypeScript classes.
  You write `userRepository.findOne(...)` instead of raw SQL. TypeORM and Prisma are ORMs.
- **ODM** (object-document mapper) is the equivalent idea for document databases like
  MongoDB. Mongoose is an ODM.

## Connecting the database

Regardless of the library, the pattern is the same: a database module in `app.module.ts`
holds the connection settings (usually read from `ConfigService`), and each feature module
registers the models/entities it uses.

Because connection settings come from configuration, the two modules always appear
together. That is why chapter 03 (configuration) came first.

## 1. TypeORM (SQL: PostgreSQL, MySQL, SQLite, ...)

### Install

```bash
npm install @nestjs/typeorm typeorm
npm install pg                    # PostgreSQL driver
# or: npm install mysql2          # MySQL
# or: npm install better-sqlite3 # SQLite (great for local dev / tests)
```

### Connect in the root module

```typescript
// app.module.ts
import { Module } from '@nestjs/common';
import { TypeOrmModule } from '@nestjs/typeorm';
import { ConfigModule, ConfigService } from '@nestjs/config';

@Module({
  imports: [
    ConfigModule.forRoot({ isGlobal: true }),
    TypeOrmModule.forRootAsync({
      inject: [ConfigService],
      useFactory: (config: ConfigService) => ({
        type: 'postgres',                         // or 'mysql', 'sqlite', ...
        host: config.get('DATABASE_HOST', 'localhost'),
        port: config.get('DATABASE_PORT', 5432),
        username: config.get('DATABASE_USER'),
        password: config.get('DATABASE_PASSWORD'),
        database: config.get('DATABASE_NAME'),
        autoLoadEntities: true,                   // entities registered in feature modules are picked up automatically
        synchronize: true,                        // dev only: creates/updates tables from entities
      }),
    }),
  ],
})
export class AppModule {}
```

Important warning: `synchronize: true` changes your schema automatically on every start.
That is convenient in development but destructive in production. Use migrations there.

### Define an entity

An entity is a class decorated with `@Entity()`. Each property maps to a column.

```typescript
// cats/cat.entity.ts
import { Entity, PrimaryGeneratedColumn, Column } from 'typeorm';

@Entity()
export class Cat {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  name: string;

  @Column()
  age: number;
}
```

### Use repositories in a service

Register the entity inside its feature module, then inject a "repository" (a TypeORM
object that wraps the table).

```typescript
// cats/cats.module.ts
import { Module } from '@nestjs/common';
import { TypeOrmModule } from '@nestjs/typeorm';
import { Cat } from './cat.entity';
import { CatsService } from './cats.service';
import { CatsController } from './cats.controller';

@Module({
  imports: [TypeOrmModule.forFeature([Cat])],
  providers: [CatsService],
  controllers: [CatsController],
})
export class CatsModule {}
```

```typescript
// cats/cats.service.ts
import { Injectable } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { Cat } from './cat.entity';

@Injectable()
export class CatsService {
  constructor(
    @InjectRepository(Cat)
    private readonly cats: Repository<Cat>,
  ) {}

  findAll() {
    return this.cats.find();
  }

  create(data: Partial<Cat>) {
    const cat = this.cats.create(data);
    return this.cats.save(cat);
  }

  remove(id: number) {
    return this.cats.delete(id);
  }
}
```

The repository gives you `find`, `findOne`, `save`, `update`, `delete`, plus filtering
options like `{ where: { age: 2 } }` and relations (`relations: ['owner']`).

### Migrations

A migration is a versioned change to the schema (create table, add column, ...) that you
apply deliberately. TypeORM generates them from your entities:

```bash
npm run build
npx typeorm migration:generate src/migrations/AddAgeColumn --dataSource src/data-source.ts
npx typeorm migration:run --dataSource src/data-source.ts
```

Because `synchronize` is dangerous in production, teams turn it off and use migrations.

### Transactions

When several writes must happen together (all succeed or none do), wrap them in a
transaction:

```typescript
import { DataSource } from 'typeorm';

constructor(private readonly dataSource: DataSource) {}

async transfer(fromId: number, toId: number, amount: number) {
  await this.dataSource.transaction(async (manager) => {
    await manager.decrement(BankAccount, { id: fromId }, 'balance', amount);
    await manager.increment(BankAccount, { id: toId }, 'balance', amount);
  });
}
```

## 2. Prisma

Prisma is an alternative ORM that generates plain TypeScript query functions from a schema
file. Many teams prefer it for its type safety. There is no official `@nestjs/prisma`
module; the standard pattern is a small `PrismaService` provider.

### Install and initialize

```bash
npm install @prisma/client
npm install -D prisma
npx prisma init
```

`npx prisma init` creates `prisma/schema.prisma` and a `.env` with `DATABASE_URL`.

### Define the schema

```prisma
// prisma/schema.prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"   // or "mysql", "sqlite", ...
  url      = env("DATABASE_URL")
}

model Cat {
  id   Int    @id @default(autoincrement())
  name String
  age  Int
}
```

Generate the client (creates typed functions + the PrismaClient class):

```bash
npx prisma generate
npx prisma migrate dev --name init   # creates the tables
```

### The PrismaService

```typescript
// prisma/prisma.service.ts
import { Injectable, OnModuleDestroy, OnModuleInit } from '@nestjs/common';
import { PrismaClient } from '@prisma/client';

@Injectable()
export class PrismaService extends PrismaClient implements OnModuleInit, OnModuleDestroy {
  async onModuleInit() {
    await this.$connect();
  }

  async onModuleDestroy() {
    await this.$disconnect();
  }
}
```

Make it globally available so every feature module can inject it:

```typescript
// prisma/prisma.module.ts
import { Global, Module } from '@nestjs/common';
import { PrismaService } from './prisma.service';

@Global()
@Module({
  providers: [PrismaService],
  exports: [PrismaService],
})
export class PrismaModule {}
```

Import `PrismaModule` once in `AppModule` and use it anywhere:

```typescript
// cats/cats.service.ts
import { Injectable } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service';

@Injectable()
export class CatsService {
  constructor(private readonly prisma: PrismaService) {}

  findAll() {
    return this.prisma.cat.findMany();
  }

  create(data: { name: string; age: number }) {
    return this.prisma.cat.create({ data });
  }
}
```

Prisma queries are fully typed: `this.prisma.cat` exists only because the schema has a
`Cat` model, and the compiler checks your fields. Schema changes require a `npx prisma
generate` (and usually a migration) to reflect in the generated client.

## 3. Mongoose (MongoDB)

### Install

```bash
npm install @nestjs/mongoose mongoose
```

### Connect and define a schema

```typescript
// app.module.ts
import { Module } from '@nestjs/common';
import { MongooseModule } from '@nestjs/mongoose';

@Module({
  imports: [MongooseModule.forRoot('mongodb://localhost/nest')],
})
export class AppModule {}
```

MongoDB does not enforce a fixed table shape, so you describe the shape yourself with a
**schema**, and use an **interface** as the TypeScript type:

```typescript
// cats/cat.schema.ts
import { Prop, Schema, SchemaFactory } from '@nestjs/mongoose';
import { HydratedDocument } from 'mongoose';

export type CatDocument = HydratedDocument<Cat>;

@Schema()
export class Cat {
  @Prop()
  name: string;

  @Prop()
  age: number;
}

export const CatSchema = SchemaFactory.createForClass(Cat);
```

```typescript
// cats/cats.module.ts
import { Module } from '@nestjs/common';
import { MongooseModule } from '@nestjs/mongoose';
import { Cat, CatSchema } from './cat.schema';
import { CatsService } from './cats.service';
import { CatsController } from './cats.controller';

@Module({
  imports: [MongooseModule.forFeature([{ name: Cat.name, schema: CatSchema }])],
  providers: [CatsService],
  controllers: [CatsController],
})
export class CatsModule {}
```

Inject a **model** and use its methods:

```typescript
// cats/cats.service.ts
import { Injectable } from '@nestjs/common';
import { InjectModel } from '@nestjs/mongoose';
import { Model } from 'mongoose';
import { Cat, CatDocument } from './cat.schema';

@Injectable()
export class CatsService {
  constructor(@InjectModel(Cat.name) private readonly catModel: Model<CatDocument>) {}

  findAll() {
    return this.catModel.find().exec();
  }

  create(data: Partial<Cat>) {
    const cat = new this.catModel(data);
    return cat.save();
  }
}
```

## Which one to choose?

| Need                                  | Recommendation        |
| ------------------------------------- | --------------------- |
| Relational data, teams new to ORMs    | TypeORM (tutorials everywhere) |
| Maximum type safety, prefer schema-first | Prisma                |
| MongoDB / document data               | Mongoose              |
| Raw SQL without an ORM                | `@nestjs/typeorm` is overkill; use `pg`/`mysql2` directly, or `Knex.js` |

A reasonable default: **TypeORM for SQL, Mongoose for MongoDB** — both are the officially
documented integrations. Prisma is the popular third option if you value compile-time
checking of your queries.

## Patterns that apply to all of them

- **Register the connection once in the root module**, and register per-feature
  models/entities in their own modules. This keeps modules self-contained.
- **Take connection settings from `ConfigService`** (`forRootAsync`/`useFactory`), never
  hard-code them.
- **One repository/model per feature module**, injected into services, never used directly
  from controllers.
- **Test against the real thing or SQLite in memory**; for unit tests, mock the repository
  or model so you never touch a real database.
