# 10. Task Scheduling and Long-Running Background Tasks

## Two different problems

"Background work" splits into two ideas that are easy to confuse:

1. **Scheduled work** — run some code *at a point in time*: every night at 2am, every 10
   minutes, on the 1st of each month. This is **cron scheduling**.
2. **Long-running work** — a single job that takes a long time (send 10,000 emails, render
   a video). This is usually better handled by a **queue** (see chapter 08).

NestJS has an official package for scheduling: `@nestjs/schedule`. For long-running work,
the recommendation from chapter 08 stands: offload it to a queue so your HTTP server stays
responsive and the work survives restarts.

## Installing the scheduler

```bash
npm install @nestjs/schedule
```

Enable it once in the root module:

```typescript
// app.module.ts
import { Module } from '@nestjs/common';
import { ScheduleModule } from '@nestjs/schedule';

@Module({
  imports: [ScheduleModule.forRoot()],
})
export class AppModule {}
```

## Cron jobs: `@Cron`

A cron expression is a compact way of describing a time pattern:
`second minute hour day month weekday`. NestJS provides named presets and raw expressions.

```typescript
import { Injectable } from '@nestjs/common';
import { Cron, CronExpression } from '@nestjs/schedule';

@Injectable()
export class ReportsService {
  @Cron(CronExpression.EVERY_DAY_AT_2AM)
  generateDailyReport() {
    // runs every day at 02:00
  }

  @Cron('0 0 1 * *') // midnight on the 1st of every month
  generateMonthlyReport() {
    // ...
  }
}
```

Common presets:

| Constant                     | Meaning                       |
| ---------------------------- | ----------------------------- |
| `EVERY_SECOND`               | every second                  |
| `EVERY_10_SECONDS`           | every 10 seconds              |
| `EVERY_MINUTE`               | every minute                  |
| `EVERY_HOUR`                 | every hour                    |
| `EVERY_DAY_AT_2AM`           | daily at 02:00                |
| `EVERY_WEEKEND`              | Saturday and Sunday           |
| `EVERY_5_MINUTES`            | every 5 minutes               |

Raw expressions give full control (`minute hour day month weekday` — five fields; adding a
leading field makes it six with seconds). Use a generator tool until the syntax is
familiar.

## Intervals and timeouts

For simple "every N ms" or "once after N ms", there is no need for cron syntax:

```typescript
import { Injectable } from '@nestjs/common';
import { Interval, Timeout } from '@nestjs/schedule';

@Injectable()
export class HealthService {
  @Interval(10_000)          // run every 10 seconds
  heartbeat() {
    // ping something
  }

  @Timeout(5_000)            // run once, 5 seconds after startup
  warmUp() {
    // preload caches
  }
}
```

The method names (`heartbeat`, `warmUp`) become the job names you can reference later.

## Managing jobs at runtime: SchedulerRegistry

If jobs need to be added, started, stopped or deleted while the app is running (e.g. per
user or per tenant), use `SchedulerRegistry`:

```typescript
import { Injectable, OnApplicationBootstrap } from '@nestjs/common';
import { SchedulerRegistry } from '@nestjs/schedule';
import { CronJob } from 'cron';

@Injectable()
export class DynamicJobsService implements OnApplicationBootstrap {
  constructor(private readonly schedulerRegistry: SchedulerRegistry) {}

  onApplicationBootstrap() {
    const job = new CronJob('0 */5 * * * *', () => this.syncTenant());
    this.schedulerRegistry.addCronJob('tenant-sync', job);
    job.start();
  }

  stopSync() {
    this.schedulerRegistry.deleteCronJob('tenant-sync');
  }
}
```

The same registry exposes `getCronJob`, `getInterval`, `getTimeout`, and `getCronJobs` for
inspection and control.

## Scheduling with the correct timezone

Cron jobs run in the server's local timezone by default. If your server is UTC but your
business is elsewhere, pass `timeZone`:

```typescript
@Cron(CronExpression.EVERY_DAY_AT_2AM, {
  timeZone: 'Europe/London',
})
generateDailyReport() {}
```

## Long-running background tasks

### The rule

**Long-running work does not belong in the request path.** When a client calls your API,
respond quickly and let something else do the heavy lifting. Options, in order of
preference:

1. **A queue** (`@nestjs/bullmq`, chapter 08) — reliable, retryable, scalable, survives
   restarts. This is the right tool for real long-running tasks.
2. **The scheduler** — when the work is on a schedule rather than triggered by a request.
3. **A plain async fire-and-forget** — only for trivial work you are happy to lose.

If you have a genuinely long task triggered by a user action, the pattern is:

```text
POST /export
   -> enqueue a job              (fast, returns a job id)
   -> worker processes the job   (slow, does the export)
   -> client polls or gets an SSE event when it is done   (see chapter 09)
```

### Startup and shutdown hooks

NestJS gives you lifecycle hooks for when your app starts and stops. Use them to start
background loops and to clean them up so the process can exit cleanly:

```typescript
import { Injectable, OnApplicationShutdown, OnModuleInit } from '@nestjs/common';

@Injectable()
export class CleanupService implements OnModuleInit, OnApplicationShutdown {
  private timer: NodeJS.Timeout | undefined;

  onModuleInit() {
    this.timer = setInterval(() => this.removeStaleSessions(), 60_000);
  }

  onApplicationShutdown() {
    if (this.timer) clearInterval(this.timer);
  }
}
```

Enable graceful shutdown in `main.ts` so this hook actually runs on Ctrl-C or a termination
signal:

```typescript
const app = await NestFactory.create(AppModule);
app.enableShutdownHooks();   // catches SIGTERM/SIGINT and runs shutdown hooks
```

### The classic mistake: multiple instances

If you deploy **more than one copy** of your app (very common), every copy runs your
`@Cron`/`@Interval` jobs — so the report is generated N times. Options:

- Run scheduled jobs only on a dedicated "worker" instance.
- Add a distributed lock (via Redis) so only one instance wins.
- Use BullMQ's delayed jobs for scheduled work: schedule a job to the queue, and only one
  worker processes it.

## Decision summary

| Task                                     | Tool                      |
| ---------------------------------------- | ------------------------- |
| Run every day / every hour / on a pattern| `@nestjs/schedule` (cron) |
| Run every N ms (in-process)              | `@Interval`               |
| Run once after startup                   | `@Timeout`                |
| Add/remove jobs at runtime               | `SchedulerRegistry`       |
| Heavy work triggered by a request        | Queue (chapter 08)        |
| Cleanup on shutdown                      | `enableShutdownHooks` + hooks |
