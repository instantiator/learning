# 14. What Helmet Is For

## The problem

HTTP responses can include headers that tell the browser how to behave. By default, most
web frameworks send very few of them, which leaves the door open to a family of common
attacks:

- **Clickjacking** — a malicious page embeds your site in a hidden `<iframe>` and tricks
  users into clicking your buttons. Prevented by `X-Frame-Options`.
- **Cross-site scripting (XSS)** — if your site reflects user input into HTML, attackers
  can run their own scripts. The Content Security Policy header restricts what scripts may
  run.
- **MIME sniffing** — browsers sometimes guess a file's type; `X-Content-Type-Options`
  forces them to respect the declared type.
- **Protocol downgrade** — browsers that were once on HTTPS may fall back to plain HTTP;
  HSTS tells them never to.

Fixing each of these with the right header, for every response, is exactly the kind of
thing people forget. **Helmet** is a package that bundles ~15 security headers into one
small middleware call.

## What Helmet sets

Just a selection of the headers Helmet adds:

| Header                          | Defends against                  |
| ------------------------------- | -------------------------------- |
| `Content-Security-Policy`       | XSS / injection                  |
| `X-Frame-Options`               | Clickjacking                     |
| `X-Content-Type-Options`        | MIME sniffing                    |
| `Strict-Transport-Security` (HSTS) | HTTPS downgrade attacks       |
| `Referrer-Policy`               | Leaking URLs in the `Referer` header |
| `X-DNS-Prefetch-Control`        | Privacy (DNS prefetching)        |
| `Cross-Origin-Opener-Policy`, `Cross-Origin-Embedder-Policy` | Cross-origin isolation attacks |
| `X-Permitted-Cross-Domain-Policies` | Flash/PDF cross-domain policies |

You rarely need to understand each one in depth — the defaults are sensible. The one you
will interact with is the Content Security Policy, because it can **block legitimate
scripts** if your app loads resources from external domains (see "when to customise"
below).

## Using Helmet with NestJS (Express, the default)

```bash
npm install helmet
```

Apply it as global middleware in `main.ts`:

```typescript
import { NestFactory } from '@nestjs/core';
import helmet from 'helmet';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  app.use(helmet());   // all default headers, on every response

  await app.listen(3000);
}
bootstrap();
```

Verify it worked:

```bash
curl -I http://localhost:3000/
```

You should see headers like `X-Frame-Options: SAMEORIGIN` and
`Content-Security-Policy: default-src 'self'` in the output.

## Using Helmet with Fastify

Fastify plugins are registered, not used as middleware:

```bash
npm install @fastify/helmet
```

```typescript
import helmet from '@fastify/helmet';

const app = await NestFactory.create<NestFastifyApplication>(AppModule, new FastifyAdapter());
await app.register(helmet);
```

## When to customise

**The Content Security Policy (CSP) is the header most likely to cause trouble.** Its
default is strict (`default-src 'self'`), meaning the page can only load resources from
its own origin. If your frontend:

- loads images from a CDN,
- uses Google Fonts,
- runs an analytics script from another domain,
- uses inline styles or scripts,

you must add those sources to the policy, or the browser blocks them (and your own code
breaks):

```typescript
app.use(
  helmet({
    contentSecurityPolicy: {
      directives: {
        defaultSrc: [`'self'`],
        imgSrc: [`'self'`, 'https://cdn.example.com'],
        scriptSrc: [`'self'`, 'https://analytics.example.com'],
        styleSrc: [`'self'`, `'unsafe-inline'`],   // allow inline <style>
      },
    },
  }),
);
```

Two scenarios you will meet in practice:

- **GraphQL with Apollo Sandbox / playground**: the sandbox UI loads scripts from Apollo's
  CDN; you will need a CSP like the one in the official docs.
- **Your frontend is a separate SPA**: Helmet only protects the *API's* responses, not the
  SPA's. Apply an equivalent middleware (or the same headers) on the frontend server too.

## Order matters

Helmet must be registered **before** your routes, otherwise routes defined earlier bypass
it. Putting `app.use(helmet())` first in `main.ts`, before CORS and before anything else
that adds middleware, is the safe habit. (The same rule applies to CORS from the previous
chapter.)

## Where Helmet is NOT the whole answer

Helmet only adds headers. It does not:

- sanitise user input (that is validation + escaping in your templates),
- replace rate limiting (chapter 16) or CSRF protection (chapter 15),
- protect WebSocket endpoints the same way.

It is one cheap, high-value layer in a defence-in-depth stack. Set it and forget it.
