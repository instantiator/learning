# 07. How API Versioning Works

## Why version an API

Applications change. When you need to make a **breaking change** to an API (rename a
field, change a response shape, remove an endpoint), existing clients that depend on the
old behavior would break.

Versioning lets you run several versions of the same route **side by side** in one
application: version 1 keeps working for old clients while new clients use version 2. You
deprecate and remove version 1 at your leisure.

Versioning is for **HTTP** applications only (it has no meaning for WebSockets or
microservices).

## Enabling versioning

Versioning is switched on in `main.ts`, and there are four strategies for how a client
states which version it wants.

```typescript
import { NestFactory } from '@nestjs/core';
import { VersioningType } from '@nestjs/common';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.enableVersioning({
    type: VersioningType.URI,
  });
  await app.listen(3000);
}
```

### The four strategies

| Strategy       | How the client chooses the version                       | Example                                 |
| -------------- | -------------------------------------------------------- | --------------------------------------- |
| `URI` (default)| The version is part of the URL path                      | `GET /v2/cats`                          |
| `HEADER`       | A custom header carries the version                      | `X-Version: 2`                          |
| `MEDIA_TYPE`   | The `Accept` header carries it                           | `Accept: application/json;v=2`          |
| `CUSTOM`       | You provide a function that extracts it from the request | anything you like                       |

### URI versioning details

```typescript
app.enableVersioning({
  type: VersioningType.URI,
  // prefix: 'v',   // default prefix before the number: "/v1/cats"
  // prefix: false, // disable the "v", giving "/1/cats"
});
```

The version segment goes *after* any global prefix (`/api`) and *before* the route path:

```text
/api/v1/cats
 ^   ^^
 global  version
```

### Header versioning

```typescript
app.enableVersioning({
  type: VersioningType.HEADER,
  header: 'X-Version',
});
// Request with: X-Version: 2
```

### Media type versioning

```typescript
app.enableVersioning({
  type: VersioningType.MEDIA_TYPE,
  key: 'v=',      // the marker used inside the Accept header
});
// Request with: Accept: application/json;v=2
```

### Custom versioning

```typescript
const extractor = (request: FastifyRequest) => '2'; // any logic you like

app.enableVersioning({
  type: VersioningType.CUSTOM,
  extractor,
});
```

## Declaring versions on controllers and routes

Once versioning is enabled, **a resource must declare a version or it is unreachable**
(unversioned routes return 404).

### On a controller (applies to all its routes)

```typescript
@Controller({ version: '1' })
export class CatsControllerV1 {
  @Get('cats')
  findAll() {
    return 'cats from v1';
  }
}
```

### On individual routes (overrides the controller version)

```typescript
@Controller()
export class CatsController {
  @Version('1')
  @Get('cats')
  findAllV1() {
    return 'cats from v1';
  }

  @Version('2')
  @Get('cats')
  findAllV2() {
    return 'cats from v2';
  }
}
```

### Multiple versions and version-neutral routes

```typescript
// Available on both v1 and v2:
@Controller({ version: ['1', '2'] })
export class CatsController {}

// Available on any version (and when no version is sent):
@Controller({ version: VERSION_NEUTRAL })
export class CatsController {}
```

### A default version

If most of your app is version 1, set `defaultVersion` so controllers without a version
still respond:

```typescript
app.enableVersioning({
  type: VersioningType.URI,
  defaultVersion: '1',
});
```

## How to structure a versioned codebase

Two common layouts:

**1. One controller per version, side by side**

```text
src/cats/
├── cats-v1.controller.ts     @Controller({ version: '1', path: 'cats' })
├── cats-v2.controller.ts     @Controller({ version: '2', path: 'cats' })
└── cats.service.ts           shared business logic
```

Both controllers delegate to the same service; they only differ in what they accept and
return.

**2. Versioned routes in one controller** with `@Version()` on each method (shown above).
Good when only a few routes change.

Tip: keep the *contract* (DTOs, response shapes) per version. Define separate
`cats-v1.dto.ts` and `cats-v2.dto.ts` so version 1's shapes never mutate.

## Behavior to keep in mind

- Unversioned resources return **404** once versioning is on (unless a `defaultVersion`
  is set).
- A request with an unknown version also gets **404**.
- Middleware can be restricted to a version too:

```typescript
consumer
  .apply(LoggerMiddleware)
  .forRoutes({ path: 'cats', method: RequestMethod.GET, version: '2' });
```

- With the `CUSTOM` strategy on Express, pick a *single* version per request; multiple
  candidate versions are only handled reliably by Fastify.
- Versioning and `VERSION_NEUTRAL`: with URI versioning, a neutral resource has no version
  segment in its URL.

## When to version

Version aggressively enough that you never silently break clients, but not so aggressively
that you maintain parallel copies forever. A pragmatic default:

- Additive changes (new field, new endpoint) → no version bump.
- Breaking changes (removed/renamed fields, changed semantics) → new version.
- Keep a deprecation window: keep the old version until you have confirmed clients moved.
