# 15. What CSRF Is (and When to Protect Against It)

## The attack

**CSRF (Cross-Site Request Forgery)**, sometimes written XSRF, works like this:

1. You are logged into `bank.example.com` and your browser holds a **session cookie** for
   it.
2. While logged in, you visit a malicious page `evil.example.com`.
3. That page secretly submits a form or script to `bank.example.com` — something like
   `POST /transfer` with "send money to the attacker".
4. The browser **automatically includes the cookie** on the request. The bank sees a valid
   session and performs the transfer.

The server cannot tell the forged request from a real one: cookies travel automatically,
and the attacker never needs to read the response.

## Why modern APIs often do not need CSRF protection

The entire attack depends on the browser **automatically** attaching credentials
(cookies). If your API uses **bearer tokens in an `Authorization` header** (the JWT design
from chapter 11), a malicious page cannot include that header — it does not know the token,
and browsers do not send it automatically. The attack simply does not apply.

You should think about CSRF protection when your authentication uses **cookies** —
typically a classic web app or a SPA with cookie-based sessions.

## Defence strategies (in order of preference)

1. **Don't use cookies for auth.** Bearer tokens (JWT) sent in the `Authorization` header
   eliminate the attack surface entirely. This is why API-first apps rarely need CSRF
   tooling.
2. **SameSite cookies.** Setting `SameSite=Lax` (or `Strict`) on session cookies tells the
   browser to withhold the cookie on cross-site requests — killing the attack in the
   browser itself. Supported by all modern browsers. Use this even alongside other
   measures.
3. **CSRF tokens.** A secret token that is sent on state-changing requests *and* checked
   by the server. The token lives in a page-visible place (a cookie or hidden form field)
   so the legitimate frontend can include it, but a foreign page cannot read it.
   Two common token patterns:
   - **Synchronizer token**: server stores the token in the session and compares it with
     the submitted one.
   - **Double-submit cookie**: the server sets the token in a cookie; the frontend echoes
     it back in a header; the server checks they match.
4. **Custom headers.** Require a custom header (e.g. `X-Requested-With`) on
   state-changing requests. The same cross-origin rules (preflight, chapter 13) stop
   foreign pages from setting them. Weaker than tokens but very simple.

## What NestJS offers

NestJS does not have CSRF protection built in; the documentation recommends packages.

### Express

```bash
npm install csrf-csrf
```

This implements the **double-submit cookie** pattern. It needs `cookie-parser` (or session
middleware) set up first, then registers the protection middleware:

```typescript
import { doubleCsrf } from 'csrf-csrf';

const {
  invalidCsrfTokenError,
  generateToken,          // call this to mint a token for the client
  validateRequest,        // convenience helper for custom middleware
  doubleCsrfProtection,   // the middleware that rejects bad tokens
} = doubleCsrf({
  getSecret: () => process.env.CSRF_SECRET,
  cookieName: 'csrf-token',
  cookieOptions: { httpOnly: true, sameSite: 'lax' },
});

// in main.ts / an AppModule:
app.use(cookieParser());
app.use(doubleCsrfProtection);

// expose a token to the client (e.g. on login):
app.use('/auth/login', (req, res, next) => {
  res.cookie('csrf-token', generateToken(req, res), { httpOnly: true });
  next();
});
```

The client then reads the token from the cookie (non-httpOnly variants let JS read it)
and echoes it in a header such as `x-csrf-token` on every state-changing request. The
middleware verifies cookie and header match.

### Fastify

```bash
npm install @fastify/csrf-protection
```

```typescript
await app.register(fastifyCsrf);
```

The Fastify plugin requires a storage plugin to be registered first (see its docs) and
works as a Fastify plugin rather than plain middleware.

## Building an API with CSRF in mind (practical summary)

| Your architecture                                   | What to do                                    |
| --------------------------------------------------- | --------------------------------------------- |
| JWT bearer tokens, mobile + SPA                    | Nothing extra needed; tokens are immune.      |
| Cookie sessions (web app / SPA with cookies)        | SameSite cookie **and** a CSRF token check.   |
| Public read-only API                               | Nothing needed (no state-changing requests to protect). |

## The mental model

- CSRF abuses **trust in your cookies**. The fix is either *stop trusting cookies
  automatically* (bearer tokens), or *add a second secret the attacker cannot obtain*
  (CSRF tokens / SameSite).
- Do not confuse CSRF with XSS: XSS executes *your* page's scripts; CSRF forges requests
  *using your* cookies. Helmet (chapter 14) leans toward XSS; this chapter's tooling
  targets CSRF.
- CSRF protection rarely applies to JSON APIs that already use `Authorization` headers —
  add it only when cookie-based sessions are in play.
