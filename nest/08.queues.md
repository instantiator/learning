# 08. How and When Queues Are Used

## What a queue is

A queue is a waiting line of **jobs** waiting to be processed. One part of your system
*enqueues* a job ("send this email", "resize this image", "import this CSV"); another part
(a *worker*) *picks it up and processes it* when it has capacity.

NestJS integrates with **BullMQ**, the most popular Node.js queue library, through the
`@nestjs/bullmq` package. BullMQ stores jobs in **Redis**, which means the queue survives
restarts and can be shared across many application instances.

## When to use a queue

Use a queue when you have work that should **not** happen inline during an HTTP request:

- Slow or long-running work (email, PDF generation, video processing).
- Work that might fail and should be **retried** with a delay.
- Work you want to **spread over time** or across several machines.
- Work that should survive a crash and continue later.

Do **not** use a queue for work that must happen immediately before responding, or for
trivial in-process tasks — plain `await` or `setTimeout` is enough for those.

## How it maps to an API call

A typical flow:

```text
POST /orders
   -> OrderService creates the order
   -> adds a job "invoice" to the queue   (returns immediately, response is fast)
   -> Worker process later picks up the job
   -> generates + emails the invoice      (minutes of work, off the request path)
```

The client gets a fast response; the heavy work happens asynchronously, retries included.

## Install and set up

```bash
npm install @nestjs/bullmq bullmq
```

BullMQ needs a running **Redis** server (e.g. `redis-server` locally, or a hosted Redis
like Upstash).

### 1. Register the queue in a module

```typescript
// invoices/invoices.module.ts
import { Module } from '@nestjs/common';
import { BullModule } from '@nestjs/bullmq';

@Module({
  imports: [
    BullModule.forRoot({
      connection: { host: 'localhost', port: 6379 },   // Redis connection
    }),
    BullModule.registerQueue({ name: 'invoices' }),    // define the queue
  ],
})
export class InvoicesModule {}
```

`forRoot` configures the Redis connection once; `registerQueue` defines each queue.

### 2. Add jobs from a service

```typescript
// invoices/invoices.service.ts
import { Injectable } from '@nestjs/common';
import { InjectQueue } from '@nestjs/bullmq';
import { Queue } from 'bullmq';

@Injectable()
export class InvoicesService {
  constructor(@InjectQueue('invoices') private readonly invoicesQueue: Queue) {}

  async enqueue(orderId: number) {
    await this.invoicesQueue.add(
      'generate',                    // job type
      { orderId },                   // job data (must be JSON-serializable)
      {
        attempts: 5,                 // retry up to 5 times on failure
        backoff: { type: 'exponential', delay: 2000 }, // wait 2s, 4s, 8s...
        removeOnComplete: { age: 60_000 },  // keep finished jobs for 1 minute
      },
    );
  }
}
```

Useful job options:

| Option            | Meaning                                                |
| ----------------- | ------------------------------------------------------ |
| `delay`           | Do not start processing until N ms from now.           |
| `attempts`        | How many times to retry on failure.                    |
| `backoff`         | Waiting strategy between retries (fixed / exponential).|
| `removeOnComplete`| Keep or delete the job record after success.           |
| `removeOnFail`    | Keep or delete the job record after all attempts fail. |

### 3. Process jobs in a worker

Create a class with `@Processor('invoices')`. Every job of that queue is delivered to
`process()`:

```typescript
// invoices/invoices.processor.ts
import { Processor, WorkerHost } from '@nestjs/bullmq';
import { Job } from 'bullmq';

@Processor('invoices')
export class InvoicesProcessor extends WorkerHost {
  async process(job: Job<{ orderId: number }>) {
    if (job.name === 'generate') {
      const { orderId } = job.data;
      await this.renderAndEmailInvoice(orderId); // the heavy work
    }
  }
}
```

Register the processor as a provider in the same module:

```typescript
@Module({
  imports: [BullModule.registerQueue({ name: 'invoices' })],
  providers: [InvoicesService, InvoicesProcessor],
})
export class InvoicesModule {}
```

The worker processes jobs one at a time by default. To control throughput, set
`concurrency` on the `@Processor('invoices', { concurrency: 5 })` decorator (jobs run in
parallel up to that number within this process). You can also run *multiple* copies of the
app — BullMQ distributes jobs among them, which is how you scale.

### 4. Error handling and retries

If `process()` **throws**, the job fails. BullMQ then re-enqueues it according to
`attempts`/`backoff` set when the job was added. After the last attempt it goes to the
"failed" set, where you can inspect it (e.g. in the BullMQ dashboard or via the queue
API) and re-enqueue or clean it up.

The same queue can also be used from a different service to inspect state:

```typescript
const counts = await queue.getJobCounts(); // { waiting, active, completed, failed, delayed }
```

## Monitoring

BullMQ has an official dashboard called **Bull Board** (`bull-board`), and BullMQ itself
emits events you can subscribe to for logging/alerting:

```typescript
this.invoicesQueue.on('completed', (job) => log(job.id, 'done'));
this.invoicesQueue.on('failed', (job, err) => log(job.id, 'failed', err));
```

## Queues vs. the alternatives

| Situation                            | Use                             |
| ------------------------------------ | ------------------------------- |
| Reliable async work, retries, scale  | **Queue (BullMQ + Redis)**      |
| Recurring work at a schedule         | `@nestjs/schedule` (chapter 10) |
| Push updates to browsers in real time| SSE (09) or WebSockets (17)     |
| Simple fire-and-forget, no retries   | plain `await` in an async method|

Rule of thumb: if you find yourself writing `setTimeout`/`setInterval` to retry or defer
important work, reach for a queue instead.
