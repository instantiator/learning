# 01. Fundamentals and Feature Overview

## What NestJS is

NestJS is a framework for building **server-side applications in Node.js**. It gives your
application a fixed structure and a set of conventions, so that code written by different
people (or on different days) looks the same and fits together.

Its slogan is "a progressive Node.js framework". "Progressive" means you can start small
and grow: a tiny API today, and a large, modular system later, without rewriting anything.

Two things make NestJS distinctive compared to plain Express:

1. It is written in and designed around **TypeScript**.
2. It borrows an architecture pattern from the Java world called **dependency injection**
   (DI). You write classes, declare what they need, and the framework builds them for you.

NestJS is not a different runtime — underneath it runs a web server library you may already
know. By default that is **Express**; you can also swap in **Fastify** for higher
performance. This is done through an "adapter" so your application code does not need to
change.

## A note on the ecosystem and tools

If you have not used TypeScript or its build tools before, here is the mental model you need:

- **Node.js** is the JavaScript runtime that executes your code outside a browser.
- **TypeScript** is JavaScript with type annotations. Browsers and Node.js cannot run it
  directly, so it must be **compiled** (translated) into plain JavaScript before running.
- **The compiler** is a program called `tsc`. NestJS uses it to turn your `src/` TypeScript
  into `dist/` JavaScript. There is a faster alternative called **SWC** you can switch to.
- **npm** is the package manager. `npm install` downloads libraries (called "packages")
  into a `node_modules/` folder. A `package.json` file lists which packages your project
  needs.
- **npm scripts** are shortcuts defined in `package.json`, run with `npm run <name>`. A
  fresh Nest project comes with scripts like `build`, `start`, `start:dev`, `test` and
  `lint`.
- **Decorators** are a TypeScript feature NestJS leans on heavily. A decorator is a piece
  of syntax that starts with `@` and is placed above a class or a method to attach metadata
  to it. NestJS reads that metadata and wires your application together from it.

If any term in this guide is unfamiliar, the final file (`18.glossary.md`) has short
plain-language definitions.

## The four core building blocks

Every NestJS application is built from the same few ingredients.

### 1. Modules (`@Module`)

A module is a grouping unit. It declares which controllers and providers belong together and
what the module imports from other modules. It is the "shelf" that keeps related code in one
place.

```typescript
import { Module } from '@nestjs/common';
import { CatsController } from './cats.controller';
import { CatsService } from './cats.service';

@Module({
  controllers: [CatsController],
  providers: [CatsService],
})
export class CatsModule {}
```

Every application has a **root module** (`AppModule`) that pulls everything else together.
Modules can import other modules, and modules export providers so that other modules can use
them.

### 2. Controllers (`@Controller`)

A controller is the "front door" of the API. It maps incoming HTTP requests to methods. The
decorators on the methods describe the route, the HTTP verb, and what parts of the request
to read.

```typescript
import { Controller, Get, Param } from '@nestjs/common';

@Controller('cats')
export class CatsController {
  @Get(':id')
  findOne(@Param('id') id: string) {
    return { id };
  }
}
```

Controllers should stay thin. They receive the request and hand off to a service.

### 3. Providers / Services (`@Injectable`)

Providers are classes that do the actual work: reading from a database, calling other APIs,
implementing business rules. They are marked with `@Injectable()` so NestJS knows it may
manage them. A service is just a provider whose job is clear business logic.

```typescript
import { Injectable } from '@nestjs/common';

@Injectable()
export class CatsService {
  findAll() {
    return ['Tom', 'Garfield'];
  }
}
```

### 4. Dependency Injection

Instead of writing `new CatsService()` yourself, you declare the dependency in the
constructor and NestJS hands it to you:

```typescript
@Controller('cats')
export class CatsController {
  constructor(private readonly catsService: CatsService) {}

  @Get()
  findAll() {
    return this.catsService.findAll();
  }
}
```

NestJS keeps a registry of providers, builds them for you, and injects them where asked. It
also builds dependencies of dependencies. This is the *dependency injection container*.
Benefits: providers are easy to reuse, and easy to swap with a fake in tests.

## How a request travels through the app

When an HTTP request arrives, it passes through a chain of handlers before (and after)
reaching your controller method:

```
Request
   -> Middleware          (runs first; e.g. logging, body parsing)
   -> Guards              (decide "is this request allowed at all?")
   -> Interceptors        (can transform or wrap the response; run before and after)
   -> Pipes               (validate / transform the incoming data)
   -> Controller method   (your code)
   -> Interceptors        (run again after the handler returns)
   -> Exception filters   (catch errors and turn them into a response)
Response
```

Each of these is a feature you can add piece by piece. You can attach them to a single
route, to a whole controller, or globally to every route.

## The feature list

Below is a list of everything NestJS ships with, with a short description of each. Later
files in this guide go into detail on the ones you asked about; the rest are listed here so
you know they exist and roughly what they are for.

### Core architecture

| Feature             | What it does |
| ------------------- | ------------ |
| Modules             | Groups related code; the unit of the application's structure. |
| Controllers         | Map HTTP routes to methods. |
| Providers / Services| Classes that do the work; managed and injected by NestJS. |
| Dependency injection| NestJS builds objects and injects them, so code is loosely coupled and easy to test. |
| Custom decorators   | Your own `@Something()` decorators to attach metadata (e.g. `@Public()`). |
| Dynamic modules     | Modules you can configure when importing, e.g. `CacheModule.register({...})`. |
| Module reference    | A way to reach into modules at runtime for advanced cases. |
| Lazy loading        | Load a module only when it is first needed, to speed up startup. |
| Circular dependencies | Handling for two modules or providers that depend on each other. |
| Provider scopes     | Controls how often a provider is created (once per app, per request, per use). |
| Lifecycle events    | Hooks that run at startup/shutdown, e.g. `onModuleInit`, `onApplicationShutdown`. |
| Execution context   | A wrapper giving guards/pipes/etc. uniform access to HTTP, WebSocket or microservice requests. |
| Discovery service   | Find providers/decorators at runtime to build plugins. |
| Platform agnosticism| The same code can run on Express or Fastify (or non-HTTP platforms). |

### Request handling

| Feature             | What it does |
| ------------------- | ------------ |
| Middleware          | Runs before the route handler for every matching request. |
| Guards              | Decide whether a request may proceed (used for authentication/authorization). |
| Interceptors        | Wrap the route handler: can transform results, add extra logic, or time requests. |
| Pipes               | Validate and transform data *before* the handler receives it. |
| Exception filters   | Catch thrown errors and convert them into a structured HTTP response. |
| Built-in exceptions | Ready-made errors like `NotFoundException`, `UnauthorizedException`, `BadRequestException`. |
| Custom decorators   | (see above) extract data from requests in a reusable way. |
| Routing & params    | `@Query()`, `@Param()`, `@Body()`, `@Headers()` to read request data. |
| File upload         | Accept and store uploaded files (`@nestjs/platform-express` / multer). |
| Streaming files     | Return large files without loading them fully into memory. |
| HTTP module         | A wrapper around `axios` for calling external HTTP services from inside your app. |
| MVC / templating    | Render server-side HTML with Handlebars, Pug or EJS. |
| Cookies             | Read and set cookies (`@nestjs/platform-express`). |
| Sessions            | Session-based state via `express-session`. |
| Static files        | Serve images, CSS, etc. from a folder (`@nestjs/serve-static`). |

### Data and application logic

| Feature             | What it does |
| ------------------- | ------------ |
| Validation          | `class-validator` + pipes reject bad input before your code runs. |
| Serialization       | Transform response objects before they are sent (hide passwords, rename fields). |
| Configuration       | Read settings from `.env` files and environment variables (`@nestjs/config`). |
| Databases (SQL)     | TypeORM/Prisma integration for relational databases. |
| Databases (Mongo)   | Mongoose integration for MongoDB. |
| Caching             | Store responses or data in memory or Redis (`@nestjs/cache-manager`). |
| Queues              | Job queues via BullMQ + Redis (`@nestjs/bullmq`). |
| Task scheduling     | Cron jobs and intervals (`@nestjs/schedule`). |
| Logger              | A built-in structured logger, replaceable with e.g. `pino` or `winston`. |
| Testing             | Jest unit tests and end-to-end tests with supertest. |

### Real-time and streaming

| Feature             | What it does |
| ------------------- | ------------ |
| WebSockets          | Two-way real-time communication using `socket.io` or `ws` (gateways). |
| Server-Sent Events  | One-way server-to-browser push over plain HTTP. |
| Microservices       | Build a system of small services that talk over TCP, Redis, MQTT, NATS, Kafka, gRPC or RabbitMQ. |
| GraphQL             | A GraphQL API layer on top of Nest (`@nestjs/graphql`, code-first or schema-first). |
| OpenAPI / Swagger   | Generate API documentation and a test UI from your code (`@nestjs/swagger`). |

### Security and robustness

| Feature             | What it does |
| ------------------- | ------------ |
| Authentication      | Login flows (JWT, Passport strategies, sessions). |
| Authorization       | Rules for who may access what (roles, policies, CASL). |
| CORS                | Control which browser origins may call your API. |
| CSRF protection     | Protect cookie-based apps from cross-site request forgery. |
| Helmet              | Set security headers to harden your HTTP responses. |
| Rate limiting       | Limit how many requests a client can make in a time window. |
| Encryption/hashing  | Best practices for storing passwords (bcrypt) and handling secrets. |
| Compression         | gzip/br compression of HTTP responses (`compression` middleware). |
| Performance         | Guidance for Fastify, caching and build speed (SWC). |

### Developer experience

| Feature             | What it does |
| ------------------- | ------------ |
| Nest CLI            | Generates new projects, modules, controllers, guards, etc. |
| Devtools            | Debugging and tracing tools for running apps (NestJS Devtools). |
| Unit testing        | Scaffolded test setup with Jest. |
| End-to-end testing  | Full HTTP tests against a running app (`test/app.e2e-spec.ts`). |
| Application context | Run modules without an HTTP server (for scripts and jobs). |
| Health checks       | Endpoints that report whether the app and its dependencies are alive (`@nestjs/terminus`). |

## How the pieces fit together (a tiny example)

```text
HTTP GET /cats/42
        |
        v
[CatsController]  @Get(':id') findOne()
        |
        v
[CatsService]     getById(42)      <- business logic, talks to DB
        |
        v
[CatEntity]       returned, serialized, sent as JSON
```

The point of the architecture is **separation of concerns**: each piece has one job, and
you can add cross-cutting concerns (auth, logging, caching) without touching your business
logic.

## Choosing what to use

You do not need every feature. A sensible default stack for a typical new API:

- Controllers + services + modules (the core)
- `@nestjs/config` for settings
- Validation pipes with `class-validator`
- An ORM (TypeORM or Prisma) for the database
- `@nestjs/jwt` + guards for authentication
- `helmet`, CORS, and `@nestjs/throttler` for security hardening
- Swagger for documentation

Everything else — queues, WebSockets, GraphQL, SSE, scheduling — you add only when your
application actually needs it. The rest of this guide walks through each of these areas.
