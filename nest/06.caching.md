# 06. How Caching Is Configured

## What caching does

Caching stores the result of expensive work (a database query, a slow computation) so that
the next identical request can be answered from the cache instead of doing the work again.
This is one of the biggest, easiest performance wins for a typical API.

NestJS ships a caching module, `@nestjs/cache-manager`, built on the `cache-manager`
package. By default everything is stored **in memory** (inside the running process) with a
**TTL** — *time to live* — that says how long an entry stays valid before it expires.

## Install

```bash
npm install @nestjs/cache-manager cache-manager
```

## Enable it

```typescript
// app.module.ts
import { Module } from '@nestjs/common';
import { CacheModule } from '@nestjs/cache-manager';

@Module({
  imports: [
    CacheModule.register({
      ttl: 5000,        // milliseconds; entries expire after 5 seconds
      isGlobal: true,   // so every module can use it without importing
    }),
  ],
})
export class AppModule {}
```

Key options:

- `ttl` — milliseconds before an entry expires. `0` means "never expires".
- `isGlobal` — make the module available everywhere without per-module imports.

## Two ways to use the cache

There are two styles, and they are not mutually exclusive.

### Style A: programmatic (you call the cache yourself)

Inject the cache manager and use it directly:

```typescript
import { Inject, Injectable } from '@nestjs/common';
import { CACHE_MANAGER, Cache } from '@nestjs/cache-manager';

@Injectable()
export class PricesService {
  constructor(@Inject(CACHE_MANAGER) private readonly cache: Cache) {}

  async getPrice(ticker: string) {
    const cached = await this.cache.get(`price:${ticker}`);
    if (cached !== undefined) return cached;

    const price = await this.slowExchangeCall(ticker); // expensive
    await this.cache.set(`price:${ticker}`, price, 30000); // keep for 30s
    return price;
  }
}
```

The `Cache` instance methods:

| Method               | Purpose                                   |
| -------------------- | ----------------------------------------- |
| `get(key)`           | Read a value; `undefined` if not present  |
| `set(key, value, ttl?)` | Store a value (TTL in milliseconds)   |
| `del(key)`           | Remove one entry                          |
| `clear()`            | Remove everything                         |

This style gives you complete control: custom keys, per-key TTLs, and decisions about what
to cache.

### Style B: automatic (intercept the response)

Attach the `CacheInterceptor` and NestJS caches **GET responses** for you, keyed by the
request URL:

```typescript
import { Controller, Get, UseInterceptors } from '@nestjs/common';
import { CacheInterceptor } from '@nestjs/cache-manager';

@Controller('cats')
@UseInterceptors(CacheInterceptor)
export class CatsController {
  @Get()
  findAll() {
    return this.slowQuery();
  }
}
```

Or globally, on every GET endpoint:

```typescript
// app.module.ts
import { CacheModule, CacheInterceptor } from '@nestjs/cache-manager';
import { APP_INTERCEPTOR } from '@nestjs/core';

@Module({
  imports: [CacheModule.register({ isGlobal: true })],
  providers: [{ provide: APP_INTERCEPTOR, useClass: CacheInterceptor }],
})
export class AppModule {}
```

Per-method overrides with decorators:

```typescript
@Get()
@CacheKey('cats-list')    // use this custom key instead of the URL
@CacheTTL(60_000)         // override the default TTL for this route
findAll() {
  return this.slowQuery();
}
```

> **Important:** only `GET` routes are cached this way. Mutating requests (POST, PUT,
> DELETE) are never auto-cached. And routes that inject the raw response object with
> `@Res()` cannot be auto-cached.

## Rules of thumb (what to cache, what not to)

- Cache **reads** — lists, profile data, expensive lookups.
- Never auto-cache **writes** or anything with side effects.
- Be careful with **per-user data**. The auto interceptor keys on URL only, so `GET
  /profile` would return one user's data to everyone. Either exclude such routes, include
  the user id in the key (via a custom interceptor's `trackBy`), or use the programmatic
  style with keys like `profile:${userId}`.
- Pick a TTL that matches how often the data actually changes.

## Using Redis (or any real store)

In-memory caching is fine for one process, but it is per-instance: if you run several app
copies, each has its own cache, and a restart wipes it. For shared storage, plug in a
store such as **Redis**. The current `cache-manager` uses a library called **Keyv** for
stores.

```bash
npm install @keyv/redis
```

```typescript
import KeyvRedis from '@keyv/redis';
import { Keyv } from 'keyv';
import { KeyvCacheableMemory } from 'cacheable';

CacheModule.registerAsync({
  useFactory: () => ({
    stores: [
      new Keyv({ store: new KeyvCacheableMemory({ ttl: 60000, lruSize: 5000 }) }),
      new KeyvRedis('redis://localhost:6379'),
    ],
  }),
});
```

The first store is the primary; the rest act as fallbacks. You can also simply pass a
single Redis store if you only want Redis. Keyv has adapters for many backends (SQLite,
PostgreSQL, MongoDB, and so on) — check the Keyv documentation.

## Async configuration

Use `registerAsync()` when cache settings come from `ConfigService`:

```typescript
CacheModule.registerAsync({
  imports: [ConfigModule],
  inject: [ConfigService],
  useFactory: (config: ConfigService) => ({
    ttl: config.get<number>('CACHE_TTL_MS', 5000),
  }),
});
```

## Gotchas to remember

- TTL is in **milliseconds** here (not seconds).
- The default `ttl` is `0`, i.e. never expires — set an explicit TTL or you cache forever.
- In-memory cache is lost on restart and not shared between instances.
- If a background job updates data, remember to invalidate the cache (`del`/`clear`), or
  wait out the TTL.
- Don't cache user-specific responses on the same URL.
